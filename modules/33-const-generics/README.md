# M33 - Const generics, `const fn`, ZST

> Часть XI "Продвинутые идиомы". Предыдущий модуль: [M32 type-state и фантомные типы](../32-typestate-patterns/README.md).

## Цель модуля

Дженерики из [M11](../11-generics/README.md) обобщали код по *типам*: `Vec<T>` работает для любого
`T`. Но некоторые величины - это не типы, а *значения*, известные во время компиляции: длина
массива, размерность матрицы, ширина буфера. `[i32; 4]` и `[i32; 8]` - разные типы, отличающиеся
только числом. Const generics позволяют обобщать код и по таким числам: `struct Matrix<const R:
usize, const C: usize>` - семейство типов, параметризованное размерами, где размер живёт в системе
типов и проверяется компилятором. Так пишут структуры фиксированного размера без обращения к куче
и с гарантией согласованности размерностей на этапе компиляции.

Рядом стоят две смежные темы. `const fn` - функции, которые компилятор умеет выполнять *во время
компиляции*: ими инициализируют константы, вычисляют таблицы, задают размеры массивов. И ZST
(zero-sized types) - типы нулевого размера (`()`, пустые структуры, `PhantomData`): они ничего не
занимают в памяти, но полноценно участвуют в системе типов, что делает их основой маркеров,
type-state (M32) и ряда оптимизаций коллекций.

Общий мотив модуля - *перенос работы и проверок на этап компиляции*: размеры в типах, вычисления в
`const fn`, метки в ZST. Всё это - обобщение уже пройденного (дженерики, массивы, трейты) на
значения и на нулевой размер.

После модуля вы умеете:

- [ ] писать функции и типы, обобщённые по `const N: usize`, и работать с массивами `[T; N]`
      обобщённо;
- [ ] выражать зависимости размерностей в типах (`transpose: Matrix<R, C> -> Matrix<C, R>`);
- [ ] писать `const fn` и понимать, что в них разрешено, а что нет;
- [ ] вычислять массивы и таблицы во время компиляции (`const TABLE: [_; N] = build();`);
- [ ] строить и заполнять массивы обобщённого размера (`std::array::from_fn`);
- [ ] распознавать ZST, объяснять `size_of == 0` и применять их как бесплатные маркеры.

## 1. Const generics: числа как параметры типа

Массивы Rust несут длину *в типе*: `[i32; 4]` и `[i32; 8]` - разные типы. Поэтому функция,
принимающая `[i32; 4]`, не возьмёт `[i32; 8]`, а раньше приходилось либо фиксировать длину, либо
переходить на срез `&[i32]` и терять размер из типа. Const generics обобщают код по длине:

```rust,ignore
fn sum<const N: usize>(arr: [i32; N]) -> i32 {
    let mut total = 0;
    for x in arr { total += x; }
    total
}

sum([1, 2, 3]);        // N выведено как 3
sum([10, 20, 30, 40]); // N == 4 - та же функция
```

`const N: usize` - параметр *значения*, а не типа: при мономорфизации (M11) компилятор
подставляет конкретное число и генерирует отдельную версию под каждое использованное `N`, ровно
как под каждый тип у обычного дженерика. Параметром может быть целочисленный тип, `bool` или
`char` (числа с плавающей точкой и произвольные структуры пока нельзя). Значение доступно в теле
как обычная константа и в типах (`[T; N]`). Обзор: <https://doc.rust-lang.org/reference/items/generics.html#const-generics>.

## 2. Структуры, обобщённые по размеру

Const-параметры навешивают и на типы. Так строят контейнеры фиксированной ёмкости, не трогая
кучу - хранилище лежит прямо в структуре массивом `[T; N]`:

```rust,ignore
struct RingBuffer<T, const N: usize> {
    data: [Option<T>; N],
    head: usize,
    len: usize,
}

impl<T, const N: usize> RingBuffer<T, N> {
    fn capacity(&self) -> usize { N }   // N виден во всех методах
}
```

Размер `N` - часть типа: `RingBuffer<u8, 4>` и `RingBuffer<u8, 8>` различны, и их нельзя
перепутать. Такой буфер размещается целиком на стеке (или внутри другого объекта), без
аллокации - это ценно для встраиваемых систем и горячих путей. Ограничение массивов: чтобы
создать `[T; N]`, нужно чем-то заполнить все `N` ячеек. Для `T: Copy` с известным значением
годится `[value; N]`; в общем случае - `std::array::from_fn` (раздел 5), а для не инициализируемых
сразу ячеек берут `[const { None }; N]` / `Option` или `MaybeUninit` из [M26](../26-unsafe/README.md).

## 3. Размерности в типах

Ценность const generics не только в отсутствии кучи, но и в том, что *согласованность размеров
проверяет компилятор*. Операция может связывать входные и выходные размерности в сигнатуре:

```rust,ignore
struct Matrix<const R: usize, const C: usize> {
    data: [[f64; C]; R],   // R строк по C столбцов
}

impl<const R: usize, const C: usize> Matrix<R, C> {
    fn transpose(&self) -> Matrix<C, R> {   // тип результата - с переставленными размерами
        // ...
    }
}
```

`transpose` типом гарантирует: результат имеет размер `C x R`. Умножение матриц выражает правило
"внутренние размерности совпадают" прямо в сигнатуре:

```rust,ignore
impl<const M: usize, const N: usize> Matrix<M, N> {
    fn mul<const P: usize>(&self, rhs: &Matrix<N, P>) -> Matrix<M, P> { /* ... */ }
    //                              ^ N здесь ДОЛЖНО совпасть с N слева, иначе не скомпилируется
}
```

Попытка умножить несогласованные матрицы - ошибка компиляции, а не паника на проверке размеров в
рантайме. Так система типов ловит целый класс ошибок линейной алгебры до запуска. (Арифметика над
самими const-параметрами в *типах* - вроде `Matrix<{N + 1}>` - в стабильном Rust ограничена; это
фича `generic_const_exprs`, пока нестабильная: <https://doc.rust-lang.org/nightly/unstable-book/language-features/generic-const-exprs.html>.
Задачи модуля обходятся без неё.)

## 4. `const fn`

`const fn` - функция, которую компилятор умеет выполнить во время компиляции. Обычную функцию
нельзя вызвать в *константном контексте* (инициализация `const`/`static`, длина массива, значение
const-параметра); `const fn` - можно:

```rust,ignore
const fn factorial(n: u64) -> u64 {
    let mut result = 1;
    let mut i = 2;
    while i <= n {
        result *= i;
        i += 1;
    }
    result
}

const F5: u64 = factorial(5);     // вычислено при компиляции: 120
let arr = [0u8; factorial(3) as usize]; // размер массива - результат const fn
```

Ту же `const fn` можно звать и в обычном рантайм-коде - тогда она выполняется как всякая функция.
Ключевое: пометка `const` *разрешает* вычисление на этапе компиляции, но не требует его - место
вызова решает. В `const fn` разрешено не всё: можно арифметику, `if`, `match`, циклы `while`/
`loop`, вызовы других `const fn`; нельзя (в стабильном Rust) то, что требует рантайма или пока не
поддержано const-вычислителем - выделение в куче в общем случае, обращение к типажам без
const-поддержки, `for` по произвольному итератору (потому в примерах циклы через `while`). Набор
разрешённого расширяется от версии к версии. Справка: <https://doc.rust-lang.org/reference/const_eval.html>.

## 5. Массивы, вычисляемые при компиляции

Соединение `const fn` и массивов даёт таблицы, посчитанные компилятором и попадающие в бинарник
готовыми - без инициализации в рантайме:

```rust,ignore
const fn build_squares() -> [u32; 8] {
    let mut table = [0u32; 8];
    let mut i = 0;
    while i < 8 {
        table[i] = (i * i) as u32;
        i += 1;
    }
    table
}

const SQUARES: [u32; 8] = build_squares();  // [0,1,4,9,16,25,36,49] уже в бинарнике
```

Так предвычисляют CRC-таблицы, таблицы синусов, маски - всё, что раньше считали при старте
программы. В рантайме доступа к диску/вычислений нет: значение уже в статической памяти. Для
заполнения массива *в рантайме* (когда данные не константны) есть `std::array::from_fn`, который
строит `[T; N]`, вызывая замыкание для каждого индекса, - удобно для обобщённого `N`, где
`[value; N]` не подходит (нет `Copy` или значение зависит от индекса):

```rust,ignore
let arr: [String; 4] = std::array::from_fn(|i| format!("item {i}"));
```

Документация: <https://doc.rust-lang.org/std/array/fn.from_fn.html>.

## 6. ZST: типы нулевого размера

Zero-sized type (ZST) - тип, значение которого не занимает памяти: `size_of::<T>() == 0`. К ним
относятся `()`, пустые структуры (`struct Marker;`), `PhantomData<T>` (M32) и массивы нулевой
длины (`[T; 0]`). Значение ZST компилятор не хранит - его "создание" не порождает ни байта кода,
но тип полноценно участвует в проверке типов:

```rust,ignore
struct Meters;   // ZST-метка
assert_eq!(std::mem::size_of::<Meters>(), 0);
```

Отсюда бесплатность маркеров и type-state из M32: `Door<Open>` не больше `Door<Closed>`, метка
единицы измерения не увеличивает `Length`. ZST дают и оптимизации коллекций: `HashSet<T>` в
стандартной библиотеке - это `HashMap<T, ()>`, где значение-ZST не занимает места, так что "хранение
множества" не тратит память на значения. Ещё пример - `Vec<()>`: он не выделяет буфер под элементы
(нулевой размер), работая как чистый счётчик. ZST важны и для unsafe-кода (M26-M28): указатель на
ZST не разыменовывается в память, а `size_of`/`align_of` для них требуют аккуратности в ручном
управлении. Разбор: <https://doc.rust-lang.org/nomicon/exotic-sizes.html#zero-sized-types-zsts>.

## 7. Стоимость и границы

Const generics - это мономорфизация по значениям: каждое использованное `N` порождает отдельную
копию кода, как каждый тип у обычного дженерика. Это быстро в рантайме (размеры известны,
оптимизатор разворачивает циклы, всё на стеке), но раздувает бинарник, если `N` принимает много
разных значений - тогда десяток размеров даёт десяток копий функции. Если размер не обязан быть в
типе, дешевле по коду взять срез `&[T]` и один экземпляр функции.

`const fn` ограничена тем, что const-вычислитель умеет исполнять: набор разрешённого хоть и растёт,
но в стабильном Rust он всё ещё заметно ограниченнее рантайма (нет произвольной кучи, не все
трейт-методы const). Сложную
предвычислимую логику иногда проще вынести в build-скрипт или процедурный макрос (M31), чем гнуть
под ограничения `const fn`.

ZST бесплатны по памяти, но не по вниманию: в unsafe-коде нулевой размер - частый источник ошибок
(смещения указателя на ноль, `Vec<ZST>` без буфера), а `size_of == 0` иногда удивляет в расчётах
раскладки (M27). В безопасном коде ZST безопасны и полезны как маркеры.

## 8. Типовые грабли

```text
1. [i32; 4] и [i32; 8] - РАЗНЫЕ типы. Обобщение по длине - только через const N; функция под
   фиксированную длину не возьмёт другую. Нужна произвольная длина без типа -> срез &[T].

2. Создать [T; N] обобщённо нельзя "из ничего": все N ячеек надо заполнить. Для не-Copy или
   зависящих от индекса значений - std::array::from_fn(|i| ...), а не [value; N].

3. const-параметры (в стабильном Rust) - целые, bool, char. НЕ f64, НЕ произвольные структуры.

4. Арифметика над const-параметрами в типах ({N + 1}, {M * N}) в стабильном Rust ограничена
   (generic_const_exprs нестабильна). Проектировать сигнатуры так, чтобы размеры были
   отдельными параметрами (mul<const P>(..) -> Matrix<M, P>), а не вычислялись в типе.

5. В const fn нельзя всё: без произвольной кучи, без не-const трейт-методов, for по итератору
   обычно недоступен -> циклы через while с ручным индексом.

6. const fn РАЗРЕШАЕТ, но не ТРЕБУЕТ compile-time вычисления. В рантайм-контексте она просто
   выполняется. Чтобы значение точно посчиталось при компиляции - положить его в const/static.

7. size_of ZST == 0. Это ломает наивные расчёты (i-й элемент по base + i*size => все по одному
   адресу). В unsafe с ZST нужна отдельная аккуратность; в safe-коде ZST безопасны.

8. Мономорфизация по N раздувает код при многих разных N. Если размер не нужен в типе - срез
   дешевле по размеру бинарника.
```

  обобщение по длине массива.
- `02_const_factorial` - `const fn factorial` и `const fn fib`, используемые в константном

- `04_matrix_transpose` - `Matrix<const R, const C>`: хранение `[[f64; C]; R]`, `transpose` с
  типом `Matrix<C, R>`, `get`/`set`.

**2x - продвинутое**
