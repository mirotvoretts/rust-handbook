# M08 — Времена жизни I

> Часть II «Владение». Предыдущий модуль: [M07 Заимствование](../07-borrowing/README.md).
> Дальше: [M09 Времена жизни II](../09-lifetimes-2/README.md).

## Цель модуля

Понять **времена жизни** (lifetimes) — то, как компилятор доказывает, что ни одна ссылка не
переживёт данные, на которые указывает. В M07 borrow-checker ловил висячие ссылки «магически»;
здесь мы увидим механизм под капотом: **у каждой ссылки есть время жизни**, обычно оно
выводится, но иногда его нужно **назвать явно** (`'a`). Времена жизни — не про то, «сколько
живёт значение», а про то, «на каком участке кода ссылка обязана оставаться валидной».

После модуля вы умеете:

- [ ] объяснить, зачем нужны времена жизни (проблема висячей ссылки);
- [ ] читать и писать аннотации `'a` в сигнатурах функций;
- [ ] применять три правила **элизии** и понимать, когда аннотация не нужна;
- [ ] хранить ссылки в структурах с параметром времени жизни `Struct<'a>`;
- [ ] использовать `'static`.

> [!note] Аналога в C++ нет
> В C++ нет времён жизни в системе типов: компилятор не отслеживает, переживёт ли ссылка/
> указатель свой объект. Вернуть ссылку на локальную переменную — это UB, который в лучшем
> случае поймает санитайзер в рантайме. Времена жизни Rust переносят эту проверку **в
> компиляцию** — это одна из самых непривычных для C++-разработчика частей языка.

## 1. Зачем: проблема висячей ссылки

```rust
fn dangling() -> &String {   // ❌ на что будет указывать результат?
    let s = String::from("hi");
    &s                        // s уничтожится в конце функции — ссылка повиснет
}
```

Такой код не компилируется: `error[E0106]: missing lifetime specifier` / «returns a reference
to data owned by the current function». Компилятору нужно доказать, что возвращаемая ссылка
указывает на данные, которые **живут достаточно долго**. Для этого он и рассуждает о временах
жизни. Здесь данных, переживающих функцию, нет — значит, ссылку вернуть нельзя (нужно вернуть
`String` по значению).

---

## 2. Время жизни как область валидности

Время жизни ссылки — это участок кода, на котором ссылка **обязана** оставаться валидной.
Компилятор сопоставляет его с областью, где живёт значение-владелец:

```rust
let r;                   // ----------+-- 'a (нужно, чтобы r был валиден)
{                        //           |
    let x = 5;           // --+-- 'b  |
    r = &x;              //   |       |
}                        // --+       |   x уничтожен, но 'a ещё идёт →
println!("{r}");         //           |   ❌ 'b короче 'a: ссылка повисла
```

Правило borrow-checker'а: время жизни ссылки не должно выходить за время жизни того, на что
она ссылается. Здесь `x` (`'b`) короче, чем требуется для `r` (`'a`), — ошибка компиляции.

## 3. Аннотации времён жизни в функциях

Когда функция возвращает ссылку, компилятор должен знать, **с каким из входов** связан выход.
Если вход один — очевидно. Если несколько — нужно сказать явно:

```rust
fn longest<'a>(x: &'a str, y: &'a str) -> &'a str {
    if x.len() >= y.len() { x } else { y }
}
```

Читается так: «для некоторого времени жизни `'a`, оба входа живут **хотя бы** `'a`, и результат
живёт `'a`». Это **не меняет** сами ссылки — это **контракт**: результат нельзя использовать
дольше, чем живёт наиболее короткоживущий из входов. Синтаксис:

- `'a` — имя времени жизни (апостроф + строчное имя, по традиции `'a`, `'b`, …);
- параметр объявляется в угловых скобках: `fn longest<'a>(...)`;
- применяется к ссылке: `&'a str` — «ссылка со временем жизни `'a`».

Без аннотации этот код не соберётся: компилятор не может выбрать между «результат живёт как `x`»
и «как `y`».

## 4. Элизия времён жизни (почему аннотации нужны редко)

Большинство функций со ссылками аннотаций **не требуют** — компилятор подставляет их сам по
трём правилам **элизии**:

1. Каждому **входному** параметру-ссылке даётся своё время жизни: `fn(&x, &y)` →
   `fn<'a, 'b>(&'a x, &'b y)`.
2. Если входное время жизни **ровно одно**, оно присваивается **всем** выходным ссылкам:
   `fn(&x) -> &y` → `fn<'a>(&'a x) -> &'a y`.
3. Если среди входов есть `&self`/`&mut self` (метод), то **его** время жизни присваивается всем
   выходным ссылкам.

Пример, где элизия срабатывает (правило 2) и аннотация не нужна:

```rust
fn first_word(s: &str) -> &str {   // ← компилятор видит fn<'a>(&'a str) -> &'a str
    match s.find(' ') {
        Some(i) => &s[..i],
        None => s,
    }
}
```

А в `longest` два входных времени жизни (правило 1 даёт `'a` и `'b`), правило 2 неприменимо,
`self` нет — компилятор не знает, что писать, и **требует** явную аннотацию. Правило: если
элизия не разрешает вопрос однозначно — аннотируйте руками.

## 5. Времена жизни в структурах

Структура **может хранить ссылку**, но тогда обязана объявить время жизни: это значит «экземпляр
структуры не может пережить данные, на которые ссылается его поле».

```rust
struct Excerpt<'a> {
    part: &'a str,
}

impl<'a> Excerpt<'a> {
    fn new(part: &'a str) -> Excerpt<'a> {
        Excerpt { part }
    }
    fn part(&self) -> &str {   // элизия (правило 3): результат живёт как &self
        self.part
    }
}
```

- `struct Excerpt<'a>` — параметр времени жизни, как обобщённый параметр типа.
- `impl<'a> Excerpt<'a>` — время жизни объявляется и на `impl`.
- Экземпляр `Excerpt` валиден ровно пока жива строка, на которую смотрит `part`.

Так строят «представления» (views), не владеющие данными: парсеры, срезы структур, курсоры.
Структура, хранящая только владеющие поля (`String`, `Vec`), параметра времени жизни **не
требует** — он нужен именно из-за ссылок внутри.

## 6. `'static`

`'static` — особое время жизни: «данные живут всю программу». Строковые литералы имеют тип
`&'static str`, потому что вшиты в бинарник:

```rust
fn size_name(n: u32) -> &'static str {
    match n {
        0..=9 => "small",
        10..=99 => "medium",
        _ => "large",
    }
}
```

Возврат `&'static str` безопасен без привязки ко входу: литералы живут вечно. `'static`
встречается и как ограничение в дженериках/трейт-объектах (позже) — но там значение немного
другое; пока запомните: строковые литералы — `&'static str`.

---

## 7. Тизер к M09

Мы связывали времена жизни знаком «равно» (`'a` для всех). Но между ними бывают **отношения
подтипирования**: время жизни можно «укоротить», где-то это безопасно (ковариантность), а
где-то нет (инвариантность у `&mut`). Плюс — reborrow, времена жизни высшего ранга (`for<'a>`)
и как NLL (M07) уживается со всем этим. Это следующий, более глубокий модуль **Времена жизни
II** — за рамками базовой книги.
