# M32 - Type-state, фантомные типы, sealed-трейты

> Часть XI "Продвинутые идиомы". Предыдущий модуль: [M31 процедурные макросы](../31-procedural-macros/README.md).

## Цель модуля

До сих пор система типов проверяла, что мы не перепутали `i32` со `String`. Этот модуль про то,
как заставить её проверять *смысл* программы: что нельзя прочитать из закрытого файла, отправить
запрос без адреса, сложить метры с секундами или выполнить SQL на неаутентифицированном
соединении. Идея одна - закодировать факты о состоянии значения в его *типе*, чтобы недопустимая
операция не компилировалась. Ошибка, пойманная компилятором, не станет паникой в рантайме; целый
класс багов исчезает, потому что соответствующий код невозможно написать.

Три техники складываются в этот подход:

- *фантомные типы* (`PhantomData<T>`) - параметр типа, который влияет на проверку типов, но не
  занимает места и не хранит значения. Так к значению "приклеивают" метку (единицу измерения,
  состояние, владельца) без рантайм-стоимости;
- *type-state* - состояние объекта выражено его типом: `Door<Open>` и `Door<Closed>` - разные
  типы, и методы, доступные в одном состоянии, физически отсутствуют в другом. Переход между
  состояниями - метод, *потребляющий* старый тип и возвращающий новый;
- *sealed-трейты* - трейты, которые никто, кроме нашего крейта, не может реализовать. Так
  фиксируют закрытое множество реализаций (например, множество допустимых состояний), сохраняя
  возможность добавлять методы без слома чужого кода.

Всё это - идиомы, а не возможности языка: они строятся из уже известных дженериков (M11),
трейтов (M12), владения (M06) и ZST. Модуль показывает, как из них собирать API, где неверное
использование - ошибка компиляции.

После модуля вы умеете:

- [ ] применять `PhantomData<T>` как zero-cost метку и объяснять, зачем компилятору нужен этот
      "неиспользуемый" параметр;
- [ ] строить newtype с фантомным параметром (типизированные id, единицы измерения) и запрещать
      смешивание несовместимых значений;
- [ ] кодировать состояние в типе (type-state), делая переходы методами, потребляющими `self`;
- [ ] запечатывать трейт через приватный супертрейт (sealed trait) и понимать, что это даёт;
- [ ] проектировать builder, у которого `build()` компилируется только при заданных обязательных
      полях;
- [ ] объяснять, почему все эти проверки бесплатны в рантайме (маркеры - ZST).

## 1. Состояние в типе: зачем

Обычный подход к состоянию - поле-флаг и проверки в рантайме:

```rust,ignore
struct Door { open: bool }

impl Door {
    fn open(&mut self)  { self.open = true; }
    fn close(&mut self) { self.open = false; }
    fn walk_through(&self) {
        if !self.open { panic!("дверь закрыта"); } // ошибка ловится только в рантайме
        // ...
    }
}
```

`walk_through` на закрытой двери - логическая ошибка, но компилятор её не видит: типы верны,
`panic!` случится лишь при запуске на нужной ветке. Type-state переносит проверку в компилятор:
состояния становятся разными типами, а `walk_through` существует только у типа "открытая дверь".
Тогда вызвать его на закрытой нельзя - такой код не наберётся. Это и есть цель модуля: *сделать
недопустимые состояния непредставимыми* ("make illegal states unrepresentable"). Обзор идиомы:
<https://cliffle.com/blog/rust-typestate/>.

## 2. `PhantomData`

Чтобы навесить на тип параметр-метку, нужен способ "использовать" параметр, ничего не храня. Если
написать `struct Id<T>(u64)`, компилятор отвергнет код: параметр `T` не используется, а правила
требуют, чтобы каждый параметр где-то встречался (иначе непонятны вариантность и drop-поведение).
Решение - `std::marker::PhantomData<T>`: zero-sized маркер, который "считается" использованием `T`:

```rust,ignore
use std::marker::PhantomData;

struct Id<T> {
    value: u64,
    _marker: PhantomData<T>,   // говорит компилятору "Id ведёт себя, как будто хранит T"
}
```

`PhantomData<T>` не занимает памяти (`size_of::<PhantomData<T>>() == 0`) и не создаёт значения `T`;
он лишь сообщает компилятору, как относиться к параметру для проверки типов, вариантности (M09) и
drop-check. Разные варианты несут разный смысл:

```text
PhantomData<T>            - "владею T" (как будто поле T): для drop-check и вариантности по T
PhantomData<&'a T>       - "заимствую T на 'a": привязывает время жизни
PhantomData<*const T>    - использовать T, не притязая на владение (частый выбор для чистых меток)
PhantomData<fn() -> T>   - сделать тип ковариантным по T, не требуя Send/Sync от T
```

Для простых меток-состояний (раздел 4) обычно достаточно `PhantomData<T>` или `PhantomData<fn()
-> T>`. Точная семантика и таблица вариантности: <https://doc.rust-lang.org/std/marker/struct.PhantomData.html>
и <https://doc.rust-lang.org/nomicon/phantom-data.html>.

## 3. Фантомные newtype: типизированные метки

Самое прямое применение - различать значения одного представления, но разного смысла. Пусть в
программе есть id пользователей и id постов; оба - `u64`, и перепутать их легко:

```rust,ignore
struct User;
struct Post;

struct Id<T> {
    value: u64,
    _marker: PhantomData<T>,
}

impl<T> Id<T> {
    fn new(value: u64) -> Self {
        Id { value, _marker: PhantomData }
    }
}

fn load_user(id: Id<User>) { /* ... */ }

let u: Id<User> = Id::new(1);
let p: Id<Post> = Id::new(1);
load_user(u); // ок
load_user(p); // ОШИБКА КОМПИЛЯЦИИ: Id<Post> != Id<User>
```

`User` и `Post` здесь - пустые типы-метки (ZST), значения которых никогда не создаются; они живут
только в параметре `Id<T>`. Представление `Id<User>` и `Id<Post>` в памяти идентично (`u64`), но
для компилятора это разные типы, и подстановка одного вместо другого - ошибка. Та же схема лежит в
основе единиц измерения: `Length<Meters>` и `Length<Feet>` не складываются, пока не написана явная
конверсия. Стоимость приёма в рантайме нулевая - метка это ZST.

## 4. Type-state: состояние как тип

Следующий шаг - параметр-метка обозначает не "владельца", а *состояние жизненного цикла*.
Переход между состояниями делают методом, который *потребляет* `self` (забирает владение) и
возвращает значение с другим параметром:

```rust,ignore
struct Open;
struct Closed;

struct Door<State> {
    _state: PhantomData<State>,
}

impl Door<Closed> {
    fn new() -> Self { Door { _state: PhantomData } }
    fn open(self) -> Door<Open> {        // потребляет Door<Closed>, отдаёт Door<Open>
        Door { _state: PhantomData }
    }
}

impl Door<Open> {
    fn close(self) -> Door<Closed> {
        Door { _state: PhantomData }
    }
    fn walk_through(&self) { /* доступно только у Door<Open> */ }
}

let door = Door::<Closed>::new();
// door.walk_through();     // не компилируется: метода нет у Door<Closed>
let door = door.open();
door.walk_through();        // ок
```

Метод `walk_through` объявлен в `impl Door<Open>`, поэтому у `Door<Closed>` его просто нет - вызвать
невозможно. Поскольку `open`/`close` забирают `self` по значению, старое состояние после перехода
недоступно (оно перемещено) - нельзя случайно продолжить работать с "закрытой" дверью после
открытия. Общие для всех состояний методы кладут в `impl<State> Door<State>`. Так кодируют
протоколы: соединения (disconnected -> connected -> authenticated), парсеры, конечные автоматы -
недопустимый переход становится ошибкой компиляции.

## 5. Sealed-трейты

Часто множество состояний должно быть *закрытым*: мы хотим сказать "State может быть только `Open`
или `Closed`, и никто снаружи не добавит третьего". Или: трейт задаёт внутренний контракт, и чужие
реализации сломали бы инварианты. Обычный публичный трейт этого не гарантирует - любой крейт
реализует его для своего типа. Приём *sealed trait* закрывает трейт через приватный супертрейт:

```rust,ignore
mod sealed {
    pub trait Sealed {}          // виден снаружи (через супертрейт), но...
}

pub trait State: sealed::Sealed {  // публичный трейт требует Sealed
    // общие методы состояний
}

pub struct Open;
pub struct Closed;

impl sealed::Sealed for Open {}    // Sealed реализуем только здесь, в нашем крейте
impl sealed::Sealed for Closed {}
impl State for Open {}
impl State for Closed {}
```

Чтобы реализовать `State`, чужому типу нужно реализовать супертрейт `sealed::Sealed`. Но `Sealed`
лежит в приватном (или `pub`, но недокументированном) модуле, и его конструкции недоступны извне -
написать `impl sealed::Sealed for MyType` в другом крейте нельзя. Значит, и `State` снаружи не
реализовать: множество реализаций закрыто. При этом мы вольны добавлять в `State` методы, не ломая
чужой код (никто снаружи не реализует трейт, некому сломаться). Так делают, например, трейты в
стандартной библиотеке, которые не предполагают внешних реализаций. Разбор:
<https://rust-lang.github.io/api-guidelines/future-proofing.html#sealed-traits-protect-against-downstream-implementations-c-sealed>.

## 6. Type-state builder

Классическая задача - builder с обязательными полями. Наивный builder проверяет "все ли поля
заданы" в рантайме: `build()` возвращает `Result` или паникует. Type-state поднимает проверку в
компилятор: заданность каждого обязательного поля кодируется параметром типа, а `build()`
объявлен только для полностью заполненного состояния.

```rust,ignore
struct Yes;
struct No;

struct RequestBuilder<HasUrl> {
    url: Option<String>,
    method: String,
    _has_url: PhantomData<HasUrl>,
}

impl RequestBuilder<No> {
    fn new() -> Self {
        RequestBuilder { url: None, method: "GET".into(), _has_url: PhantomData }
    }
}

impl<HasUrl> RequestBuilder<HasUrl> {
    fn method(mut self, m: &str) -> Self {   // необязательное поле: состояние не меняет
        self.method = m.into();
        self
    }
    fn url(self, u: &str) -> RequestBuilder<Yes> {   // задать url -> перейти в состояние Yes
        RequestBuilder { url: Some(u.into()), method: self.method, _has_url: PhantomData }
    }
}

impl RequestBuilder<Yes> {          // build() существует только когда url задан
    fn build(self) -> Request {
        Request { url: self.url.unwrap(), method: self.method }
    }
}
```

`build` вызывается лишь у `RequestBuilder<Yes>`; забыть `url` нельзя - у `RequestBuilder<No>`
метода `build` нет, и `.unwrap()` внутри безопасен, потому что попасть в это состояние можно только
через `url`. Необязательные поля (`method`) не трогают параметр состояния. Для нескольких
обязательных полей заводят по параметру-метке на каждое. Приём и его границы (эргономика, рост
числа параметров): <https://doc.rust-lang.org/std/marker/struct.PhantomData.html> и раздел про
builder в <https://rust-unofficial.github.io/patterns/patterns/creational/builder.html>.

## 7. Стоимость и границы

Все метки этого модуля - ZST: `Open`, `Closed`, `Yes`, `User` не имеют полей,
`size_of` для них 0, а `PhantomData` не добавляет к размеру ничего. Значит, `Door<Open>` и
`Door<Closed>` в памяти неотличимы от "голой" двери, а `Id<User>` - от `u64`: вся проверка живёт
на этапе компиляции и исчезает в рантайме. Это делает подход дешёвым, но не бесплатным по другим
осям:

- *мономорфизация*: каждое состояние - отдельный тип, компилятор генерирует код под каждый;
  обычно это несколько мелких `impl`, но при комбинаторном числе состояний код растёт;
- *эргономика*: сигнатуры обрастают параметрами (`RequestBuilder<Yes, No, Yes>`), сообщения об
  ошибках становятся длиннее; API с десятком обязательных полей на type-state неудобен - тогда
  берут рантайм-проверку или генерацию через derive-макрос (M31);
- *хранение*: значение с параметром состояния трудно положить в `Vec` вместе с другими
  состояниями (это разные типы); если состояния нужно смешивать в одной коллекции, type-state не
  подходит - там уместнее enum или trait object (M14).

Правило: type-state хорош для протоколов с небольшим числом состояний и переходов, где важно
исключить неверный порядок операций во время компиляции. Когда состояний много или их надо
хранить вперемешку - возвращаются к рантайм-представлению.

## 8. Типовые грабли

```text
1. Параметр типа без использования не компилируется ("parameter T is never used"). Нужен
   PhantomData<T> (или иное упоминание T). Это не "заглушка ради компилятора" - метка задаёт
   вариантность и drop-check.

2. PhantomData<T> подразумевает владение T (влияет на drop-check и авто-трейты). Для чистой
   метки без притязаний на T берут PhantomData<*const T> или PhantomData<fn() -> T>.

3. Переход состояния должен ПОТРЕБЛЯТЬ self (fn open(self) -> Door<Open>), иначе старое
   состояние останется доступным и инвариант "после open дверь открыта" сломается.

4. Метод, общий для всех состояний, кладут в impl<State> Type<State>; специфичный - в
   impl Type<КонкретноеСостояние>. Перепутать -> метод доступен не в том состоянии.

5. Sealed достигается ПРИВАТНЫМ супертрейтом. Если Sealed объявлен pub и в достижимом модуле -
   печать не работает, чужой крейт реализует трейт.

6. Метки-состояния должны быть ZST (пустые struct). Если у метки есть поля, теряется
   zero-cost и появляются лишние значения, которые надо конструировать.

7. Значения разных состояний - разные типы: их нельзя сложить в один Vec<Door<_>>. Нужна
   разнородная коллекция состояний -> enum/dyn, а не type-state.

8. Число параметров растёт мультипликативно с числом обязательных полей. Для многих полей
   type-state builder становится нечитаемым - это сигнал вернуться к рантайм-проверке.
```

## Упражнения

Решайте по порядку, ярусами. В каждом крейте: условие в `src/lib.rs`, тесты в `tests/tests.rs`
(менять нельзя). Запуск: `cargo test -p ex-32-NN-...`. Часть проверок в этих упражнениях -
*компиляционные*: если API спроектирован верно, тест собирается и проходит; смысл type-state в
том, что *ошибочный* вызов не скомпилировался бы (такие строки в тестах помечены комментарием и
оставлены закомментированными как иллюстрация).

**0x - синтаксис**
- `01_typed_id` - `Id<T>` с `PhantomData`: типизированный идентификатор, `Id<User>` не подставить
  вместо `Id<Post>`.
- `02_length_units` - `Length<U>` с фантомной единицей: сложение только одноимённых единиц,
  конверсия между ними явным методом.

**1x - базовое**
- `03_sealed_trait` - sealed-трейт `Shape` через приватный супертрейт: реализации только внутри
  крейта, общий метод площади.
- `04_door_typestate` - `Door<Open>`/`Door<Closed>`: переходы `open`/`close`, потребляющие `self`;
  `walk_through` только у открытой.

**2x - продвинутое**
- `05_traffic_light` - конечный автомат светофора на type-state: `Red -> Green -> Yellow -> Red`,
  каждый переход возвращает следующий тип.
- `06_builder_typestate` - builder с обязательными полями: `build()` компилируется только когда
  все обязательные поля заданы (параметры-метки `Yes`/`No`).

**3x - хитрое**
- `07_connection` - протокол соединения `Disconnected -> Connected -> Authenticated`: методы
  доступны строго по состоянию (`query` только у `Authenticated`), состояния запечатаны
  sealed-трейтом, данные (адрес, токен) переносятся между переходами.
