# M15 - Продвинутые трейты

> Часть IV "Трейты и дженерики". Предыдущий модуль: [M14 Trait objects](../14-trait-objects/README.md).

## Цель модуля

Инструментарий, на котором стоит стандартная библиотека: **ассоциированные типы**
(почему `Iterator::Item` - не параметр), **`impl Trait`** в возвращаемой позиции
("существует тип"), **blanket impls** (как `ToString` достаётся всем сразу),
**маркер-трейты** и **GAT** - ассоциированные типы с собственными параметрами времени
жизни. После этого модуля сигнатуры std перестанут выглядеть заклинаниями.

После модуля вы умеете:

- [ ] выбирать между ассоциированным типом и параметром трейта - и обосновать выбор;
- [ ] возвращать `-> impl Trait` и объяснить разницу с дженериком и с `Box<dyn>`;
- [ ] писать blanket impl (`impl<T: A> B for T`) и предсказывать конфликты;
- [ ] применять маркер-трейты как статические "печати" на типах;
- [ ] прочитать и написать простой GAT (`type View<'a>`);
- [ ] понимать default-параметры типов (`Add<Rhs = Self>`).

## 1. Ассоциированные типы против параметров

Два способа дать трейту "тип-дырку":

```rust
trait Parser {                       // (а) ассоциированный тип
    type Output;
    fn parse(&self, input: &str) -> Option<Self::Output>;
}

trait ParserG<Output> {              // (б) параметр трейта
    fn parse(&self, input: &str) -> Option<Output>;
}
```

Разница фундаментальна:

- **(б)** позволяет одному типу иметь **много** реализаций: `impl ParserG<i32> for X`
  и `impl ParserG<f64> for X` сосуществуют. При вызове тип приходится уточнять.
- **(а)** допускает **ровно одну** реализацию на тип: `Output` - функция от `Self`.
  Компилятор выводит его сам, вызовы не требуют аннотаций.

Правило выбора: если для типа осмысленна единственная реализация - ассоциированный
тип. `Iterator` - классика: у конкретного итератора ровно один тип элементов, поэтому
`type Item`, а не `Iterator<T>` (иначе `it.next()` требовал бы turbofish всюду).
Параметр оставляют, когда множественность нужна: `From<T>` (один тип конвертируется
из многих), `Add<Rhs>` (складывать можно с разным).

`Add` показывает и **default-параметр**: `trait Add<Rhs = Self>` - обычный случай
пишется коротко (`impl Add for Vec2`), особый - явно (`impl Add<f64> for Vec2`).
А `Output` у `Add` - ассоциированный: у пары (Self, Rhs) результат один.

## 2. `impl Trait` в возвращаемой позиции

```rust
fn make_adder(k: i32) -> impl Fn(i32) -> i32 {
    move |x| x + k        // тип замыкания невыразим - имени у него нет
}
```

Семантика - "**существует** конкретный тип, реализующий трейт; я его знаю, вам не
скажу". Сравните направления выбора:

| | кто выбирает тип |
|---|---|
| `fn f<T: Trait>() -> T` | **вызывающий** ("верни мне любой T, какой попрошу") |
| `fn f() -> impl Trait` | **функция** ("верну какой-то один, мой") |
| `fn f() -> Box<dyn Trait>` | функция, **в рантайме, хоть разный** |

Свойства `-> impl Trait`:

- zero-cost: конкретный тип известен компилятору, никакого стирания и vtable;
- **один** тип на все `return`-пути (ветка `if` не может вернуть `Circle`, а `else` -
  `Square`; для этого - `Box<dyn>`, M14);
- главный потребитель - невыразимые типы: замыкания и цепочки итераторов
  (`-> impl Iterator<Item = u32>` вместо
  `Map<Filter<Range<u32>, {closure}>, {closure}>`).

В аргументах `impl Trait` - просто сахар для дженерика (M12 п.2); не путайте позиции.
С Rust 1.75 `-> impl Trait` разрешён и в методах трейтов (RPITIT).

## 3. Blanket impls

Реализация **сразу для всех** типов с нужным свойством:

```rust
trait Loggable {
    fn log_line(&self) -> String;
}

impl<T: std::fmt::Display> Loggable for T {      // blanket impl
    fn log_line(&self) -> String {
        format!("[LOG] {self}")
    }
}

5.log_line();               // "[LOG] 5"
"hi".log_line();            // "[LOG] hi"
```

Так в std работают `ToString` (для всех `Display`), `Into` (для всех `From`,
M13 п.6), `Borrow`, частично `Iterator` (`impl Iterator for &mut I`). Ограничение -
когерентность: blanket impl "занимает" все типы сразу, второй impl для конкретного
типа даст `E0119: conflicting implementations` (специализация в stable Rust не
доступна). Поэтому blanket-трейты проектируют как "финальные": реализация одна,
кастомизация - через трейт-границу (`Display` в примере).

## 4. Маркер-трейты

Трейт без методов - **утверждение о типе**, проверяемое компилятором:

```rust
trait Approved {}                    // "прошёл ревью безопасности"

struct SafeAlgo;
impl Approved for SafeAlgo {}

fn deploy<T: Approved>(algo: T) { /* ... */ }
// deploy(ExperimentalAlgo) - ошибка компиляции: нет печати
```

std построена на маркерах: `Copy` ("можно дублировать байтами"), `Eq` ("равенство
полное"), `Sized`, `Send`/`Sync` (M22 - "можно между потоками"; их компилятор выводит
сам - auto traits). Маркер - способ протащить **инвариант** через систему типов:
нарушение становится ошибкой компиляции, а не багом в проде.

## 5. GAT: ассоциированные типы с параметрами

Обычный ассоциированный тип фиксирован для типа. **GAT** (generic associated type)
даёт ему собственные параметры - чаще всего время жизни:

```rust
trait Windows {
    type Window<'a> where Self: 'a;              // GAT: тип зависит от 'a

    fn window_at(&self, start: usize) -> Option<Self::Window<'_>>;
}

struct Chunks { data: Vec<i32>, size: usize }

impl Windows for Chunks {
    type Window<'a> = &'a [i32];                 // окно - заём из self

    fn window_at(&self, start: usize) -> Option<&[i32]> {
        self.data.get(start..start + self.size)
    }
}
```

Без GAT тип `Window` не мог бы ссылаться на `self` - некуда привязать время жизни.
Классическая мотивация - **lending iterator**: итератор, чьи элементы занимают из
самого итератора (`type Item<'a>`), что обычному `Iterator` недоступно (его `Item`
не может ссылаться на итератор - потому и существуют отдельно `iter()` и
`into_iter()`, M19). GAT стабильны с Rust 1.65; предложение `where Self: 'a` -
техническое требование: "окно живёт не дольше самого значения".

## 6. Ориентирование в сигнатурах std

Соберём модуль воедино - прочитаем настоящую сигнатуру:

```rust
impl<T: fmt::Display + ?Sized> ToString for T {
    fn to_string(&self) -> String { /* ... */ }
}
```

- `impl<T: ...> ToString for T` - blanket impl (п.3);
- `?Sized` - работает и для DST вроде `str` (M14 п.4);
- `Display` - граница-кастомизация: поведение приходит из `fmt` (п.3).

Одна строка - три концепции модуля. Такому чтению сигнатур и стоило научиться:
дальше курс будет опираться на него постоянно.
