# M12 — Трейты

> Часть IV «Трейты и дженерики». Предыдущий модуль: [M11 Дженерики](../11-generics/README.md).
> Дальше: [M13 Трейты-операторы и конверсии](../13-operator-traits/README.md).

## Цель модуля

Освоить **главный customization point языка**. Трейт задаёт набор методов, которые тип
обязан предоставить; всё поведение типов в Rust — сравнение, хеширование, печать,
уничтожение — выражено трейтами, и между примитивными, библиотечными и вашими типами
нет никакой разницы. Здесь же — чем трейт отличается от интерфейса ООП, как трейты
заменяют наследование и что такое orphan rule.

После модуля вы умеете:

- [ ] объявить трейт, реализовать его для своего и для **чужого** типа;
- [ ] писать default-методы и понимать, когда их переопределять;
- [ ] выражать ограничения тремя способами: `<T: A + B>`, `where`, `impl Trait` в
      аргументе — и знать, чем они различаются;
- [ ] пользоваться ассоциированными функциями (`Self` в возврате) и константами;
- [ ] объявлять супертрейты и вызывать методы одного трейта из реализации другого;
- [ ] разрешать коллизии имён fully qualified syntax `<S as T>::метод`;
- [ ] сформулировать orphan rule и обходить его через newtype;
- [ ] заменять наследование композицией + трейтами.

## 1. Объявление и реализация

```rust
trait Say {
    fn say(&self) -> String;
}

struct Cat;
struct Dog;

impl Say for Cat {
    fn say(&self) -> String { String::from("meow!") }
}
impl Say for Dog {
    fn say(&self) -> String { String::from("woof!") }
}
```

Реализация живёт **отдельно** от определения типа — это не «методы внутри класса».
Один тип может реализовать сколько угодно трейтов, и трейт можно реализовать для уже
существующего типа, не трогая его определение.

### Реализация для чужого типа

```rust
impl Say for i32 {
    fn say(&self) -> String { format!("я число {self}") }
}

92.say();    // работает: никакой vtable внутри i32 нет и не нужно
```

В Java добавить интерфейс к `int` или к чужому `final`-классу нельзя: интерфейс — часть
определения класса, диспетчеризация — через таблицу у объекта. В Rust `impl` — внешняя
таблица соответствия «тип → методы», известная компилятору статически. Это и делает
возможным `impl Display for MyType` и `impl MyTrait for Vec<T>`.

> [!note] Трейт ≠ интерфейс ООП
> Сходство обманчиво. Три отличия: (1) impl для чужих типов; (2) диспетчеризация по
> умолчанию **статическая** — мономорфизация из M11, никакого vtable; (3) методы без
> `self` и с `Self` в возврате (см. §4) — интерфейс, невозможный в ООП.

## 2. Ограничения: три синтаксиса

```rust
fn describe_all<T: Say>(xs: &[T]) -> Vec<String> { /* ... */ }   // (1) inline bound

fn process<T, U>(t: T, u: U) -> String                            // (2) where-клауза
where
    T: Say + Clone,
    U: Say,
{ /* ... */ }

fn greet(x: &impl Say) -> String { x.say() }                      // (3) impl Trait
```

- **(1)** — компактно, пока ограничений мало.
- **(2)** `where` — то же самое, но читаемо при нескольких параметрах и составных
  границах; `+` объединяет требования (`T: Say + Clone` — «и то, и другое»).
- **(3)** `impl Trait` в позиции аргумента — сахар для (1) с анонимным параметром.
  Разница: к анонимному параметру нельзя обратиться turbofish'ем (`greet::<Cat>` не
  напишешь), и два `impl Say`-аргумента — два **независимых** типа.

Правило из M11 действует и здесь: просите минимальные ограничения. `fn len_of<T>(xs:
&[T])` не требует ничего; ограничение появляется, только когда тело реально вызывает
метод трейта.

## 3. Default-методы

Трейт может дать реализацию по умолчанию — тогда типу достаточно реализовать «ядро»:

```rust
trait Greet {
    fn name(&self) -> String;                       // обязательный

    fn greet(&self) -> String {                     // default: выражен через name()
        format!("Привет, {}!", self.name())
    }
}

impl Greet for Cat {
    fn name(&self) -> String { String::from("кот") }
    // greet достаётся бесплатно; при желании можно переопределить
}
```

Так устроена половина стандартной библиотеки: у `Iterator` один обязательный метод
(`next`) и ~70 default-методов (`map`, `filter`, `count`, ...). Проектируя трейт,
выделяйте минимальное ядро, остальное — default'ами.

## 4. Ассоциированные функции и константы

Методы трейта не обязаны принимать `self`:

```rust
trait Zero {
    const ZERO: Self;                 // ассоциированная константа
    fn zero() -> Self;                // ассоц. функция: возвращает Self!
    fn is_zero(&self) -> bool;
}

impl Zero for i32 {
    const ZERO: i32 = 0;
    fn zero() -> i32 { 0 }
    fn is_zero(&self) -> bool { *self == 0 }
}

fn sum<T: Zero + std::ops::Add<Output = T>>(xs: Vec<T>) -> T {
    let mut acc = T::zero();          // вызов через параметр типа
    for x in xs { acc = acc + x; }
    acc
}
```

`fn zero() -> Self` — **return type polymorphism** из M11: вызов диспетчеризуется по
типу *результата*, объекта-получателя нет. Именно так работает `Default::default()`.

## 5. Супертрейты

```rust
trait Animal {
    fn name(&self) -> String;
}

trait Pet: Animal {                   // сахар для where Self: Animal
    fn owner(&self) -> String;

    fn tag(&self) -> String {         // default-метод Pet может звать методы Animal
        format!("{} (хозяин: {})", self.name(), self.owner())
    }
}
```

Тип, реализующий `Pet`, **обязан** реализовать и `Animal` (двумя отдельными impl).
Это не наследование: `Pet` не «расширяет» данные `Animal`, а лишь требует наличия его
интерфейса. Знакомые примеры: `Copy: Clone`, `Eq: PartialEq`, `Ord: Eq + PartialOrd`.

### Замена наследования

Иерархию «базовый класс с данными + наследники» в Rust раскладывают на части:
общие **данные** — композиция (поле со структурой), общее **поведение** — трейт с
default-методами, полиморфизм — дженерики (M11) или trait objects (M14). Глубокие
иерархии превращаются в плоский набор способностей, которые тип набирает impl'ами.

## 6. Orphan rule: чей impl?

Можно ли написать `impl Display for Vec<String>`? **Нет**:

```rust
use std::fmt::Display;
impl Display for Vec<String> { /* ... */ }
// ❌ error[E0117]: only traits defined in the current crate can be implemented
//    for types defined outside of the crate
```

**Orphan rule**: `impl Trait for Type` разрешён, только если трейт **или** тип
определён в вашем крейте. Оба чужие («сирота» — impl без родителя) — запрещено. Иначе
два крейта могли бы дать **разные** реализации `Display` для `Vec<String>`, и
компилятор не смог бы выбрать (когерентность: на всю программу — не больше одной
реализации трейта для типа).

Обход — **newtype**: своя обёртка делает тип «вашим»:

```rust
struct Names(Vec<String>);            // tuple-структ из M04

impl std::fmt::Display for Names {
    fn fmt(&self, f: &mut std::fmt::Formatter<'_>) -> std::fmt::Result {
        write!(f, "{}", self.0.join(", "))
    }
}
```

Цена — доступ через `.0` (или `Deref`, M20). Взамен — нулевая стоимость в рантайме:
`Names` и `Vec<String>` идентичны в памяти.

## 7. Коллизии имён и fully qualified syntax

```rust
trait Pilot  { fn fly(&self) -> String; }
trait Wizard { fn fly(&self) -> String; }
struct Human;
impl Pilot  for Human { fn fly(&self) -> String { "рейс 314".into() } }
impl Wizard for Human { fn fly(&self) -> String { "на метле".into() } }
impl Human  {           fn fly(&self) -> String { "руками машу".into() } }

let h = Human;
h.fly();                  // inherent-метод побеждает: "руками машу"
Pilot::fly(&h);           // "рейс 314"
<Human as Wizard>::fly(&h); // полностью квалифицированно: "на метле"
```

Правила: (1) чтобы вызвать метод трейта, трейт должен быть **в области видимости**
(`use`); (2) при коллизии inherent-метод важнее трейтового; (3) неоднозначность двух
трейтов разрешается `Trait::метод(&x)` или в общем виде `<Тип as Трейт>::метод`.

## 8. `derive` и условные impl

`#[derive(...)]` генерирует impl автоматически: `Clone`, `Copy`, `Debug`, `PartialEq`,
`Eq`, `PartialOrd`, `Ord`, `Hash`, `Default`. Для дженерик-типов derive добавляет
ограничение на **каждый** параметр:

```rust
#[derive(Clone)]
struct Wrapper<T> { value: T }
// сгенерировано: impl<T: Clone> Clone for Wrapper<T> { ... }
```

Обычно это то, что нужно, но иногда ограничение лишнее: `Wrapper<T>`, хранящий
`*const T`, копируем при **любом** `T` — а derive потребует `T: Copy`. Тогда impl
пишут руками без лишней границы. Запомните симптом: «`derive(Clone)` есть, а тип
`Wrapper<НеClone>` всё равно не клонируется».

---

## 9. Тизер к M13

Трейты объявлены и реализованы — теперь посмотрим на трейты, которые **перегружают
операторы и конверсии**: `Add` для `+`, `PartialEq` для `==`, `Index` для `[]`,
`From`/`Into`/`TryFrom` для преобразований и `Display`/`Debug` для печати. Окажется,
что `a + b` — это сахар для `Add::add(a, b)`, и ваш тип может участвовать в любом
операторе на равных с `i32`.
