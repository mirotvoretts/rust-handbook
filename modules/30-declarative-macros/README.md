# M30 - Декларативные макросы

> Часть X "Метапрограммирование". Предыдущий модуль: [M29 FFI](../29-ffi/README.md).

## Цель модуля

Макрос - это код, который пишет код. До сих пор всё, что мы вызывали, было функцией: она
получает *значения* и возвращается в рантайме. Макрос работает раньше и с другим материалом -
он получает *синтаксис* (последовательность токенов исходника) и на этапе разбора программы
разворачивается в новый фрагмент кода, который дальше компилируется как обычный. Отсюда его
возможности, недоступные функции: переменное число аргументов (`println!`, `vec!`), работа до
проверки типов, генерация целых элементов - структур, impl-блоков, функций.

`macro_rules!` - это *декларативные* макросы (их ещё зовут "макросами по образцу", macros by
example). Устроены они как `match`, но не по значениям, а по синтаксису: у макроса есть набор
правил, каждое - пара "образец токенов -> во что развернуть". Компилятор берёт токены вызова,
находит первое подходящее правило и подставляет тело, перенося захваченные куски на их места.

В модуле разбирается всё, из чего складывается такой макрос: захват фрагментов через
*fragment specifiers* (`expr`, `ident`, `ty`, `tt`, ...), повторения `$(...)*`, гигиена
идентификаторов, несколько правил и рекурсия, экспорт макроса и `$crate`. Это фундамент под
следующий модуль (процедурные макросы) и под чтение исходников стандартной библиотеки, где
`macro_rules!` встречается на каждом шагу.

После модуля вы умеете:

- [ ] писать `macro_rules!` с одним и несколькими правилами и понимать порядок их
      сопоставления;
- [ ] захватывать фрагменты нужным specifier (`expr`/`ident`/`ty`/`literal`/`tt`/...) и знать,
      где каждый допустимо подставлять обратно;
- [ ] строить повторения `$(...)* / + / ?` с разделителями и синхронно повторять несколько
      метапеременных;
- [ ] объяснять гигиену: почему локальные имена из макроса не сталкиваются с пользовательскими;
- [ ] писать рекурсивные макросы и TT-munchers с внутренними правилами-аккумуляторами;
- [ ] экспортировать макрос через `#[macro_export]` и ссылаться на элементы своего крейта
      через `$crate`.

## 1. Макрос против функции

Функция получает готовые значения: `fn add(a: i32, b: i32)` требует ровно два `i32`, известных
типов, вычисленных в рантайме. Макрос получает *токены* и разворачивается ещё до типизации,
поэтому умеет то, чего функция не может:

- принимать переменное число аргументов (`vec![1, 2, 3]`, `println!("{} {}", a, b)`);
- принимать не только выражения, но и типы, шаблоны, целые фрагменты синтаксиса;
- порождать элементы - объявлять функции, структуры, impl-блоки.

Плата за это - макрос ничего не знает о типах и значениях: он работает чисто синтаксически.
Ошибка в раскрытии всплывёт уже после подстановки, иногда с невнятным сообщением, а сам макрос
не участвует в выводе типов и не проверяется, пока его не вызовут. Поэтому правило простое:
если задачу решает функция (или дженерик-функция) - берут функцию; макрос достают, когда нужна
переменная арность, работа с синтаксисом или генерация кода. Справка:
<https://doc.rust-lang.org/reference/macros-by-example.html>.

## 2. Синтаксис `macro_rules!`

Определение - это имя и набор правил, каждое вида `(образец) => {раскрытие};`:

```rust
macro_rules! say_hi {
    () => {
        println!("hi");
    };
}

say_hi!(); // вызвать можно с (), [] или {} - выбор скобок на стиль не влияет
```

Левая часть правила (*matcher*) описывает, какие токены принять; правая (*transcriber*) - во
что развернуть. Литеральные токены в matcher должны встретиться в вызове дословно, а
интересные куски захватываются в *метапеременные* вида `$имя:specifier`:

```rust
macro_rules! square {
    ($x:expr) => {
        $x * $x
    };
}

let n = square!(3 + 1); // разворачивается в (3 + 1) * (3 + 1) == 16
```

Захваченный `$x:expr` в раскрытии подставляется как единое выражение (компилятор оборачивает
его в невидимые скобки, поэтому приоритет операций не ломается - `3 + 1` не станет `3 + 1 * 3 +
1`). Скобки вызова взаимозаменяемы, но по соглашению `vec![]` берут квадратные, а
макросы-элементы (`macro_rules!` сам) - фигурные.

## 3. Fragment specifiers

Specifier говорит, *какой синтаксический фрагмент* захватывает метапеременная. Компилятор
разбирает этот кусок по правилам грамматики и дальше обращается с ним как с единым узлом.
Основные:

```text
expr     - выражение:            1 + 2, foo(), if x { a } else { b }
ident    - идентификатор:        x, Foo, my_var
ty       - тип:                  i32, Vec<String>, &'a str
pat      - шаблон (pattern):     Some(x), 0..=9, _
literal  - литерал:              42, "text", 'c', true
tt       - один token tree:      любой токен или группа в скобках - самый гибкий
block    - блок:                 { let x = 1; x }
stmt     - оператор (statement)
path     - путь:                 std::collections::HashMap
lifetime - время жизни:          'a
meta     - содержимое атрибута:  derive(Debug)
vis      - модификатор видимости: pub, pub(crate) или пусто
```

Выбор specifier - это обещание грамматике и одновременно ограничение. `expr` удобен, но
"закрывает" фрагмент: захваченное как `expr` уже нельзя внутри макроса разобрать дальше на
токены - для компилятора это цельное выражение. Когда нужно именно перебирать токены (рекурсия,
munching из раздела 6), берут `tt` - самый примитивный specifier, матчащий один токен или одну
скобочную группу целиком. Полный список и грамматика:
<https://doc.rust-lang.org/reference/macros-by-example.html#metavariables>.

## 4. Повторения

Переменная арность выражается *повторениями*. Конструкция `$( ... )sep rep` повторяет свой
образец: `sep` - необязательный разделитель (обычно `,`), `rep` - сколько раз:

```text
$(...)*   - ноль или больше
$(...)+   - один или больше
$(...)?   - ноль или один (без разделителя)
```

В matcher повторение захватывает список, в transcriber - раскрывается столько раз, сколько
было захвачено. Классический пример - сборка `Vec`:

```rust
macro_rules! my_vec {
    ($($x:expr),* $(,)?) => {{        // список выражений через запятую, опц. хвостовая запятая
        let mut v = Vec::new();
        $( v.push($x); )*             // тело повторяется по каждому $x
        v
    }};
}

let v = my_vec![10, 20, 30];         // let mut v = ...; v.push(10); v.push(20); v.push(30); v
```

`$(,)?` в конце matcher разрешает необязательную хвостовую запятую - без него `my_vec![1, 2,]`
не скомпилировался бы. Повторения можно *синхронизировать*: если в matcher захвачены две
метапеременные под одним `$( ... )*`, в transcriber они разворачиваются попарно. Так строят,
например, `HashMap` из пар `ключ => значение`:

```rust
macro_rules! hashmap {
    ($($k:expr => $v:expr),* $(,)?) => {{
        let mut m = std::collections::HashMap::new();
        $( m.insert($k, $v); )*      // $k и $v идут парами
        m
    }};
}
```

Число повторений `$k` и `$v` всегда совпадает (они под одним `$(...)`), иначе это ошибка
компиляции. Повторения бывают вложенными - внешнее по строкам, внутреннее по элементам строки.

## 5. Гигиена

Гигиена (hygiene) - свойство, из-за которого макросы Rust безопаснее сишного `#define`.
Идентификаторы, *введённые самим макросом* (локальные переменные в его теле), живут в
отдельном "синтаксическом контексте" и не сталкиваются с именами из места вызова, даже если
буквально совпадают:

```rust
macro_rules! swap {
    ($a:expr, $b:expr) => {{
        let tmp = $a;   // это tmp - "макросовый", он невидим снаружи
        $a = $b;
        $b = tmp;
    }};
}

let mut x = 1;
let mut y = 2;
let tmp = 99;          // пользовательский tmp - совсем другой
swap!(x, y);
assert_eq!((x, y), (2, 1));
assert_eq!(tmp, 99);   // не затёрт: макросовый tmp его не видит
```

В сишном `#define` такой макрос молча испортил бы пользовательскую `tmp`. В Rust имя `tmp` из
тела макроса и `tmp` из вызова - разные идентификаторы, компилятор их не путает.

Гигиена распространяется на *локальные переменные и метки*, но не на всё: имена типов, полей
структур, функций и любых элементов гигиеной не защищены (иначе макрос не мог бы объявить
структуру, видимую снаружи). Поэтому, ссылаясь из макроса на элемент, его берут по полному пути
(`std::collections::HashMap`, `$crate::...` из раздела 7), а не полагаются на то, что нужный
`use` окажется в месте вызова. Подробно: <https://veykril.github.io/tlborm/decl-macros/minutiae/hygiene.html>.

## 6. Несколько правил и рекурсия

У макроса может быть несколько правил; компилятор пробует их *сверху вниз* и берёт первое,
чей matcher подходит целиком. Это позволяет обрабатывать базовый и общий случаи отдельно - и
строить рекурсию, где макрос вызывает сам себя, снимая по кусочку с ввода:

```rust
macro_rules! max {
    ($x:expr) => { $x };                       // база: один аргумент
    ($x:expr, $($rest:expr),+ $(,)?) => {{     // голова + непустой хвост
        let head = $x;
        let tail = max!($($rest),+);           // рекурсия по хвосту
        if head >= tail { head } else { tail }
    }};
}

let m = max!(3, 9, 2, 7); // 9
```

Порядок правил важен: более частный образец (`$x:expr` - ровно один) ставят раньше более
общего, иначе общий перехватит всё. Особый приём - *TT muncher*: макрос по одному "откусывает"
токены (`tt`) от ввода, накапливая результат в скрытом аргументе-аккумуляторе, обычно помеченном
служебным токеном вроде `@`, чтобы отличать внутренние правила от публичных:

```rust
macro_rules! reverse {
    ($($x:expr),* $(,)?) => { reverse!(@acc [] $($x),*) };  // публичный вход
    (@acc [$($acc:expr),*]) => { [$($acc),*] };             // база: отдать накопленное
    (@acc [$($acc:expr),*] $head:expr $(, $tail:expr)*) => {
        reverse!(@acc [$head $(, $acc)*] $($tail),*)         // голову - в начало аккумулятора
    };
}
```

Каждый шаг снимает `$head` и кладёт его перед аккумулятором; когда ввод опустел, срабатывает
база и возвращает массив. Munching - основной способ обрабатывать в декларативном макросе
произвольные списки нетривиальной структуры. Разбор приёма:
<https://veykril.github.io/tlborm/decl-macros/patterns/tt-muncher.html>.

## 7. Экспорт макроса и `$crate`

Область видимости `macro_rules!` необычна - *текстовая*: макрос виден в модуле после строки, где
объявлен, и в дочерних модулях. Чтобы сделать его доступным из других крейтов (и из
integration-тестов в `tests/`, которые компилируются как отдельный крейт), над определением
ставят `#[macro_export]` - тогда макрос попадает в корень крейта и импортируется по имени:

```rust
#[macro_export]
macro_rules! my_vec { /* ... */ }

// в другом крейте: use имя_крейта::my_vec;
```

Экспортированный макрос может развернуться в чужом крейте, где нет нужных `use`. Чтобы
ссылки на элементы своего крейта не сломались, внутри используют специальную метапеременную
`$crate` - она раскрывается в путь к крейту, где макрос определён:

```rust
#[macro_export]
macro_rules! make_pi {
    () => { $crate::Circle::new(1.0) }; // не Circle, а $crate::Circle - найдётся везде
}
```

Без `$crate` вызов в другом крейте потребовал бы, чтобы `Circle` был в области видимости в
точке вызова, - хрупко. `$crate` работает только для путей к элементам; локальные имена не
заменяет (для них есть гигиена). Справка:
<https://doc.rust-lang.org/reference/macros-by-example.html#path-based-scope>.

## 8. Типовые грабли

```text
1. Фрагмент, захваченный как expr/ty/pat, дальше нельзя разбирать на токены: для компилятора
   это цельный узел. Нужен перебор токенов -> захватывать как tt.

2. Follow-set: после $x:expr в matcher разрешены лишь => , ; (грамматика запрещает иное,
   чтобы разбор был однозначным). Аналогичные ограничения у stmt, pat, ty.

3. Число повторений синхронных метапеременных должно совпадать: $( $k ... $v )* с разным
   количеством $k и $v -> ошибка компиляции.

4. Забыть $(,)? -> вызов с хвостовой запятой (my_vec![1, 2,]) не компилируется.

5. Порядок правил: общий образец, поставленный раньше частного, перехватит все вызовы.
   Частные (базовые) случаи - выше.

6. expr вставляет невидимые скобки (приоритет сохраняется), но $x повторённый дважды
   ВЫЧИСЛЯЕТ аргумент дважды: square!(f()) вызовет f() два раза. Захватывать в let при
   необходимости.

7. Экспортированный макрос без $crate ломается в чужом крейте, если там нет нужного use.
   Ссылки на элементы - через $crate::.., полными путями.

8. macro_rules! виден только ПОСЛЕ своего объявления (текстовая область). Определение
   ставят выше первого использования.
```

## Упражнения

Решайте по порядку, ярусами. В каждом крейте: условие в `src/lib.rs`, тесты в `tests/tests.rs`
(менять нельзя). Запуск: `cargo test -p ex-30-NN-...`. Все макросы экспортируются
(`#[macro_export]`), тесты импортируют их по имени. Заглушка каждого макроса на любой ввод
выдаёт `compile_error!` - крейт не компилируется, пока макрос не реализован, это ожидаемо
(упражнение считается решённым, когда крейт собрался и тесты зелёные).

**0x - синтаксис**
- `01_my_vec` - `my_vec![...]`: повторение `$(...),*` и хвостовая запятая, сборка `Vec`.
- `02_hashmap` - `hashmap!{ k => v, ... }`: синхронное повторение пар, сборка `HashMap`.

**1x - базовое**
- `03_variadic_max` - `max!(a, b, ...)`: несколько правил и рекурсия по хвосту.
- `04_def_const` - `def_const!(NAME: ty = expr)`: генерация элемента (`const`), specifier
  `ident`/`ty`/`expr`.

**2x - продвинутое**
- `05_swap` - `swap!(a, b)`: обмен значений, демонстрация гигиены (внутренний `tmp`).
- `06_record` - `record!(Name { field: ty, ... })`: генерация `struct` + `impl new`.

**3x - хитрое**
- `07_reverse` - `reverse!(...)`: TT-muncher с аккумулятором, переворот списка в массив.
- `08_json` - `json!(...)`: рекурсивный макрос над мини-DSL (null/число/строка/массив/объект).
