# M23 - Разделяемое состояние

> Часть VIII "Многопоточность". Предыдущий модуль: [M22 Потоки](../22-threads/README.md).

## Цель модуля

M22 показал, как запускать потоки и передавать им данные по владению (`move`) или
заимствованием (`thread::scope`). Но передача владения делит данные "по кускам":
каждый поток получает свою часть и работает с ней независимо. Как только двум потокам
нужно писать в **один и тот же** объект, правило shared-XOR-mutable и трейты
`Send`/`Sync` (M22) блокируют наивный `&mut` из двух мест - это и есть защита от гонки
данных.

Этот модуль - про потокобезопасную внутреннюю изменяемость. В M21 `Cell`/`RefCell`
давали изменяемость через общий `&`, но проверяли инварианты в одном потоке и потому
не `Sync`. Здесь те же идеи переносятся в многопоточность: `Mutex`/`RwLock` - это
`RefCell` с блокирующей синхронизацией, `Atomic*` - это `Cell` для примитивов без
замка, а `Condvar` даёт потокам ждать условия, не крутя процессор впустую.

После модуля вы умеете:

- [ ] делить изменяемые данные между потоками через `Arc<Mutex<T>>` и объяснять роль
      guard-а как RAII-владельца замка;
- [ ] выбирать `RwLock` там, где читателей много, а писателей мало, и понимать его
      инвариант "много `read` XOR один `write`";
- [ ] пользоваться атомарными типами (`AtomicUsize`, `AtomicBool`) и операциями
      `fetch_add`/`compare_exchange`, отличать их от Mutex по стоимости и назначению;
- [ ] на пальцах объяснить, что задаёт `Ordering` (Relaxed/Acquire/Release/SeqCst) и
      зачем нужен цикл CAS;
- [ ] строить синхронизацию "ждать условия" на `Condvar` (`wait`/`notify`), проверяя
      условие в цикле `while` из-за spurious wakeups;
- [ ] объяснить poisoning: почему паника под замком помечает его отравленным и как
      восстановить данные через `into_inner`;
- [ ] распознавать взаимоблокировку (deadlock) и называть дисциплины её предотвращения.

## 1. Проблема: разделяемое изменяемое состояние

`Arc<T>` (M20) даёт нескольким потокам разделяемое **владение** значением, но выдаёт
только `&T` - shared-ссылки. Изменять `T` через `&T` нельзя. Наивная попытка

```rust
use std::sync::Arc;
use std::thread;

let data = Arc::new(0i32);
let d = Arc::clone(&data);
thread::spawn(move || {
    // *d += 1;   // [!] нельзя: Arc даёт &i32, а не &mut i32
});
```

не компилируется. Чтобы менять разделяемое, нужна **внутренняя изменяемость** (M21) -
но потокобезопасная. `RefCell` не подходит: его счётчик заёмов неатомарный, поэтому
`RefCell` не `Sync` и не пройдёт через границу потока. Замена - примитивы синхронизации
из `std::sync` и `std::sync::atomic`. Общий шаблон - `Arc<Замок<T>>`: `Arc` даёт
разделяемое владение, внутренний замок - контролируемую изменяемость.

## 2. `Mutex<T>`: взаимное исключение

`Mutex<T>` (mutual exclusion) хранит `T` и допускает к нему по одному потоку.
`lock()` блокирует текущий поток, пока замок занят, и возвращает
`LockResult<MutexGuard<T>>`. `MutexGuard<T>` - это RAII-владелец: пока он жив, поток
держит замок и через `Deref`/`DerefMut` работает с `T` как с `&mut T`. На `Drop`
guard-а замок автоматически отпускается.

```rust
use std::sync::{Arc, Mutex};
use std::thread;

let counter = Arc::new(Mutex::new(0));
let mut handles = Vec::new();
for _ in 0..10 {
    let c = Arc::clone(&counter);
    handles.push(thread::spawn(move || {
        let mut guard = c.lock().unwrap();   // ждём замок
        *guard += 1;                         // эксклюзивный доступ
    }));                                     // guard дропнут -> замок отпущен
}
for h in handles {
    h.join().unwrap();
}
assert_eq!(*counter.lock().unwrap(), 10);
```

Ключевые свойства:

- `Mutex<T>: Sync` при `T: Send`. Отсюда `Arc<Mutex<T>>` можно раздать в потоки, а
  `Rc<Mutex<T>>` - нет (`Rc` не `Send`).
- Замок нужно держать как можно **короче**: guard, живущий дольше нужного, сериализует
  потоки и убивает параллелизм. Освобождайте явно (`drop(guard)`) или ограничивайте
  областью `{ ... }`, если после вычисления замок больше не нужен.
- Держать guard через точку `.await` или через `join` другого потока, ждущего этот же
  замок, - прямой путь к взаимоблокировке (раздел 8).

Важно: `Mutex<T>` защищает **логическую инвариантность данных**, а не отдельные строки.
Если два поля должны меняться согласованно, они кладутся под один Mutex, а не под два.

## 3. `RwLock<T>`: много читателей XOR один писатель

`Mutex` пускает по одному даже на чтение. Если читателей много, а писателей мало,
`RwLock<T>` эффективнее: он различает два вида доступа.

- `read()` -> `RwLockReadGuard<T>` (как `&T`). Одновременно их может быть **много**.
- `write()` -> `RwLockWriteGuard<T>` (как `&mut T`). Он **эксклюзивен**: пока держат
  write, не пустят ни другого писателя, ни читателей.

Это тот же инвариант shared-XOR-mutable, но проверяемый в рантайме между потоками.

```rust
use std::sync::RwLock;

let config = RwLock::new(vec![1, 2, 3]);

{
    let r1 = config.read().unwrap();   // читатель
    let r2 = config.read().unwrap();   // и ещё читатель - можно одновременно
    assert_eq!(r1.len(), r2.len());
}   // читатели отпущены

{
    let mut w = config.write().unwrap();   // писатель - эксклюзивно
    w.push(4);
}
```

Когда что: `Mutex` проще и часто быстрее при коротких критических секциях; `RwLock`
выигрывает при явном перекосе в сторону чтения. `RwLock` может по-разному вести себя с
голоданием писателей (writer starvation) в зависимости от платформы - не полагайтесь на
конкретный порядок пробуждения.

## 4. Атомарные типы: синхронизация без замка

Для одиночных примитивов (счётчик, флаг) брать Mutex расточительно. `std::sync::atomic`
даёт типы (`AtomicUsize`, `AtomicI64`, `AtomicBool`, `AtomicPtr`, ...), операции над
которыми процессор выполняет **атомарно** - неделимо относительно других потоков, без
блокировки. Все методы принимают `&self` (внутренняя изменяемость), поэтому атомик
делят через `&` или `Arc`.

```rust
use std::sync::atomic::{AtomicUsize, Ordering};
use std::sync::Arc;
use std::thread;

let hits = Arc::new(AtomicUsize::new(0));
let mut handles = Vec::new();
for _ in 0..8 {
    let h = Arc::clone(&hits);
    handles.push(thread::spawn(move || {
        for _ in 0..1000 {
            h.fetch_add(1, Ordering::Relaxed);   // атомарный ++, возвращает старое
        }
    }));
}
for h in handles {
    h.join().unwrap();
}
assert_eq!(hits.load(Ordering::Relaxed), 8000);
```

Почему это не то же, что `*x += 1` под Mutex: `+= 1` - это три шага (load, add, store),
и без синхронизации два потока прочитали бы одно значение и потеряли инкремент. `Atomic`
делает read-modify-write одной неделимой инструкцией.

### 4.1. `Ordering`: барьеры памяти

Компилятор и процессор переупорядочивают обращения к памяти ради скорости. `Ordering` -
аргумент каждой атомарной операции - задаёт, какие переупорядочивания запрещены и,
значит, что один поток гарантированно **увидит** из записей другого.

- `Relaxed` - атомарность самой операции есть, но никаких гарантий про порядок с
  соседними обращениями. Годится для независимых счётчиков, где важен лишь итог.
- `Acquire` (на чтениях) / `Release` (на записях) - образуют пару: всё, что поток
  записал **до** `Release`-store, становится видно потоку, сделавшему `Acquire`-load
  того же атомика. Это механизм передачи данных "через флаг".
- `AcqRel` - для read-modify-write (и Acquire, и Release сразу).
- `SeqCst` - самый строгий: вдобавок единый глобальный порядок всех `SeqCst`-операций.
  Проще рассуждать, но дороже. Если не уверены - берите `SeqCst`, потом ослабляйте.

Для простого счётчика (пример выше) достаточно `Relaxed`: важен итог, а не порядок.
Для "записал данные, потом поднял флаг готовности" нужна пара `Release`/`Acquire`.

### 4.2. `compare_exchange` и цикл CAS

Атомарный **условный** апдейт: "замени значение на новое, только если сейчас там
ожидаемое". Сравнение и запись неделимы.

```rust
use std::sync::atomic::{AtomicUsize, Ordering};

let cell = AtomicUsize::new(5);
// заменить 5 на 6, если там всё ещё 5
let r = cell.compare_exchange(5, 6, Ordering::AcqRel, Ordering::Relaxed);
assert_eq!(r, Ok(5));   // Ok(старое) при успехе; Err(фактическое) при промахе
```

На CAS строятся lock-free-алгоритмы. Типичный шаблон - **цикл CAS**: прочитать текущее,
вычислить новое, попытаться заменить; при неудаче (кто-то опередил) - повторить с
обновлённым значением.

```rust
// Атомарно увеличить, но не выше потолка cap. Mutex не нужен.
fn try_bump(a: &AtomicUsize, cap: usize) -> bool {
    let mut cur = a.load(Ordering::Relaxed);
    loop {
        if cur >= cap {
            return false;
        }
        match a.compare_exchange_weak(cur, cur + 1, Ordering::AcqRel, Ordering::Relaxed) {
            Ok(_) => return true,
            Err(actual) => cur = actual,   // промах: повторяем с актуальным
        }
    }
}
```

`compare_exchange_weak` может ложно промахнуться даже при совпадении (дешевле на
некоторых архитектурах) - поэтому её всегда используют в цикле, где повтор бесплатен.

## 5. `Condvar`: ожидание условия

Атомики и замки решают "не наступай на данные". Но часто поток должен **дождаться**,
пока другой что-то подготовит, не крутя процессор в цикле опроса (busy-wait).
`Condvar` (condition variable) усыпляет поток и будит его по сигналу. Condvar всегда
работает в паре с `Mutex`: под замком проверяют условие и, если оно ложно, атомарно
отпускают замок и засыпают.

```rust
use std::sync::{Arc, Condvar, Mutex};
use std::thread;

// Пара (замок вокруг флага, переменная условия)
let pair = Arc::new((Mutex::new(false), Condvar::new()));

let p = Arc::clone(&pair);
let worker = thread::spawn(move || {
    let (lock, cvar) = &*p;
    let mut ready = lock.lock().unwrap();
    while !*ready {                       // цикл, а не if!
        ready = cvar.wait(ready).unwrap();   // отпустить замок и спать; проснуться с замком
    }
    // здесь ready == true
});

// главный поток готовит данные и сигналит
let (lock, cvar) = &*pair;
{
    let mut ready = lock.lock().unwrap();
    *ready = true;
}
cvar.notify_one();
worker.join().unwrap();
```

Два правила, нарушение которых - классические баги:

- **Условие проверяют в цикле `while`, а не в `if`.** `wait` может вернуться без
  всякого `notify` (spurious wakeup, ложное пробуждение) или потому, что состояние
  успело снова стать невалидным. Цикл перепроверяет предикат после каждого пробуждения.
- **Менять условие нужно под тем же замком, а сигналить - обычно после.**
  `notify_one` будит один ждущий поток, `notify_all` - все. Если пропустить смену флага
  под замком, возможна потеря сигнала (пробуждение до того, как поток заснул).

На `Condvar` строятся барьеры, семафоры, ограниченные очереди producer-consumer.

## 6. Poisoning: паника под замком

Если поток паникует, **держа guard** Mutex или RwLock, замок помечается как отравленный
(poisoned). Смысл: паника могла оставить защищаемые данные в частично обновлённом,
неконсистентном состоянии, и другой поток не должен молча продолжить, как ни в чём не
бывало. Поэтому последующий `lock()` возвращает `Err(PoisonError)`.

```rust
use std::sync::{Arc, Mutex};
use std::thread;

let data = Arc::new(Mutex::new(vec![1, 2, 3]));
let d = Arc::clone(&data);

let _ = thread::spawn(move || {
    let _guard = d.lock().unwrap();
    panic!("сбой под замком");   // замок отравлен
}).join();

// Теперь lock даёт Err. Данные внутри достаются через into_inner:
let recovered = match data.lock() {
    Ok(g) => g,
    Err(poisoned) => poisoned.into_inner(),   // берём данные "как есть"
};
assert_eq!(*recovered, vec![1, 2, 3]);
```

- `PoisonError::into_inner()` отдаёт guard, признавая: "я знаю, что данные могли
  испортиться, беру ответственность". Короткая идиома игнорирования отравления -
  `lock().unwrap_or_else(|e| e.into_inner())`.
- `Atomic*` **не отравляются**: у них нет guard-а и нет понятия "критическая секция под
  паникой".
- Poisoning - защитный механизм, а не то, на что закладываются в штатной логике. Если
  критическая секция коротка и не паникует - вопрос не возникает.

## 7. `Arc<Mutex<T>>` целиком: собираем шаблон

Канонический разделяемый счётчик/состояние выглядит так:

```rust
use std::sync::{Arc, Mutex};
use std::thread;

let shared = Arc::new(Mutex::new(Vec::<i32>::new()));
let mut handles = Vec::new();

for i in 0..4 {
    let s = Arc::clone(&shared);          // клон Arc: +1 к счётчику ссылок
    handles.push(thread::spawn(move || {
        let mut v = s.lock().unwrap();    // берём замок
        v.push(i * i);                    // меняем под замком
    }));                                  // замок отпущен на выходе
}
for h in handles {
    h.join().unwrap();
}

// Все клоны Arc, кроме одного, дропнуты -> можно забрать T обратно без замка:
let mut result = Arc::try_unwrap(shared).unwrap().into_inner().unwrap();
result.sort();
assert_eq!(result, vec![0, 1, 4, 9]);
```

`Arc::try_unwrap` возвращает `Ok(Mutex<T>)`, если это был последний `Arc` (иначе
`Err` с самим `Arc`); `Mutex::into_inner` затем отдаёт `T` без блокировки, раз владелец
единственный. Порядок вставки между потоками не определён - поэтому `sort` перед
сравнением.

## 8. Взаимоблокировка (deadlock)

Синхронизация не отменяет логических ошибок. Самая частая - deadlock: потоки взаимно
ждут замки друг друга и не двигаются.

```rust
// Поток A: lock(x); ... lock(y);
// Поток B: lock(y); ... lock(x);
// A держит x и ждёт y, B держит y и ждёт x - оба стоят навсегда.
```

Дисциплины, устраняющие deadlock:

- **Единый глобальный порядок захвата.** Если все потоки берут замки в одном и том же
  порядке (например, всегда x перед y), цикла ожидания не возникает.
- **Не удерживать один замок, ожидая другой.** По возможности брать по одному.
- **Меньше замков и меньше время удержания.** Не держать guard через долгие операции,
  через `join`, через ожидание Condvar чужого замка.
- Rust ловит гонки данных на этапе компиляции, но deadlock, потерю сигнала Condvar и
  неверный `Ordering` - **не ловит**. Это по-прежнему на совести автора.

## 9. Типовые грабли

```rust
// 1. Rc<Mutex<..>> вместо Arc<Mutex<..>> - Rc не Send, не пройдёт в spawn.
// 2. Guard живёт слишком долго - потоки сериализуются, параллелизм исчезает:
let g = m.lock().unwrap();
long_computation();          // [!] замок держится всё вычисление; посчитайте до lock
*m.lock().unwrap() = result; // а не так: тут будет второй lock при живом g -> deadlock

// 3. Condvar через if вместо while - ложное пробуждение пройдёт мимо проверки:
if !*ready { ready = cvar.wait(ready).unwrap(); }   // [!] нужен while

// 4. Смена условия Condvar без замка - потеря сигнала (поток заснёт после notify).

// 5. Два потока увеличивают счётчик через load + store вместо fetch_add -
//    гонка read-modify-write, часть инкрементов теряется.

// 6. .unwrap() на lock() маскирует poisoning - при отравлении будет паника;
//    осознанно восстанавливайтесь через into_inner, если это допустимо.
```

Решайте по порядку, ярусами. В каждом крейте: условие и `todo!()` в `src/lib.rs`,
тесты в `tests/tests.rs` (менять нельзя). Запуск: `cargo test -p ex-23-NN-...`.

**0x - синтаксис**

- `02_atomic_counter` - тот же счётчик через `AtomicUsize::fetch_add`, без замка.

**1x - базовое**
- `03_shared_vec` - `Arc<Mutex<Vec<T>>>`: параллельно наполнить общий вектор, забрать
  через `try_unwrap`/`into_inner`.
- `04_rwlock_registry` - `RwLock<HashMap<..>>`: реестр "ключ -> счётчик", read/write.

**2x - продвинутое**
- `05_barrier` - барьер на `Mutex` + `Condvar`: N потоков ждут друг друга.
- `06_seat_counter` - счётчик с потолком на цикле `compare_exchange`, без Mutex.

**3x - хитрое**
- `07_poison_recover` - чтение сквозь отравленный Mutex через `into_inner`.
- `08_semaphore` - counting semaphore на `Mutex` + `Condvar` с инвариантом
  "не более N одновременно".
