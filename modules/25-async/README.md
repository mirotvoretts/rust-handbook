# M25 - async/await

> Часть VIII "Многопоточность". Предыдущий модуль: [M24 Каналы и сеть](../24-channels-net/README.md).

## Цель модуля

M22-M24 давали параллелизм на потоках ОС: "поток на соединение", разделяемое состояние
под замком, обмен сообщениями по каналам. У этой модели есть цена. Поток ОС - дорогой
ресурс: собственный стек (обычно мегабайты зарезервированного адресного пространства),
переключение контекста через ядро, планировщик ОС. Сервер, держащий десятки тысяч
медленных соединений, где каждое почти всё время просто ждёт данных из сети, тратит эти
ресурсы впустую - потоки стоят заблокированными в `read`.

Асинхронное программирование решает ровно эту задачу: **много одновременных операций
ввода-вывода на небольшом числе потоков**. Вместо того чтобы блокировать поток в ожидании
сокета, задача **уступает** управление (yield) в точке ожидания, поток берётся за другую
готовую задачу, а к первой возвращается, когда её данные пришли. Это кооперативная
многозадачность в пространстве пользователя, без участия ядра на каждом переключении.

Rust реализует async без сборщика мусора и без обязательного рантайма в языке: `async`/
`.await` - синтаксис, который компилятор разворачивает в конечный автомат (state machine),
реализующий трейт `Future`. Кто и когда крутит эти автоматы - дело библиотеки-executor'а,
а не языка. Отсюда центральная особенность модели: **Future ленив** и ничего не делает,
пока его не начнёт опрашивать executor.

После модуля вы умеете:

- [ ] писать `async fn` и асинхронные блоки, приостанавливать их в точках `.await` и
      объяснять, почему Future ничего не выполняет до первого опроса (лень);
- [ ] читать сигнатуру трейта `Future` (`poll`, `Poll::Ready`/`Poll::Pending`, `Context`,
      `Waker`) и реализовывать `Future` вручную для простого типа;
- [ ] объяснять роль executor'а и `Waker`: как задача засыпает на `Pending` и как её
      будят к повторному опросу;
- [ ] написать простейший блокирующий executor (`block_on`) на примитивах стандартной
      библиотеки (`Waker`, `thread::park`/`unpark`);
- [ ] отличать конкурентность (concurrency) от параллелизма, запускать несколько Future
      одновременно на одном потоке через `join!`/`join_all`;
- [ ] в общих чертах понимать, зачем `poll` берёт `Pin<&mut Self>` и что такое `Unpin`;
- [ ] поднимать асинхронный ввод-вывод на рантайме tokio (`tokio::net`, `tokio::spawn`)
      и понимать, почему в async-коде нельзя блокировать поток и держать `std::Mutex`
      через `.await`.

## 1. Зачем async: блокировка против уступки

Синхронный вызов `stream.read(&mut buf)` **блокирует** поток ОС: поток снимается с
процессора и не получает управления, пока ядро не разбудит его пришедшими данными. Один
поток - одно ожидание за раз. Чтобы ждать тысячу сокетов, нужна тысяча потоков.

Асинхронная операция `stream.read(&mut buf).await` устроена иначе. Если данных ещё нет,
задача не блокирует поток, а **возвращает управление** executor'у со словами "я не готова,
разбуди меня, когда на сокете появятся данные". Поток тут же берётся за другую готовую
задачу. Одна нить исполнения обслуживает много ожиданий, переключаясь между ними в
пространстве пользователя - без системного вызова и без стека на каждую задачу.

```text
поток на соединение (M24):          async (M25):
  поток1 --[ждёт read, спит]           поток1 --[задача A ждёт]--\
  поток2 --[ждёт read, спит]                    [задача B готова]-> исполняет B
  поток3 --[ждёт read, спит]                    [задача C ждёт]  --/
  ...тысячи потоков ОС                  ...тысячи задач на 1-N потоках
```

async выигрывает именно на нагрузке, где преобладает **ожидание ввода-вывода** (I/O-bound).
Для счётной нагрузки (CPU-bound), где потоки реально работают, а не ждут, выигрыша нет -
там нужны потоки M22.

## 2. `async` и `.await`

`async fn` - функция, тело которой не выполняется при вызове. Вызов возвращает **значение,
реализующее трейт `Future`**, - "отложенное вычисление". Само вычисление пойдёт только
когда Future начнут опрашивать.

```rust
async fn double(x: i64) -> i64 {
    x * 2
}

let fut = double(21);   // тело НЕ выполнилось; fut - это Future<Output = i64>
// пока fut никто не опрашивает, ничего не происходит
```

`.await` применяется к Future внутри async-контекста и означает "приостанови меня здесь,
пока этот Future не даст результат, затем продолжи с его значением". Пока внутренний Future
не готов, точка `.await` уступает управление наверх.

```rust
async fn work(a: i64, b: i64) -> i64 {
    let x = double(a).await;   // дождались первого
    let y = double(b).await;   // затем второго
    x + y
}
```

Ключевое свойство - **лень (laziness)**. В отличие от потока, который стартует сразу при
`thread::spawn`, Future не делает ничего, пока его не опросят. Создать Future и не сделать
`.await` (и не отдать executor'у) - значит не выполнить его тело вообще. Это частая
ошибка: "мой async-код не запустился" обычно означает "Future создан, но не дождан".

Асинхронный блок `async { ... }` - выражение того же рода: даёт Future из произвольного
куска кода, аналогично тому как замыкание даёт вызываемое значение из блока.

## 3. Трейт `Future`

За синтаксисом стоит один трейт (упрощённо, как в стандартной библиотеке):

```rust
pub trait Future {
    type Output;
    fn poll(self: Pin<&mut Self>, cx: &mut Context<'_>) -> Poll<Self::Output>;
}

pub enum Poll<T> {
    Ready(T),      // готово, вот результат
    Pending,       // ещё не готово, опроси позже
}
```

`poll` - это один "тик" исполнения Future. Executor вызывает `poll`:

- если работа закончена, `poll` возвращает `Poll::Ready(value)` - результат готов;
- если приходится ждать (сокет пуст, таймер не истёк), `poll` возвращает `Poll::Pending`,
  предварительно **зарегистрировав интерес** к пробуждению через `Waker` из `cx`
  (раздел 4). Executor больше не будет крутить эту задачу вхолостую - он опросит её снова
  только после сигнала `Waker`.

Компилятор превращает каждую `async fn`/`async`-блок в **конечный автомат**: тип, чьи
состояния - это участки между точками `.await`. Локальные переменные, живущие через
`.await`, становятся полями этого автомата. Каждый `poll` продвигает автомат от одной
точки приостановки к следующей, пока не дойдёт до конца и не вернёт `Ready`.

```text
async fn f() {          состояния автомата:
    a();                  Start   -> выполнить a(), дойти до .await
    x().await;            AwaitX  -> опрашивать x, пока Pending
    b();                  AwaitX  -> когда Ready: выполнить b(), дойти до .await
    y().await;            AwaitY  -> опрашивать y, пока Pending
    c();                  AwaitY  -> когда Ready: выполнить c()
}                         Done    -> вернуть Ready(())
```

Обычно этот тип вручную не пишут - его генерирует компилятор. Но чтобы понять модель,
полезно реализовать `Future` руками для простого типа (упражнения 04-05).

## 4. Executor и `Waker`: кто крутит Future

Future сам себя не исполняет. Его крутит **executor** (он же runtime, планировщик задач).
Минимальный executor - функция `block_on(future)`: она опрашивает один Future в цикле,
пока тот не вернёт `Ready`, а между опросами усыпляет поток, чтобы не жечь процессор.

Возникает вопрос: если `poll` вернул `Pending`, когда опрашивать снова? Опрашивать в
плотном цикле - тратить процессор впустую. Ответ - `Waker`. В `Context`, который executor
передаёт в `poll`, лежит `Waker` - ручка "разбуди эту задачу". Future, возвращая `Pending`,
обязан где-то сохранить `Waker` (например, отдать его драйверу ввода-вывода) и вызвать
`wake()` тогда, когда появится смысл опрашивать снова. `wake()` сообщает executor'у "эту
задачу пора опросить"; executor просыпается и снова зовёт `poll`.

```text
executor.poll(task) -> Pending   (task сохранил Waker у источника события)
executor засыпает (thread::park)
... приходят данные из сети ...
источник вызывает waker.wake()   -> executor просыпается (thread::unpark)
executor.poll(task) -> Ready(v)
```

Простейший `Waker` для блокирующего `block_on` не имеет очереди задач: задача одна, будить
= разбудить спящий поток. Это делается через `std::thread`: `park` усыпляет текущий поток,
`unpark` будит. Стандартная библиотека даёт удобный способ построить `Waker` из своего
типа - трейт `std::task::Wake` (реализуется для `Arc<T>`), из которого `Waker::from` создаёт
готовый `Waker`.

```rust
use std::sync::Arc;
use std::task::{Wake, Waker};
use std::thread::{self, Thread};

struct ThreadWaker(Thread);

impl Wake for ThreadWaker {
    fn wake(self: Arc<Self>) {
        self.0.unpark();   // разбудить поток, спящий в block_on
    }
}

let waker: Waker = Waker::from(Arc::new(ThreadWaker(thread::current())));
```

Полноценный executor (tokio, async-std) устроен сложнее: очередь готовых задач, пул потоков,
интеграция с epoll/kqueue/IOCP для сигналов от ОС. Но принцип тот же - `poll` до `Ready`,
`Pending` + `Waker` для сна. Свой `block_on` из примитивов `std` - упражнение 06; там же
пригодится макрос `std::pin::pin!` (см. раздел 6 и
<https://doc.rust-lang.org/std/pin/macro.pin.html>).

## 5. Конкурентность против параллелизма

**Параллелизм** - несколько вычислений физически идут одновременно на разных ядрах (потоки
M22). **Конкурентность** - несколько задач находятся "в процессе" и чередуются, но в каждый
момент, возможно, выполняется одна. async в первую очередь про конкурентность: на одном
потоке можно вести тысячу соединений, переключаясь между ними в точках `.await`.

Последовательный `await` двух Future не даёт им идти одновременно - второй начнётся после
завершения первого:

```rust
let a = fetch(1).await;   // сначала полностью это
let b = fetch(2).await;   // потом это
```

Чтобы вести Future **конкурентно** на одном потоке, их объединяют комбинатором. `join!`
опрашивает все свои Future по очереди в одном `poll`, продвигая каждый, что готов
двигаться, и завершается, когда готовы все; `join_all` делает то же для коллекции Future,
сохраняя порядок результатов:

```rust
// две задачи конкурентно, результат - кортеж:
let (a, b) = futures::join!(fetch(1), fetch(2));

// коллекция задач конкурентно, результат - Vec в исходном порядке:
let results: Vec<_> = futures::future::join_all(vec![fetch(1), fetch(2), fetch(3)]).await;
```

Пока одна из объединённых задач висит на `Pending` (ждёт сети), `join` продвигает
остальные. Это и есть выигрыш: ожидания перекрываются во времени, хотя поток один.
Синтаксис `join!`/`join_all` - из крейта `futures`; см.
<https://docs.rs/futures/latest/futures/macro.join.html> и
<https://docs.rs/futures/latest/futures/future/fn.join_all.html>.

## 6. `Pin` и `Unpin` - коротко

Обратите внимание на приёмник в `poll`: не `&mut self`, а `self: Pin<&mut Self>`. Причина
- в устройстве автомата из раздела 3. Локальные переменные, живущие через `.await`,
становятся полями автомата; среди них могут оказаться **ссылки на другие поля того же
автомата** (например, переменная-буфер и ссылка-срез на него). Такой тип -
*самоссылающийся* (self-referential): его нельзя перемещать в памяти, иначе внутренние
ссылки станут висячими.

`Pin<&mut T>` - обёртка над указателем, дающая гарантию: пока значение опрашивается, оно не
будет перемещено (его адрес зафиксирован, "приколот"). Это позволяет автомату безопасно
содержать ссылки на себя.

`Unpin` - marker-трейт (автоматический, как `Send`/`Sync`): тип, которому перемещение не
вредит даже под `Pin`. Почти все обычные типы `Unpin` (числа, `String`, `Vec`, ваши
структуры без самоссылок). Для `Unpin`-типа `Pin` не накладывает ограничений, и добраться
до `&mut self` можно безопасно через `Pin::get_mut`:

```rust
fn poll(self: Pin<&mut Self>, _cx: &mut Context<'_>) -> Poll<i64> {
    let this = self.get_mut();   // безопасно: Self: Unpin
    // ... работаем с this как с &mut Self ...
    Poll::Ready(0)
}
```

Для нашей цели этого достаточно: реализуемые вручную Future (упражнения 04-05) - `Unpin`,
и `Pin` в них не мешает. Полное объяснение самоссылающихся автоматов и проекций `Pin` -
за рамками модуля; см. главу async book: <https://rust-lang.github.io/async-book/> (раздел
про `Pin`) и документацию <https://doc.rust-lang.org/std/pin/index.html>.

## 7. Рантаймы и асинхронный ввод-вывод (tokio)

Стандартная библиотека даёт трейт `Future`, `Poll`, `Context`, `Waker`, `Pin` - но **не
даёт executor'а** и асинхронного ввода-вывода. Их поставляет рантайм-крейт. Самый
распространённый - **tokio**: пул потоков-executor'ов, планировщик задач и async-версии
сокетов/файлов/таймеров поверх epoll/kqueue/IOCP.

Точка входа - объект `Runtime`. `Runtime::block_on(future)` крутит Future до готовности на
пуле рантайма; внутри async-контекста `tokio::spawn(future)` отдаёт **новую задачу** пулу,
и она исполняется конкурентно с остальными (аналог `thread::spawn`, но для задач, а не
потоков). Атрибут `#[tokio::main]` - просто сахар, оборачивающий `main` в создание
`Runtime` и `block_on`.

```rust
use tokio::io::{AsyncReadExt, AsyncWriteExt};
use tokio::net::TcpListener;

async fn echo_server() -> std::io::Result<()> {
    let listener = TcpListener::bind("127.0.0.1:0").await?;
    loop {
        let (mut socket, _) = listener.accept().await?;      // ждём соединение, не блокируя поток
        tokio::spawn(async move {                            // каждое соединение - отдельная задача
            let mut buf = Vec::new();
            if socket.read_to_end(&mut buf).await.is_ok() {
                let _ = socket.write_all(&buf).await;
            }
        });
    }
}
```

Async-аналоги знакомых по M24 сокетов: `tokio::net::TcpListener`/`TcpStream`, а методы
`read`/`write` приходят из трейтов `AsyncReadExt`/`AsyncWriteExt`. Построчное чтение -
`tokio::io::BufReader` + `AsyncBufReadExt::lines`. Полный обзор - учебник tokio:
<https://tokio.rs/tokio/tutorial>.

Два правила, нарушение которых ломает async-код:

- **Не блокируйте поток executor'а.** `std::thread::sleep`, синхронный `read`, тяжёлый
  счёт в задаче занимают поток пула, и все остальные задачи на нём встают. Для пауз -
  `tokio::time::sleep(...).await`, для тяжёлого счёта - `tokio::task::spawn_blocking`.
- **Не держите `std::sync::Mutex` через `.await`.** Guard (`MutexGuard`) не `Send`, и задача
  с удержанным guard'ом через точку `.await` либо не скомпилируется в `spawn`, либо
  рискует дедлоком. Либо берите значение под замком и отпускайте guard **до** `.await`
  (сузьте область блокировки), либо используйте асинхронный `tokio::sync::Mutex`, чей
  guard можно держать через `.await`. Разница разбирается в упражнении 08.

## 8. Типовые грабли

```rust
// 1. Future создан, но не дождан -> тело не выполнилось:
async fn task() { /* ... */ }
let _f = task();     // [!] ничего не произошло; нужно .await или отдать executor'у

// 2. Последовательный await там, где хотели конкурентность:
let a = slow(1).await;   // [!] b начнётся только после a
let b = slow(2).await;   //     нужно join!(slow(1), slow(2)), чтобы шли вместе

// 3. Блокирующий вызов в async-задаче морозит весь поток executor'а:
async fn bad() { std::thread::sleep(std::time::Duration::from_secs(1)); }  // [!]
//               нужно tokio::time::sleep(..).await

// 4. std::Mutex через .await:
// let g = m.lock().unwrap(); something().await; *g += 1;   // [!] guard живёт через await
//   -> сузить область { let g = ...; *g += 1; }  или tokio::sync::Mutex

// 5. Забыли .await у самого Future-возвращающего вызова -> warning "unused Future",
//    и операция не выполняется. Компилятор предупреждает - не игнорируйте.
```

асинхронный ввод-вывод на рантайме tokio. Сетевые упражнения слушают `127.0.0.1` на
