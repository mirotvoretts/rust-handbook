# M09 - Времена жизни II

> Часть II "Владение". Предыдущий модуль: [M08 Времена жизни I](../08-lifetimes-1/README.md).

## Цель модуля

Углубить понимание времён жизни за рамки базовой книги: **несколько независимых времён жизни**,
**подтипирование и вариантность** (почему `&T` можно "укоротить", а `&mut T` - нет),
**outlives-ограничения** (`'b: 'a`, `T: 'static`), **reborrow** (почему `&mut` можно
переиспользовать, хотя он не `Copy`) и **времена жизни высшего ранга** (`for<'a>`). Это
механика, которую borrow-checker применяет незаметно; знание её снимает большинство "загадочных"
ошибок про lifetimes.

После модуля вы понимаете:

- [ ] когда в сигнатуре нужны **разные** времена жизни `'a`, `'b`, а не одно;
- [ ] что такое ковариантность `&'a T` и почему `&'a mut T` инвариантна по `T`;
- [ ] outlives-ограничения `'b: 'a` и `T: 'static` - когда их требует компилятор;
- [ ] reborrow: неявный `&mut *r` при передаче `&mut` в функцию;
- [ ] HRTB `for<'a>` - функции/замыкания, работающие для **любого** времени жизни.

> [!note] Это уже "за рамками книги"
> Большая часть этого модуля работает **автоматически**, и в повседневном коде её не пишут
> руками. Но понимание - ключ к чтению сложных ошибок borrow-checker'а и к проектированию API
> со ссылками. В C++ аналогов нет вовсе: там нет ни времён жизни, ни их вариантности в системе
> типов.

## 1. Несколько независимых времён жизни

Если результат связан **только с одним** входом, остальным входам ни к чему разделять его время
жизни - им дают **свои** параметры:

```rust
fn keep_first<'a>(first: &'a str, second: &str) -> &'a str {
    first                        // результат живёт как first; second независим
}
```

`second` получает собственное (элидированное) время жизни, никак не связанное с `'a`. Практическое
следствие: `second` может быть **короткоживущим** - результат всё равно валиден, пока жив `first`.
Если бы мы (как в M08 `longest`) написали оба входа как `&'a str`, компилятор потребовал бы,
чтобы **оба** жили как минимум `'a`, - и короткоживущий `second` не прошёл бы. Разделять или нет
времена жизни - это про то, **какие входы обязаны пережить результат**.

Явные несколько времён жизни объявляют списком: `fn f<'a, 'b>(x: &'a str, y: &'b str)`.

---

## 2. Подтипирование и вариантность

Времена жизни образуют отношение **подтипирования**: если `'long` живёт дольше `'short`, то
`'long` - **подтип** `'short` (пишут `'long: 'short`, читают "`'long` outlives `'short`").
Интуиция: где нужна короткоживущая ссылка, долгоживущая всегда подойдёт - её можно безопасно
"укоротить".

**Вариантность** - как это подтипирование переносится на составные типы:

| Тип | По времени жизни `'a` | По типу `T` |
|---|---|---|
| `&'a T` | **ковариантен** (можно укоротить `'a`) | ковариантен по `T` |
| `&'a mut T` | ковариантен по `'a` | **инвариантен** по `T` |

**Ковариантность** `&'a T`: `&'static str` можно передать туда, где ждут `&'a str` - долгую
ссылку укорачиваем до нужной. Это работает автоматически и очень часто.

**Инвариантность `&mut T` по `T`** - тонкий, но важный момент безопасности. Будь `&mut T`
ковариантен по `T`, можно было бы записать через него короткоживущую ссылку в место,
рассчитанное на долгоживущую, и получить висячую ссылку:

```text
Если бы &mut Vec<&'long str> можно было использовать как &mut Vec<&'short str>,
то через него в Vec положили бы &'short str, а потом читали как &'long str -> UB.
```

Поэтому запись (`&mut`) запрещает менять `T` даже на "совместимый" - тип под `&mut` фиксирован.
Знать это наизусть не нужно; важно понимать, **почему** `&mut` "строже" `&`.

## 3. Outlives-ограничения: `'b: 'a`, `T: 'static`

Иногда компилятор не может сам вывести, что одно время жизни переживает другое, и требует
**написать** это:

```rust
fn as_shorter<'a, 'big: 'a>(big: &'big str) -> &'a str {
    big                          // ок: 'big: 'a - big живёт хотя бы 'a
}
```

`'big: 'a` ("`'big` outlives `'a`") - обещание, что `'big` не короче `'a`. Без него компилятор
не разрешит вернуть `&'big` как `&'a`: между **именованными** параметрами он outlives-связи не
додумывает.

Ограничения бывают и на типы:

- `T: 'a` - "все ссылки внутри `T` живут хотя бы `'a`" (тип не содержит болтающихся ссылок короче `'a`).
- `T: 'static` - "`T` не содержит нестатических ссылок": либо владеет данными (`String`, `i32`),
  либо ссылается только на `'static`. Это ограничение встречается у потоков (`thread::spawn`
  требует `'static`, M22) и трейт-объектов.

> [!warning] `T: 'static` - это НЕ "значение живёт вечно"
> Частое заблуждение. `T: 'static` означает лишь, что тип **способен** жить сколько угодно
> (не одолжен на время). `String` - `'static`-тип, хотя конкретная строка живёт недолго.

## 4. Reborrow

`&mut T` - **не** `Copy` (иначе было бы два `&mut`, нарушение shared-XOR-mutable). Тогда почему
это работает?

```rust
fn bump(x: &mut i32) { *x += 1; }

fn bump_twice(n: &mut i32) {
    bump(n);      // n НЕ перемещён...
    bump(n);      // ...и доступен снова
}
```

Это **reborrow**: при передаче `n` в `bump` компилятор автоматически подставляет `&mut *n` -
новый краткосрочный `&mut`, живущий только на время вызова. Исходный `n` на это время как бы
"приостановлен", а после возврата снова активен. Так `&mut` переиспользуется, не будучи `Copy`.
Reborrow происходит **неявно** при передаче `&mut` в функцию или метод; иногда (редко) его
пишут явно: `bump(&mut *n)`.

---

## 5. NLL и двухфазные заимствования (кратко)

В M07 мы видели NLL: заём живёт до последнего использования. Есть связанное расширение -
**двухфазные заимствования** (two-phase borrows), благодаря которому компилируется, например,
`v.push(v.len())`: `&mut v` для `push` сначала "зарезервирован" (не активирован), пока
вычисляется аргумент `v.len()` (общий заём), и активируется только к самому вызову. Без этого
пришлось бы вручную разносить чтение и запись, как мы делали в M07. Это ещё один случай, когда
borrow-checker умнее "лексических" правил.

---

## 6. Времена жизни высшего ранга (HRTB)

Иногда функция должна принять другую функцию/замыкание, работающее **для любого** времени
жизни аргумента-ссылки. Это выражается синтаксисом `for<'a>` - **higher-ranked trait bound**:

```rust
fn apply_to_both<F>(f: F)
where
    F: for<'a> Fn(&'a str) -> usize,   // f обязана работать для ЛЮБОГО 'a
{
    let s1 = String::from("short");
    let s2 = String::from("a bit longer");
    let _ = f(&s1);                     // разные времена жизни...
    let _ = f(&s2);                     // ...одна и та же f
}
```

`for<'a> Fn(&'a str) -> usize` читается: "для всякого `'a`, `F` - это `Fn(&'a str) -> usize`".
Без HRTB нельзя было бы вызвать `f` с двумя ссылками разного времени жизни. Обычные
**fn-указатели** типа `fn(&str) -> usize` уже неявно higher-ranked (работают для любой ЖЖ) -
поэтому их можно передавать без всяких аннотаций; с замыканиями (M18) `for<'a>` иногда нужно
писать явно. В C++ ближайшая (очень отдалённая) аналогия - шаблонный параметр-функтор, но без
каких-либо гарантий времени жизни.
