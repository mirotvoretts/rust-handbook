# M24 - Каналы и сеть

> Часть VIII "Многопоточность". Предыдущий модуль: [M23 Разделяемое состояние](../23-shared-state/README.md).

## Цель модуля

M23 делил между потоками **общее** изменяемое состояние под замком - модель "shared
memory". Есть альтернативная модель координации: потоки не трогают общих данных, а
**обмениваются сообщениями** через каналы. Лозунг, пришедший из языка Go, формулирует
принцип: "не общайтесь, разделяя память; разделяйте память, общаясь" (do not
communicate by sharing memory; instead, share memory by communicating). Владение в Rust
делает эту модель особенно надёжной: значение, отправленное в канал, **перемещается** -
отправитель теряет к нему доступ, гонок за него быть не может в принципе.

Вторая половина модуля - ввод-вывод по сети через TCP. `TcpListener`/`TcpStream` из
стандартной библиотеки дают блокирующие сокеты, а модель "поток на соединение"
естественно ложится на потоки M22 и каналы этого модуля.

После модуля вы умеете:

- [ ] создавать канал `mpsc::channel`, передавать значения по владению через
      `Sender::send`/`Receiver::recv` и объяснять move-семантику передачи;
- [ ] итерировать `Receiver` и понимать, что цикл заканчивается, когда закрыты все
      `Sender`;
- [ ] строить схему "несколько производителей, один потребитель" клонированием
      `Sender`;
- [ ] выбирать `sync_channel` (ограниченный буфер, backpressure) против неограниченного
      `channel` и понимать смысл ёмкости 0 (рандеву);
- [ ] собирать конвейеры (pipeline) и пулы воркеров (worker pool) на каналах;
- [ ] поднимать TCP-сервер (`TcpListener::bind`, `incoming`) и клиента
      (`TcpStream::connect`), читать и писать через сокет, в т.ч. построчно через
      `BufReader`;
- [ ] обрабатывать каждое соединение в отдельном потоке и комбинировать это с
      разделяемым состоянием (M23).

## 1. Каналы `mpsc`: передача владения между потоками

`std::sync::mpsc::channel()` создаёт канал и возвращает пару `(Sender<T>, Receiver<T>)`.
Аббревиатура mpsc - "multiple producer, single consumer": отправителей может быть много,
получатель один. `Sender::send` кладёт значение в очередь, `Receiver::recv` блокирует
поток, пока значение не появится, и забирает его.

```rust
use std::sync::mpsc;
use std::thread;

let (tx, rx) = mpsc::channel();

thread::spawn(move || {
    let data = String::from("сообщение");
    tx.send(data).unwrap();   // data перемещена в канал
    // data здесь уже недоступна: владение ушло
});

let received = rx.recv().unwrap();   // блокируемся, забираем значение
assert_eq!(received, "сообщение");
```

- `send` **перемещает** `T` в канал: отправитель теряет владение. Поэтому канал
  безопасен без всяких замков - двух ссылок на одно значение не возникает.
- `T` должен быть `Send` (значение пересекает границу потока, M22).
- `send` возвращает `Result`: `Err(SendError)`, если получатель уже уничтожен (некому
  принять). `recv` возвращает `Err(RecvError)`, если закрыты все отправители и очередь
  пуста.

## 2. Закрытие канала и итерация по `Receiver`

`Receiver` реализует `IntoIterator`: цикл `for v in rx` выдаёт значения по мере
поступления и **завершается**, когда уничтожены все `Sender` и очередь опустела. Это
основной способ "прочитать всё, что пришлют, и остановиться".

```rust
use std::sync::mpsc;
use std::thread;

let (tx, rx) = mpsc::channel();
thread::spawn(move || {
    for i in 1..=5 {
        tx.send(i).unwrap();
    }
    // tx выходит из области и дропается -> канал закрывается
});

let sum: i32 = rx.into_iter().sum();   // цикл кончится сам после закрытия tx
assert_eq!(sum, 15);
```

Ключевой момент: пока жив **хоть один** `Sender`, `recv`/итератор будут блокироваться в
ожидании. Забытый (не дропнутый) отправитель - частая причина того, что получатель висит
вечно (раздел 8). Отсюда идиома `drop(tx)` перед сбором, когда основной поток сам держит
лишний клон.

## 3. Несколько производителей: клонирование `Sender`

`Sender<T>` можно клонировать - каждый клон пишет в тот же канал. Так несколько потоков
шлют одному получателю. `Receiver` не клонируется (consumer один).

```rust
use std::sync::mpsc;
use std::thread;

let (tx, rx) = mpsc::channel();
let mut handles = Vec::new();
for id in 0..4 {
    let tx = tx.clone();               // отдельный отправитель на поток
    handles.push(thread::spawn(move || {
        tx.send(id * 10).unwrap();
    }));
}
drop(tx);                              // исходный tx больше не нужен - закрываем

let mut got: Vec<i32> = rx.into_iter().collect();
for h in handles { h.join().unwrap(); }
got.sort();
assert_eq!(got, vec![0, 10, 20, 30]);
```

`drop(tx)` обязателен: пока исходный `Sender` жив, канал не закроется и `collect`
заблокируется навсегда, даже когда все потоки-клоны отработали. Порядок сообщений от
разных отправителей не определён.

## 4. `sync_channel`: ограниченный буфер и backpressure

`channel()` не ограничивает очередь: `send` никогда не блокирует, но быстрый
производитель может забить память. `mpsc::sync_channel(cap)` создаёт канал с буфером на
`cap` сообщений; когда буфер полон, `send` **блокируется**, пока получатель не заберёт
элемент. Это backpressure - обратное давление, автоматически подстраивающее производителя
под темп потребителя.

```rust
use std::sync::mpsc;
use std::thread;

let (tx, rx) = mpsc::sync_channel(2);   // в буфере не больше двух
thread::spawn(move || {
    for i in 0..10 {
        tx.send(i).unwrap();            // блокируется, если буфер полон
    }
});
let total: i32 = rx.into_iter().sum();
assert_eq!(total, 45);
```

Особый случай - `sync_channel(0)`: буфера нет вовсе, каждый `send` ждёт, пока
соответствующий `recv` не заберёт значение прямо из рук. Это рандеву (rendezvous):
отправитель и получатель встречаются в одной точке синхронизации.

## 5. Конвейеры и пулы воркеров

Из каналов собираются два типовых узора параллелизма.

**Pipeline** - цепочка стадий, каждая в своём потоке, соединённых каналами: выход одной
стадии - вход следующей. Данные текут по конвейеру, стадии работают одновременно над
разными элементами.

```text
источник --tx1--> [стадия-воркер] --tx2--> сток
```

**Worker pool** - один канал задач, из которого несколько одинаковых воркеров разбирают
работу, и один канал результатов, в который они складывают ответы. Так распределяют
нагрузку по фиксированному числу потоков. Поскольку `Receiver` не клонируется, общий
приёмник задач разделяют через `Arc<Mutex<Receiver<T>>>` (M23): воркер под замком берёт
одну задачу и тут же отпускает замок.

Оба узора разбираются в упражнениях 04 и 05.

## 6. TCP-сеть: `TcpListener` и `TcpStream`

Стандартная библиотека даёт блокирующие TCP-сокеты в `std::net`.

- **Сервер.** `TcpListener::bind(addr)` открывает слушающий сокет. `listener.incoming()`
  - итератор входящих соединений; каждый элемент - `io::Result<TcpStream>`. Приняв
  соединение, сервер обычно порождает поток на его обработку и возвращается слушать
  дальше.
- **Клиент.** `TcpStream::connect(addr)` устанавливает соединение и даёт `TcpStream`.
- **Обмен.** `TcpStream` реализует трейты `Read` и `Write` (M16/стдлиб): `read`,
  `write_all`, `read_to_end`, `read_to_string`. Оборачивание в `BufReader` даёт
  построчное чтение через `lines()`.

```rust
use std::io::{Read, Write};
use std::net::{TcpListener, TcpStream};
use std::thread;

// Эхо-сервер: возвращает клиенту то, что тот прислал.
let listener = TcpListener::bind("127.0.0.1:0").unwrap();   // порт 0 - любой свободный
let addr = listener.local_addr().unwrap();
thread::spawn(move || {
    for stream in listener.incoming() {
        let mut stream = stream.unwrap();
        thread::spawn(move || {
            let mut buf = Vec::new();
            stream.read_to_end(&mut buf).unwrap();   // читаем до закрытия записи клиентом
            stream.write_all(&buf).unwrap();         // пишем обратно
        });
    }
});

// Клиент
let mut client = TcpStream::connect(addr).unwrap();
client.write_all(b"ping").unwrap();
client.shutdown(std::net::Shutdown::Write).unwrap();   // сигнал EOF: мы всё отправили
let mut reply = String::new();
client.read_to_string(&mut reply).unwrap();
assert_eq!(reply, "ping");
```

Тонкости, о которые спотыкаются чаще всего:

- **Адрес `127.0.0.1:0`.** Порт 0 просит ОС выделить любой свободный порт; реальный узнают
  через `local_addr()`. В тестах это избавляет от конфликтов за фиксированный порт.
- **EOF и `shutdown`.** `read_to_end`/`read_to_string` читают, пока противоположная
  сторона не закроет запись. Если клиент не сделает `shutdown(Write)` (или не дропнет
  сокет), сервер будет ждать данные вечно. `shutdown(Write)` закрывает только свою
  запись, оставляя чтение ответа открытым.
- **Частичное чтение.** Один `read` может вернуть меньше байт, чем прислали: TCP - поток,
  а не сообщения. Читайте в цикле или через `read_to_end`/`BufReader::lines`, а не
  единственным `read`.

## 7. Поток на соединение и разделяемое состояние

Модель "поток на соединение" (thread-per-connection) естественно комбинируется с M23:
несколько обработчиков параллельно правят общее состояние под `Arc<Mutex<..>>` или
атомиками.

```rust
use std::sync::{Arc, Mutex};

let total = Arc::new(Mutex::new(0i64));
// в цикле incoming: на каждое соединение
//   let total = Arc::clone(&total);
//   thread::spawn(move || { *total.lock().unwrap() += n; ... });
```

Чтобы и читать запрос, и писать ответ в один сокет из кода, где `Read` и `Write` нужны
раздельно (например, `BufReader` забрал stream по значению), сокет **клонируют** через
`TcpStream::try_clone` - обе половины указывают на одно соединение.

## 8. Типовые грабли

```rust
// 1. Забыли drop/clone-учёт Sender -> получатель висит вечно:
let (tx, rx) = std::sync::mpsc::channel::<i32>();
let tx2 = tx.clone();
// ... разослали через tx2 из потоков, но исходный tx жив в main
for _ in rx { }          // [!] не кончится: tx ещё не дропнут

// 2. Держат Mutex-guard приёмника задач через блокирующий recv в пуле -
//    остальные воркеры стоят; берите задачу под замком и сразу отпускайте.

// 3. Единственный read вместо цикла - прочитали не всё (TCP не сохраняет границы).

// 4. Клиент не сделал shutdown(Write) - сервер с read_to_end ждёт EOF навсегда.

// 5. send после уничтожения получателя -> Err(SendError); не .unwrap() вслепую,
//    если получатель может уйти раньше.

// 6. incoming() блокирует поток на accept; слушающий цикл держите в своём потоке,
//    а не в main, если main должен делать что-то ещё.
```
