# M00 — Инструментарий Rust

> Часть 0 «Инструментарий». Это самый первый модуль — про **инструменты**, а не про язык.
> Дальше: [M01 Значения и поток управления](../01-basics/README.md).

## Цель модуля

Освоить рабочий инструмент Rust-разработчика — `rustup` и `cargo` — и научиться главному
навыку новичка: **читать сообщения компилятора**. Rust известен строгим, но необычайно
подробным и дружелюбным компилятором: он не только говорит, что не так, но и **как починить**.
Здесь же — как устроены тесты (включая doc-тесты), на которых держится весь этот курс.

После модуля вы умеете:

- [ ] понимать роли `rustup` (тулчейн) и `cargo` (сборка/тесты/зависимости);
- [ ] запускать `cargo build`/`run`/`test`/`check`/`clippy`/`fmt`;
- [ ] читать ошибку `rustc`: код `Exxxx`, подчёркнутый фрагмент, `help`/`note`;
- [ ] писать тесты `#[test]`, `assert_eq!`, `#[should_panic]` и doc-тесты;
- [ ] проходить упражнения этого курса (`cargo test -p ...`).

## 1. `rustup` — менеджер тулчейнов

`rustup` устанавливает и переключает **тулчейны** — комплекты «компилятор `rustc` + `cargo` +
стандартная библиотека». Каналы:

| Канал | Что это | Когда |
|---|---|---|
| `stable` | стабильный релиз (раз в 6 недель) | по умолчанию, для всего |
| `beta` | кандидат в следующий stable | тестирование перед релизом |
| `nightly` | ежедневная сборка с экспериментальными фичами | нестабильные возможности (некоторые темы позже) |

Полезное:

```bash
rustup show            # активный тулчейн
rustup update          # обновить
rustup component add clippy rustfmt   # доустановить компоненты
```

В этом курсе тулчейн зафиксирован файлом `rust-toolchain.toml` (канал `stable` + `clippy`,
`rustfmt`) — cargo подхватит его автоматически. Сравните с C++, где «поставить компилятор»,
«переключить версию» и «взять стандартную библиотеку» — три разные, часто ручные задачи;
`rustup` делает это одной командой и на всех платформах одинаково.

## 2. `cargo` — сборка, тесты, зависимости в одном

`cargo` — это система сборки **и** пакетный менеджер (роль `make`+`cmake`+`vcpkg`/`conan` из
мира C++, но встроенная и единая). Ключевые команды:

| Команда | Что делает |
|---|---|
| `cargo new имя` | создать проект (`Cargo.toml` + `src/`) |
| `cargo build` | скомпилировать (debug); `--release` — оптимизированно |
| `cargo run` | собрать и запустить бинарник |
| `cargo check` | проверить типы/заимствования БЕЗ генерации кода (быстро) |
| `cargo test` | собрать и прогнать тесты |
| `cargo clippy` | линтер: ловит неидиоматичный/подозрительный код |
| `cargo fmt` | автоформатирование по общему стилю |
| `cargo doc --open` | сгенерировать и открыть документацию |

Проект описывается манифестом `Cargo.toml` (имя, версия, edition, зависимости). Артефакты
сборки складываются в `target/` (его не коммитят — он в `.gitignore`). Зависимости
подтягиваются с [crates.io](https://crates.io) автоматически по записи в `Cargo.toml` —
никакого ручного скачивания и прописывания путей к заголовкам.

> [!note] `cargo check` — ваш главный друг в цикле правок
> `check` выполняет весь анализ (типы, заимствования), но не тратит время на генерацию машинного
> кода. В цикле «поправил → посмотрел ошибки» он в разы быстрее полной сборки.

## 3. Как устроен этот курс технически

Курс — это **cargo workspace**: каждое упражнение и каждое эталонное решение — отдельный
крейт-библиотека. Внутри упражнения:

```
modules/00-toolchain/exercises/01_hello_cargo/
  Cargo.toml           # имя крейта: ex-00-01-hello-cargo
  src/lib.rs           # УСЛОВИЕ + todo!()  — здесь вы пишете код
  tests/tests.rs       # тесты — их менять НЕЛЬЗЯ (это ТЗ)
```

Рабочий цикл:

```bash
cargo test -p ex-00-01-hello-cargo   # запустить одно упражнение (сначала КРАСНОЕ)
# ... правите src/lib.rs, заменяя todo!() ...
cargo test -p ex-00-01-hello-cargo   # снова — теперь ЗЕЛЁНОЕ
```

Эталон — рядом в `solutions/`. Флаг `-p` (package) выбирает конкретный крейт из workspace.

> [!warning] Упражнения «почини сломанное»
> Часть упражнений этого модуля **намеренно не компилируется** — в них ошибка, которую надо
> прочитать и исправить (а не `todo!()`). Это и есть тренировка чтения ошибок компилятора.
> Такие задания отмечены в условии.

## 4. Чтение ошибок компилятора

Сообщение `rustc` устроено единообразно. Пример:

```
error[E0308]: mismatched types
 --> src/lib.rs:3:5
  |
2 | pub fn add_one(n: i32) -> i32 {
  |                           --- expected `i32` because of return type
3 |     n + 1;
  |     ^^^^^^ expected `i32`, found `()`
  |
help: remove this semicolon to return this value
  |
3 -     n + 1;
3 +     n + 1
```

Как читать:

- **`error[E0308]`** — категория ошибки и её **код**. `rustc --explain E0308` покажет подробное
  объяснение с примерами.
- **`--> файл:строка:столбец`** — точное место.
- **`^^^^`** — подчёркнутый проблемный фрагмент + краткое пояснение («expected `i32`, found `()`»).
- **`help:` / `note:`** — часто **готовое** предложение исправления (иногда даже дифф).

Философия: сообщения писались, чтобы **учить**, а не просто ругаться. Прежде чем гадать —
дочитайте `help`. Частые коды, которые встретятся: `E0308` (несовпадение типов), `E0384`
(присваивание неизменяемой переменной), `E0425` (не найдено имя — обычно опечатка), `E0382`
(использование перемещённого значения — это уже про владение, M06).

## 5. Тесты

Тест — функция с атрибутом `#[test]`, которая **паникует при провале** (обычно через
макросы-проверки):

```rust
#[test]
fn adds() {
    assert_eq!(add_one(4), 5);      // равенство (печатает обе стороны при провале)
    assert!(add_one(0) > 0);        // булево условие
    assert_ne!(add_one(1), 1);      // неравенство
}
```

Ожидаемую панику проверяют атрибутом `#[should_panic]`:

```rust
#[test]
#[should_panic]
fn divides_by_zero() {
    safe_div_100(0);                // тест ПРОЙДЁТ, только если здесь будет паника
}
```

- **Модульные тесты** живут рядом с кодом (в `src/`, часто в `mod tests`), **интеграционные** —
  в каталоге `tests/` (как в этом курсе) и видят крейт «снаружи», как обычный пользователь.
- `cargo test`, запуск подмножества: `cargo test имя_функции`, вывод `println!`: `-- --nocapture`.

В отличие от C++, где тест-фреймворк (GoogleTest, Catch2) — внешняя зависимость с ручной
настройкой, в Rust тестирование **встроено** в язык и cargo.

## 6. Doc-тесты

Примеры кода в документационных комментариях `///` — это **тоже тесты**: `cargo test`
компилирует и выполняет их. Так документация не «протухает»:

```rust
/// Возводит число в квадрат.
///
/// # Примеры
/// ```
/// use ex_00_05_doctest::square;
/// assert_eq!(square(4), 16);
/// ```
pub fn square(n: i32) -> i32 {
    n * n
}
```

Блок ```` ``` ```` внутри `///` собирается как отдельная мини-программа и проверяется. Это
уникальная связка «документация = исполняемый пример»; в C++ (Doxygen) примеры в комментариях
никто автоматически не компилирует.

## 7. `clippy`, `fmt`, `miri`

- **`cargo clippy`** — линтер из сотен правил: подсказывает идиоматичный Rust (например,
  `n % 2 == 0` вместо `if ... { true } else { false }`). Предупреждения не ломают сборку, но к
  ним стоит прислушиваться.
- **`cargo fmt`** — форматтер по единому стилю (аналог `clang-format`, но с одним каноничным
  стилем — споров о скобках нет).
- **`miri`** — интерпретатор, детектирующий неопределённое поведение в `unsafe`-коде
  (пригодится в части IX). Ставится через `rustup component add miri`, запуск `cargo miri test`.
