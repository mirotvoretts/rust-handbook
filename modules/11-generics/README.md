# M11 - Дженерики и мономорфизация

> Часть IV "Трейты и дженерики". Предыдущий модуль: [M10 Модули, пути и крейты](../10-modules/README.md).

## Цель модуля

Научиться писать код, **обобщённый по типам**: функции, структуры, перечисления и
impl-блоки с параметрами типа. Понять, во что дженерики компилируются
(**мономорфизация**), чем это отличается от дженериков Java (стирание типов) и шаблонов
C++ (та же мономорфизация, но другой момент проверки), и почему обобщённая функция
не может делать с `T` ничего, что не разрешено ограничениями.

После модуля вы умеете:

- [ ] писать обобщённые функции `fn foo<T>(x: T)` и понимать, когда тип выводится, а
      когда нужен turbofish `::<>`;
- [ ] объявлять обобщённые структуры и enum'ы (`Pair<T>`, `Either<L, R>`) и узнавать
      в `Option<T>`/`Result<T, E>` обычные дженерики;
- [ ] писать `impl<T> ... for Type<T>` и отдельные impl для конкретного типа
      (`impl Point<f64>`);
- [ ] добавлять минимальные ограничения (`T: PartialOrd`) и объяснять, почему без них
      `x + y` или `x < y` не компилируется;
- [ ] объяснить мономорфизацию: сколько копий функции окажется в бинарнике, причём тут
      inlining и code bloat;
- [ ] сравнить дженерики Rust с шаблонами C++ и дженериками Java.

## 1. Проблема: один алгоритм - много типов

Функция "наибольший элемент среза" для `i32` и для `char` - одинаковый код, разные типы.
В Rust **нет перегрузки функций** (одно имя - одна сигнатура), и копипаста
`largest_i32`/`largest_char` - не выход. Решение - параметр типа:

```rust
fn largest<T: PartialOrd>(xs: &[T]) -> &T {
    let mut best = &xs[0];
    for x in xs {
        if x > best { best = x; }
    }
    best
}

largest(&[1, 5, 3]);           // T = i32 - вывелся сам
largest(&['a', 'z', 'q']);     // T = char
```

`<T>` после имени функции объявляет **параметр типа**. Он ведёт себя как обычный тип
внутри тела и сигнатуры. Конвенция имён: `T`, `U`, `K`, `V`, `E` - одна заглавная буква,
либо осмысленное `CamelCase`-имя.

## 2. Вывод типов и turbofish

Обычно параметр типа выводится из аргументов или из контекста:

```rust
fn identity<T>(x: T) -> T { x }

let a = identity(5);           // T = i32 (из аргумента)
let b: f64 = identity(2.0);    // T = f64 (из аннотации)
```

Когда вывести неоткуда - тип задают **turbofish**-синтаксисом `::<>`:

```rust
let n = "42".parse::<i32>().unwrap();       // parse обобщён по типу результата
let xs = (1..5).collect::<Vec<i32>>();      // collect может собрать во что угодно
```

Почему не `parse<i32>(...)`? Синтаксическая неоднозначность: `a < b > (c)` - это два
сравнения или вызов? `::<` снимает её. Альтернатива turbofish - аннотация слева:
`let n: i32 = "42".parse().unwrap();`.

> [!note] Return type polymorphism
> `parse`/`collect`/`Default::default` обобщены по **возвращаемому** типу - вызов
> "подстраивается" под то, куда кладут результат. В ООП-языках такого нет: там
> диспетчеризация идёт по объекту-получателю, а у результата объекта ещё нет.

## 3. Обобщённые структуры и enum

```rust
struct Point<T> { x: T, y: T }             // оба поля ОДНОГО типа T
struct Pair<A, B> { first: A, second: B }  // два независимых параметра

let p = Point { x: 1, y: 2 };              // Point<i32>
let q = Point { x: 1.0, y: 2.0 };          // Point<f64>
// let r = Point { x: 1, y: 2.0 };         // [!] mismatched types: T не может быть i32 и f64 сразу
```

Перечисления - так же. Вы уже давно пользуетесь двумя главными дженерик-enum'ами:

```rust
enum Option<T>     { Some(T), None }
enum Result<T, E>  { Ok(T), Err(E) }
enum Either<L, R>  { Left(L), Right(R) }   // популярный "или-или" (крейт either)
```

`Point<i32>` и `Point<f64>` - **разные типы** без общего представления: у каждого свой
размер и раскладка. `Vec<Point<i32>>` хранит их инлайн, как обычно.

## 4. Обобщённые impl-блоки

```rust
struct Point<T> { x: T, y: T }

impl<T> Point<T> {                    // impl<T> - "для любого T"
    fn new(x: T, y: T) -> Self { Point { x, y } }
    fn into_pair(self) -> (T, T) { (self.x, self.y) }
    fn swap(self) -> Point<T> { Point { x: self.y, y: self.x } }
}

impl Point<f64> {                     // impl ТОЛЬКО для Point<f64>
    fn distance_from_origin(&self) -> f64 {
        (self.x * self.x + self.y * self.y).sqrt()
    }
}
```

Первое `<T>` (после `impl`) **объявляет** параметр, второе (в `Point<T>`) -
**использует**. Отдельный `impl Point<f64>` даёт методы, существующие только у
конкретной инстанциации: `Point::new(1, 2).distance_from_origin()` не скомпилируется,
`Point::new(1.0, 2.0).distance_from_origin()` - да.

Метод может вводить и **собственные** параметры типа поверх параметров структуры:

```rust
impl<A, B> Pair<A, B> {
    fn map_first<C>(self, f: impl FnOnce(A) -> C) -> Pair<C, B> {
        Pair { first: f(self.first), second: self.second }
    }
}
```

## 5. Ограничения: с "голым" T нельзя почти ничего

```rust
fn add<T>(x: T, y: T) -> T {
    x + y      // [!] error[E0369]: cannot add `T` to `T`
}
```

Внутри обобщённой функции о `T` известно ровно то, что объявлено в **ограничениях**
(bounds). Голый `T` можно только перемещать, брать по ссылке и ронять. Сложение,
сравнение, клонирование, печать - всё это **способности**, которые надо запросить:

```rust
fn add<T: std::ops::Add<Output = T>>(x: T, y: T) -> T { x + y }   // ok
fn max2<T: PartialOrd>(x: T, y: T) -> T { if x > y { x } else { y } }
```

Это фундаментальное отличие от шаблонов C++:

| | Rust дженерики | C++ шаблоны |
|---|---|---|
| компиляция | мономорфизация | мономорфизация |
| проверка типов | в точке **определения** дженерика | в точке **инстанцирования** |
| ошибка "нет операции" | сразу, в самой обобщённой функции | у пользователя, простыня в чужом коде |
| выразительность | меньше (всё через трейты) | больше (duck typing на компиляции) |

В C++ `template<class T> T add(T x, T y) { return x + y; }` компилируется молча и
взрывается только на `add(Foo{}, Foo{})` без `operator+`. Rust требует честной
декларации способностей заранее - за это ошибки локальны и понятны. (C++20 concepts -
шаг в ту же сторону.)

Ограничений может быть несколько (`T: Clone + PartialOrd`); развёрнутый синтаксис
`where` и весь мир трейтов - в M12.

## 6. Мономорфизация: во что это компилируется

Компилятор генерирует **отдельную копию** обобщённой функции для каждого набора
конкретных типов-параметров, который реально используется:

```rust
fn make_default<T: Default>() -> T { T::default() }

let a: i32 = make_default();     // в бинарнике: make_default::<i32>
let b: String = make_default();  // и make_default::<String> - ДВЕ разные функции
```

Следствия:

- **Zero-cost**: вызов статический, никакой vtable, никакой косвенности. Компилятор
  видит конкретную функцию и может её **заинлайнить** - а инлайн открывает дорогу
  оптимизации тела в контексте вызова (`multiply(x, 2)` -> `x * 2` -> сдвиг).
- **Оптимальные структуры данных**: `Vec<i32>` и `Vec<i64>` - разный машинный код и
  разная раскладка, без боксинга.
- **Цена - code bloat**: 20 инстанциаций = 20 копий кода в бинарнике и 20 компиляций.
  Генерируются только реально используемые варианты.

### Сравнение с Java

В Java дженерики - **стирание типов**: существует один `ArrayList` для всех `T`,
элементы - указатели на объекты в куче, разное поведение - через виртуальные вызовы.
Плюсы: один экземпляр кода, быстрая раздельная компиляция. Минусы: косвенность,
боксинг примитивов, нет `Vec<i32>` с инлайн-хранением.

Rust даёт **оба** механизма: мономорфизацию по умолчанию (этот модуль) и стирание
типов по запросу - trait objects `dyn Trait` (M14).

## 7. Обобщённые функции над коллекциями

Типовые сигнатуры, которые вы будете писать постоянно:

```rust
fn first<T>(xs: &[T]) -> Option<&T>;               // заём из среза
fn swap_ends<T>(xs: &mut [T]);                     // мутация на месте (mem::swap)
fn zip_pairs<A, B>(xs: Vec<A>, ys: Vec<B>) -> Vec<(A, B)>;
fn count_matching<T: PartialEq>(xs: &[T], target: &T) -> usize;
```

Обратите внимание: `first` возвращает `Option<&T>` - владение не нужно, достаточно
займа; `swap_ends` не требует **никаких** ограничений - перестановка элементов не
создаёт и не копирует значения. Привычка спрашивать "какое МИНИМАЛЬНОЕ ограничение
нужно этой функции?" - признак зрелого Rust-кода.

## 8. Тизер к M12

`T: PartialOrd` мы использовали как заклинание. Следующий модуль - **трейты**: как
объявить собственный интерфейс, реализовать его для своих и чужих типов, что такое
default-методы, супертрейты и orphan rule. Там же станет ясно, откуда берутся
`PartialOrd`, `Clone` и `Default` и почему трейт - главный customization point языка.

## Упражнения

Решайте по порядку, ярусами. В каждом крейте: условие и `todo!()` в `src/lib.rs`,
тесты в `tests/tests.rs` (менять нельзя). Запуск: `cargo test -p ex-11-NN-...`.

**0x - синтаксис**
- `01_generic_fn` - `identity`, `first`, `last`: обобщённые функции без ограничений.
- `02_generic_struct` - `Pair<T>`: объявление, конструктор, доступ к полям.
- `03_turbofish` - `parse`/`collect` с явным указанием типа.

**1x - базовое**
- `04_generic_methods` - `impl<T>`: `new`, `into_inner`, `swap`, метод с собственным параметром типа.
- `05_two_params` - `Either<L, R>`: обобщённый enum с двумя параметрами и методами.
- `06_bounded_largest` - `largest`/`smallest` по `PartialOrd`; минимальность ограничений.

**2x - продвинутое**
- `07_specialized_impl` - общий `impl<T>` + отдельный `impl Point<f64>` с геометрией.
- `08_generic_swap` - `swap_ends`, `replace_all`: мутация через `mem::swap`/`mem::replace` без лишних ограничений.
- `09_zip_unzip` - `zip_pairs`/`unzip_pairs`: владение, кортежи, два параметра типа.

**3x - хитрое**
- `10_generic_stack` - `Stack<T>` на `Vec<T>`: `push`/`pop`/`peek`/`peek_mut`, обобщённый `map` в `Stack<U>`.
