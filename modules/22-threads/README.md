# M22 - Потоки

> Часть VIII "Многопоточность". Предыдущий модуль: [M21 Внутренняя изменяемость](../21-interior-mutability/README.md).

## Цель модуля

До сих пор программа была однопоточной: один поток исполнения шёл по коду сверху вниз.
Поток (thread) - независимая последовательность исполнения внутри процесса; несколько
потоков делят адресное пространство, но выполняются параллельно (на разных ядрах) или
вперемешку (вытесняющая многозадачность). Rust переносит гарантии владения в
многопоточность: правило shared-XOR-mutable вместе с маркерными трейтами `Send`/`Sync`
не даёт **на этапе компиляции** двум потокам одновременно писать в одни данные (data
race). Это "fearless concurrency" - гонки данных ловит компилятор, а не отладчик.

После модуля вы умеете:

- [ ] запускать поток через `thread::spawn` и дожидаться его через `JoinHandle::join`;
- [ ] объяснить, зачем замыканию потока нужен `move`, и что означает граница `'static`
      на `spawn`;
- [ ] получать результат работы потока из `join` (`thread::Result<T>`);
- [ ] запускать много потоков, собирать хендлы и результаты по порядку;
- [ ] объяснить `Send` и `Sync`: что они означают, кто их не реализует (`Rc`, `RefCell`,
      сырые указатели) и почему;
- [ ] заимствовать стековые данные в потоках через `thread::scope`, не прибегая к
      `'static` и `Arc`;
- [ ] понимать, что паника в потоке изолирована и приходит как `Err` из `join`.

## 1. Запуск потока: `spawn` и `join`

`std::thread::spawn` принимает замыкание и запускает его в новом потоке ОС, возвращая
`JoinHandle<T>`, где `T` - тип значения, которое вернёт замыкание. `join` блокирует
текущий поток, пока запущенный не завершится, и отдаёт его результат:

```rust
use std::thread;

let handle = thread::spawn(|| {
    // тело работает в отдельном потоке
    2 + 2
});

let result = handle.join().unwrap();   // ждём завершения, забираем 4
assert_eq!(result, 4);
```

- Порядок исполнения между потоками не определён: без `join` главный поток может
  завершиться раньше дочернего, и тот не успеет доработать. `join` - точка синхронизации.
- `join` возвращает `thread::Result<T>` (см. раздел 6): `Ok(значение)` при нормальном
  завершении, `Err` - если поток запаниковал.

## 2. `move`-замыкания: передача владения в поток

Замыкание потока по умолчанию захватывало бы переменные по ссылке (M18). Но дочерний
поток может пережить область, где эти переменные объявлены, - тогда ссылки повисли бы.
Компилятор это запрещает и требует `move`: замыкание должно **забрать владение**
захваченными данными.

```rust
use std::thread;

let data = vec![1, 2, 3];
let handle = thread::spawn(move || {
    // data перемещена сюда: поток - её единственный владелец
    data.iter().sum::<i32>()
});
// data здесь уже недоступна: перемещена в поток
assert_eq!(handle.join().unwrap(), 6);
```

Без `move` был бы `&data`, живущий, возможно, дольше самой `data`, - `spawn` такое не
пропустит. С `move` данные принадлежат потоку, и вопрос времени жизни снимается.

## 3. Граница `'static` и почему она есть

Сигнатура `spawn` требует, чтобы замыкание было `'static`:

```rust
pub fn spawn<F, T>(f: F) -> JoinHandle<T>
where
    F: FnOnce() -> T + Send + 'static,
    T: Send + 'static,
```

`'static` означает "не содержит заимствованных ссылок с ограниченным временем жизни" -
замыкание либо владеет всеми данными (через `move`), либо ссылается лишь на `'static`.
Причина: `spawn` не знает, когда поток закончится, поэтому не может гарантировать, что
любые одолженные данные проживут достаточно долго. `Send` рядом требует, что и замыкание,
и результат безопасно **переместить** в другой поток (раздел 4).

Чтобы поделить с потоком данные, которыми нельзя пожертвовать по владению, их либо
клонируют и `move`-ают копию, либо оборачивают в `Arc` (разделяемое владение, M20/M23),
либо - если данные на стеке и переживут потоки - используют `thread::scope` (раздел 5).

## 4. `Send` и `Sync`: маркеры потокобезопасности

Два авто-трейта (компилятор выводит их сам) кодируют, что можно делать с типом между
потоками:

- `Send` - значение типа безопасно **переместить** в другой поток. Почти всё `Send`:
  `i32`, `String`, `Vec<T>` (если `T: Send`).
- `Sync` - на значение безопасно **ссылаться** (`&T`) из нескольких потоков сразу.
  `T: Sync` тогда и только тогда, когда `&T: Send`.

Оба выводятся автоматически: тип `Send`/`Sync`, если из таких же его поля. Важные
исключения - и почему:

- `Rc<T>` - **не** `Send` и не `Sync`: счётчик ссылок неатомарный, два потока
  инкрементировали бы его наперегонки и потеряли бы обновление -> двойное освобождение
  или утечка. Межпоточный аналог - `Arc<T>` (атомарный счётчик).
- `RefCell<T>` - `Send` (если `T: Send`), но **не** `Sync`: его счётчик заёмов тоже
  неатомарный, из двух потоков `borrow_mut` сломал бы проверку. Межпоточные аналоги -
  `Mutex`/`RwLock` (M23).
- Сырые указатели `*const T`/`*mut T` - ни то, ни другое: компилятор не знает их
  инвариантов.

Смысл: тип-система гарантирует, что не-`Send` значение (например `Rc`) физически нельзя
передать в `thread::spawn`, - гонку данных ловит компилятор.

## 5. Scoped threads: заимствование без `'static`

Часто хочется, чтобы несколько потоков лишь **прочитали** (или поделили по кусочкам)
данные на стеке вызывающего, не забирая их во владение и не оборачивая в `Arc`.
`thread::scope` создаёт область, из которой **гарантированно** все порождённые потоки
завершатся (join происходит на выходе из области). Раз так, компилятор разрешает этим
потокам заимствовать стековые данные - они точно переживут потоки:

```rust
use std::thread;

let data = vec![1, 2, 3, 4];
let mid = data.len() / 2;
let (left, right) = data.split_at(mid);

let (sl, sr) = thread::scope(|s| {
    let hl = s.spawn(|| left.iter().sum::<i32>());   // заимствует left - без move!
    let hr = s.spawn(|| right.iter().sum::<i32>());
    (hl.join().unwrap(), hr.join().unwrap())
});   // на выходе из scope все потоки уже соединены

assert_eq!(sl + sr, 10);
// data всё ещё принадлежит нам: её только одалживали
```

- `s.spawn` внутри `scope` не требует `'static`: замыкание может держать `&data`.
- Все потоки области соединяются при выходе из `scope` (явный `join` не обязателен, но
  нужен, если хотите получить возвращаемые значения).
- Дисциплина shared-XOR-mutable сохраняется: одновременно можно раздать много `&`
  (чтение) либо непересекающиеся `&mut` (например через `split_at_mut`), но не общий
  `&mut` в два потока.

## 6. Паника в потоке изолирована

Паника раскручивает стек только своего потока и не роняет остальные (в т.ч. главный).
`join` сообщает о ней через `Err`:

```rust
use std::thread;

let h = thread::spawn(|| panic!("сбой в потоке"));
let outcome = h.join();     // главный поток жив
assert!(outcome.is_err());  // Err(Box<dyn Any + Send>) - причина паники
```

- `thread::Result<T>` = `Result<T, Box<dyn Any + Send + 'static>>`. Полезную нагрузку
  паники (обычно `&str`/`String`) при желании достают через `downcast_ref`.
- Изоляция позволяет запустить пачку задач и, соединяя хендлы, отделить успешные от
  упавших, не обрушив программу.

## 7. Типовые грабли

```rust
// 1. Без move - ссылка переживёт владельца: не компилируется
let v = vec![1, 2, 3];
thread::spawn(|| v.len());   // [!] замыкание одалживает v без 'static -> нужен move

// 2. Забыли join - главный поток вышел, дочерний не доработал
thread::spawn(|| long_task());   // результат может не наступить: хендл потерян

// 3. Rc через границу потока запрещён
let rc = std::rc::Rc::new(5);
thread::spawn(move || *rc);   // [!] Rc: !Send -> используй Arc

// 4. join одалживаемого потока внутри scope не обязателен для завершения,
//    но обязателен, если нужно вернуть значение
thread::scope(|s| { s.spawn(|| do_work()); });   // ок: соединится на выходе

// 5. Общий &mut в два потока не пройдёт даже в scope
//    раздавайте непересекающиеся куски через split_at_mut / chunks_mut
```
