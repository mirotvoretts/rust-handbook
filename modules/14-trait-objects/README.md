# M14 — Trait objects и динамическая диспетчеризация

> Часть IV «Трейты и дженерики». Предыдущий модуль: [M13 Трейты-операторы](../13-operator-traits/README.md).
> Дальше: [M15 Продвинутые трейты](../15-advanced-traits/README.md).

## Цель модуля

M11–M13 работали со статическим полиморфизмом: мономорфизация, все типы известны на
компиляции. Этот модуль — про второй механизм: **`dyn Trait`**, стирание типов по
запросу. Гетерогенные коллекции, плагины, колбэки — всё, где набор типов неизвестен
заранее. Разберём устройство (толстые указатели, vtable), правила **dyn
compatibility** (какой трейт может стать объектом) и `dyn Any` — управляемый
downcast.

После модуля вы умеете:

- [ ] складывать разнотипные значения в `Vec<Box<dyn Trait>>` и вызывать методы;
- [ ] нарисовать толстый указатель и vtable; сказать, чему равен
      `size_of::<&dyn Trait>()`;
- [ ] выбирать между `<T: Trait>` и `&dyn Trait` и объяснить цену каждого;
- [ ] объяснить `Sized`/`?Sized` и почему `dyn Trait` и `[T]` — DST;
- [ ] проверить трейт на dyn compatibility и «спрятать» несовместимый метод за
      `where Self: Sized`;
- [ ] хранить замыкания в `Box<dyn Fn...>`;
- [ ] делать downcast через `dyn Any`.

## 1. Проблема: трейт — не тип

```rust
trait Shape { fn area(&self) -> f64; }
struct Circle { r: f64 }
struct Square { a: f64 }
```

`Vec<Shape>` написать нельзя: у `Circle` и `Square` разный размер, они не помещаются
в один слот вектора, и компилятор не знает, чей `area` вызывать. Дженерик
`Vec<T: Shape>` не спасает: это вектор, где **все** элементы одного типа `T`.
Нужен один тип, представляющий «любой Shape», — **trait object**:

```rust
let shapes: Vec<Box<dyn Shape>> = vec![
    Box::new(Circle { r: 1.0 }),
    Box::new(Square { a: 2.0 }),
];
let total: f64 = shapes.iter().map(|s| s.area()).sum();
```

---

## 2. Устройство: толстый указатель + vtable

`dyn Shape` — это **пара указателей** (fat pointer): на данные и на **vtable** —
таблицу с указателями на методы конкретного типа (плюс size/align/drop):

```
Rust (fat pointer):                       C++/Java (thin pointer):
┌───────┬─────────┐                       ┌────────────┐
│ data ●│ vtable ●│──▶ [Circle::area,...] │ vtable* ───┼──▶ [методы]
└───┼───┴─────────┘                       │ поля...    │
    ▼                                     └────────────┘
 Circle { r }   ← данные БЕЗ vtable       vtable живёт ВНУТРИ объекта
```

Ключевое отличие от C++/Java: у Rust данные **не знают о своём типе** — vtable-указатель
лежит рядом с указателем на данные, а не внутри объекта. Следствия:

- `Circle` остаётся простой структурой без скрытых полей; в `Vec<Circle>` — никаких
  vtable, zero-cost;
- один и тот же объект можно видеть как `&dyn Shape`, `&dyn Debug`, `&Circle` —
  vtable подставляется в момент приведения;
- `dyn Trait` работает и для чужих типов (`impl Shape for i32` → `&5 as &dyn Shape`).

`dyn Trait` сочетается с любым указателем, и размер всегда два машинных слова:

```rust
use std::mem::size_of;
assert_eq!(size_of::<&dyn Shape>(),      2 * size_of::<usize>());
assert_eq!(size_of::<Box<dyn Shape>>(),  2 * size_of::<usize>());
assert_eq!(size_of::<&Circle>(),             size_of::<usize>());  // обычный тонкий
```

## 3. Статический против динамического: выбор

| | `<T: Trait>` / `impl Trait` (M11) | `&dyn Trait` / `Box<dyn Trait>` |
|---|---|---|
| диспетчеризация | статическая (мономорфизация) | динамическая (vtable) |
| скорость вызова | прямой вызов, возможен inline | косвенный вызов, inline невозможен |
| размер кода | копия функции на каждый тип | одна копия |
| гетерогенные коллекции | нет | да |
| набор типов | известен на компиляции | может пополняться в рантайме (плагины) |
| где живёт | где угодно | за указателем (`&`, `Box`, `Rc`, ...) |

Практика: по умолчанию — дженерики; `dyn` — когда нужна именно гетерогенность
(коллекция разного, колбэки, плагины) или когда критичен размер кода. Цена `dyn` —
косвенность и потерянный inline; для методов, вызываемых миллионы раз в цикле, это
измеримо.

## 4. DST и `Sized`

`dyn Shape` (как и срез `[T]`, и `str`) — **динамически-размерный тип** (DST): размер
значения не известен компилятору. DST существуют только за указателем — отсюда
`&dyn Shape`, `Box<dyn Shape>`, но не голый `let x: dyn Shape`.

Каждый параметр типа неявно получает границу `Sized`; снять её можно `?Sized`:

```rust
fn generic<T>(x: T)              // на самом деле T: Sized
fn by_ref<T: ?Sized>(x: &T)      // принимает и dyn Trait, и str, и [u8]
```

Так `size_of_val(&*boxed_dyn)` в std работает: сигнатура — `fn size_of_val<T:
?Sized>(val: &T) -> usize`.

## 5. Dyn compatibility (бывш. object safety)

Не всякий трейт может стать `dyn Trait`. Метод несовместим с vtable, если:

- принимает или возвращает `Self` **по значению** — в vtable нельзя записать «верну
  нечто неизвестного размера» (`Clone::clone -> Self`: поэтому `Box<dyn Clone>` не бывает);
- это ассоциированная функция **без self** (`Default::default() -> Self`: кого звать
  без объекта?);
- он **обобщённый** (`fn hash<H: Hasher>(&self, ...)`: в vtable пришлось бы класть
  бесконечно много мономорфизаций).

Несовместимый метод можно **спрятать** за `where Self: Sized` — тогда трейт остаётся
dyn-совместимым, но на trait object этот метод недоступен:

```rust
trait Storage {
    fn read(&self, key: &str) -> Option<String>;            // dyn-ok

    fn copy(&self) -> Self where Self: Sized;               // спрятан от dyn
}

fn use_storage(s: &dyn Storage) {
    s.read("k");
    // s.copy();      // ❌ недоступен через dyn — и это цена совместимости
}
```

Именно так устроен `Iterator`: `next` — dyn-совместим, а `map`/`filter`/`collect`
помечены `where Self: Sized`. Поэтому `Box<dyn Iterator<Item = u32>>` существует.

> [!note] Терминология
> С 2024 года официальное название — **dyn compatibility** (dyn-совместимость); в
> старых текстах и сообщениях компилятора встречается «object safety» — это одно и то же.

## 6. Замыкания за `dyn`: колбэки

Тип каждого замыкания уникален и невыразим — а хранить их в структуре хочется.
`Box<dyn Fn...>` — аналог `std::function` из C++:

```rust
type Callback = Box<dyn Fn(u32) -> u32>;

fn adder(x: u32) -> Callback {
    Box::new(move |y| x + y)          // замыкания — полноценно в M18
}

let callbacks: Vec<Callback> = vec![adder(1), adder(10)];
let result: u32 = callbacks.iter().fold(5, |acc, f| f(acc));   // 5+1+10
```

## 7. `dyn Any`: управляемый downcast

`Any` — трейт из std, реализованный для всех `'static`-типов; позволяет спросить у
стёртого типа, «кто он», и вернуть конкретный тип обратно:

```rust
use std::any::Any;

fn describe(x: &dyn Any) -> String {
    if let Some(n) = x.downcast_ref::<i32>() {
        format!("i32: {n}")
    } else if let Some(s) = x.downcast_ref::<String>() {
        format!("String: {s}")
    } else {
        String::from("что-то другое")
    }
}
```

Это RTTI в духе `dynamic_cast` из C++, но: работает только через явный `dyn Any`
(обычные типы не тащат RTTI), сравнивает `TypeId` (u128-хеш типа), и это **последнее
средство** — обычно вместо downcast стоит добавить метод в трейт. Легитимные
применения: `Box<dyn Any>` в качестве «сумки с чем угодно» (например, payload паники
`std::panic::catch_unwind`), гетерогенные контексты плагинов.

## 8. Тизер к M15

Мы дважды упёрлись в ограничения: «метод возвращает `Self` — не dyn-совместим»,
«тип итератора невыразим». Следующий модуль — продвинутые трейты: **ассоциированные
типы** (чем `Iterator::Item` лучше параметра), **GAT**, **`impl Trait`** в возврате
(«существует тип» без стирания), blanket impls и маркер-трейты. Это инструментарий,
на котором стоит вся стандартная библиотека.
