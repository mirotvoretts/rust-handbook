# M26 - unsafe

> Часть IX "Небезопасность, память, FFI". Предыдущий модуль: [M25 async/await](../25-async/README.md).

## Цель модуля

Весь предыдущий курс был про *safe* Rust: компилятор доказывал отсутствие висячих
ссылок, гонок и обращений за границы, а код, нарушающий эти правила, просто не собирался.
Но borrow checker консервативен - он отвергает и часть *корректных* программ, которые не
умеет доказать. И есть операции, которые он в принципе не может проверить: разыменование
указателя, пришедшего от C, чтение памяти, инициализированной вручную, соблюдение
инварианта, известного программисту, но не выраженного в типах.

Ключевое слово `unsafe` - это способ сказать компилятору: "здесь я беру доказательство
корректности на себя". Оно не выключает borrow checker и не превращает Rust в C. Оно
разблокирует ровно пять дополнительных операций (раздел 1), правильность которых теперь
гарантирует не компилятор, а программист. Нарушение этих гарантий - неопределённое
поведение (undefined behavior, UB): компилятор вправе сгенерировать любой код, и
"работает на моей машине" ничего не значит.

Практическая ценность unsafe - в построении *безопасных абстракций*: внутри маленького
проверенного вручную ядра на unsafe (так устроены `Vec`, `Rc`, `Mutex`, каналы M24)
скрывается небезопасность, а наружу торчит безопасный API, которым нельзя вызвать UB. Это
и есть главная дисциплина модуля: unsafe локализуется, документируется контрактом и
оборачивается так, чтобы внешний код оставался безопасным.

После модуля вы умеете:

- [ ] перечислять пять операций, которые разблокирует `unsafe`, и объяснять, что он не
      отменяет проверки заимствования для обычных ссылок;
- [ ] создавать сырые указатели `*const T`/`*mut T` из ссылок, разыменовывать их в
      `unsafe`-блоке и объяснять, чем указатель отличается от ссылки (может быть null,
      dangling, не несёт lifetime и гарантий алиасинга);
- [ ] пользоваться арифметикой указателей (`add`/`offset`) в пределах одной аллокации;
- [ ] писать `unsafe fn` с контрактом безопасности (`# Safety`) и оборачивать unsafe в
      безопасный API (soundness);
- [ ] называть основные виды UB и знать про Miri как инструмент их поиска;
- [ ] работать с неинициализированной памятью через `MaybeUninit` (чтение uninit - UB);
- [ ] контролировать вызов деструкторов через `ManuallyDrop`, `ptr::read`/`write`/
      `drop_in_place`, не допуская double-free и утечек.

## 1. Что разблокирует `unsafe` (и что нет)

`unsafe` бывает в двух ролях: `unsafe { ... }`-блок ("я выполняю здесь небезопасные
операции и отвечаю за их корректность") и `unsafe fn` ("вызов этой функции требует
соблюдения контракта, отвечает вызывающий"). Внутри `unsafe`-блока становятся доступны
ровно пять операций (superpowers):

1. разыменование сырого указателя (`*const T`/`*mut T`);
2. вызов `unsafe fn` (включая функции из FFI, M29);
3. доступ к полю `union` и к изменяемой `static mut`;
4. реализация `unsafe`-трейта (например, ручной `Send`/`Sync`, M22);
5. чтение изменяемой статической переменной.

Чего `unsafe` **не** делает:

- не выключает borrow checker для обычных ссылок `&`/`&mut` - они по-прежнему проверяются;
- не отключает проверки типов;
- не делает произвольные приведения безопасными.

То есть unsafe - не "режим C", а узкая дверца к пяти операциям. Всё остальное в
unsafe-блоке проверяется как обычно.

```rust
let x = 42;
let p: *const i32 = &x;        // создать указатель можно и в safe-коде
// let y = *p;                 // а разыменовать - нельзя: нужна дверца
let y = unsafe { *p };         // внутри unsafe - можно; за корректность отвечаю я
assert_eq!(y, 42);
```

## 2. Сырые указатели `*const T` и `*mut T`

Сырой указатель - это адрес без гарантий, которые несёт ссылка. Ссылка `&T`/`&mut T`
всегда валидна, выровнена, указывает на живое значение и подчиняется правилу
shared-XOR-mutable. Указатель `*const T`/`*mut T` не гарантирует **ничего**: он может быть
null, невыровненным, висячим (dangling), их может быть сколько угодно на одну ячейку, и он
не несёт lifetime - компилятор не следит, жив ли адресат.

Создать указатель безопасно (это просто число-адрес); небезопасно его *разыменовать*.

```rust
let mut v = 10;

let p: *const i32 = &v;         // из &T   -> *const T
let q: *mut i32 = &mut v;       // из &mut T -> *mut T

unsafe {
    println!("{}", *p);         // чтение через *const
    *q = 20;                    // запись через *mut
}
assert_eq!(v, 20);
```

Разыменовывая указатель, программист обещает, что тот в этот момент валиден: не null,
выровнен, указывает на живое инициализированное значение правильного типа, и что не
нарушается алиасинг (нет одновременного `&mut` и другого доступа к той же памяти).
Обещание ложно - UB.

Обратно из указателя ссылку добывают через `&*p` (в unsafe), беря на себя lifetime и
алиасинг. Полезные методы: `ptr::null()`/`null_mut()`, `<*const T>::is_null()`,
`ptr.cast::<U>()` для смены типа указателя.

## 3. Арифметика указателей

Указатели умеют адресную арифметику - основу работы с массивами и буферами на низком
уровне. `ptr.add(n)` сдвигает указатель на `n` *элементов* (не байт) вперёд, `sub(n)` -
назад, `offset(n)` - на знаковое смещение. Чтение по адресу - `*ptr` или `ptr.read()`.

```rust
let a = [10, 20, 30, 40];
let base: *const i32 = a.as_ptr();

let third = unsafe { *base.add(2) };    // элемент с индексом 2
assert_eq!(third, 30);
```

Жёсткий инвариант: результат `add`/`offset` обязан оставаться **в пределах той же
аллокации** (или на одну позицию за её концом - "one-past-the-end"). Уводить указатель за
границы объекта - UB, даже если разыменования не будет: у указателя есть *provenance*
(происхождение), привязывающее его к конкретной аллокации, и выход за неё компилятор
считает недопустимым. Поэтому арифметика указателей - типичное содержимое `unsafe fn`,
где длина буфера передаётся как часть контракта (раздел 4).

## 4. `unsafe fn` и контракты безопасности

Когда функция сама по себе безопасна лишь при выполнении условий, которые она проверить не
может, её объявляют `unsafe fn`. Это переносит обязанность на вызывающего: чтобы вызвать
её, он обязан написать `unsafe`-блок и гарантировать *контракт* - предусловия, при которых
поведение определено. Контракт документируется разделом `# Safety`.

```rust
/// Складывает `len` подряд идущих i64, начиная с `ptr`.
///
/// # Safety
/// `ptr` должен быть валиден для чтения `len` последовательных значений `i64`
/// (одна аллокация, корректное выравнивание, инициализированные данные).
unsafe fn sum_raw(ptr: *const i64, len: usize) -> i64 {
    let mut sum = 0;
    for i in 0..len {
        sum += unsafe { *ptr.add(i) };   // корректно при соблюдении контракта
    }
    sum
}
```

Главная цель модуля - **безопасная абстракция** (soundness). Небезопасное ядро прячут
внутри функции с *безопасной* сигнатурой, которая сама устанавливает все предусловия перед
входом в unsafe, так что никакой (даже вредительский) безопасный код снаружи не сможет
вызвать UB. Классический пример - `split_at_mut`: он раздаёт две непересекающиеся `&mut`-
части одного среза, что borrow checker в safe-коде запрещает, но за счёт проверки `mid`
и знания, что части не пересекаются, обёртка остаётся безопасной.

```rust
fn split_at_mut(slice: &mut [i64], mid: usize) -> (&mut [i64], &mut [i64]) {
    let len = slice.len();
    assert!(mid <= len);                 // предусловие, делающее unsafe корректным
    let ptr = slice.as_mut_ptr();
    unsafe {
        (
            std::slice::from_raw_parts_mut(ptr, mid),
            std::slice::from_raw_parts_mut(ptr.add(mid), len - mid),
        )
    }
}
```

Абстракция *unsound* (нездоровая), если существует безопасный вызывающий код, способный ею
вызвать UB. Такой API - ошибка, даже если внутри "обычно работает".

## 5. Неопределённое поведение и Miri

UB - это операции, которые модель Rust объявляет недопустимыми; при них компилятор ничего
не гарантирует (оптимизатор вправе исходить из того, что UB не случается). Основные виды:

- гонка данных (data race) - незащищённый конкурентный доступ, где хоть один пишет (M22);
- разыменование null, висячего или невыровненного указателя;
- обращение за границы аллокации, увод указателя за её пределы;
- чтение неинициализированной памяти (раздел 6);
- нарушение алиасинга: живой `&mut` одновременно с другим доступом к той же ячейке;
- создание *невалидного значения*: `bool` не 0/1, `char` вне диапазона, ссылка = null,
  недопустимый вариант enum.

UB не обязано проявляться сразу: программа может "работать", пока смена оптимизаций,
платформы или входных данных не превратит скрытое UB в сбой. Поэтому unsafe-код проверяют
инструментами. Главный - **Miri**, интерпретатор MIR, ловящий многие UB во время
выполнения тестов:

```sh
cargo +nightly miri test -p sol-26-...
```

Miri отлавливает выход за границы, чтение uninit, нарушения алиасинга (модель Stacked/Tree
Borrows), утечки. Прогонять unsafe-решения под Miri - хорошая привычка; см.
<https://github.com/rust-lang/miri>. Систематическое изложение unsafe - Rustonomicon:
<https://doc.rust-lang.org/nomicon/>.

## 6. `MaybeUninit`: неинициализированная память

Читать неинициализированную память - UB (это невалидное значение). Поэтому нельзя просто
"завести переменную без значения" и записать её позже через указатель - модель считает
такое чтение UB даже для целых чисел. Для легального обращения с ещё-не-инициализированной
памятью существует `MaybeUninit<T>`: обёртка размером с `T`, которой *разрешено* быть
неинициализированной.

Жизненный цикл: `MaybeUninit::uninit()` создаёт "дырку", `write(value)` кладёт значение
(не запуская деструктор старого - его нет), `assume_init()` забирает готовое `T`.
`assume_init` - unsafe: вы утверждаете, что запись уже была; иначе UB.

```rust
use std::mem::MaybeUninit;

let mut slot: MaybeUninit<String> = MaybeUninit::uninit();
slot.write(String::from("hi"));                // проинициализировали
let s: String = unsafe { slot.assume_init() }; // теперь забирать безопасно
assert_eq!(s, "hi");
```

Массив неинициализированных ячеек - `[MaybeUninit<T>; N]` - можно создать сразу (сам
массив не требует инициализации элементов); каждый элемент затем заполняют `write`.
Удобная форма создания - inline const:

```rust
use std::mem::MaybeUninit;

let mut buf = [const { MaybeUninit::<i64>::uninit() }; 4];
for (i, slot) in buf.iter_mut().enumerate() {
    slot.write(i as i64 * 10);
}
// после заполнения элементы читают через assume_init/ptr::read.
```

`MaybeUninit` нужен и при построении своих коллекций (буфер под ещё не добавленные
элементы, M28), и в FFI. Документация: <https://doc.rust-lang.org/std/mem/union.MaybeUninit.html>.

## 7. Контроль деструкторов: `ManuallyDrop` и `ptr::read`/`write`

Обычно Rust сам зовёт `Drop` в конце области видимости. Иногда это мешает: при ручном
перемещении значений через указатели один и тот же объект может быть "прочитан" дважды и
дважды дропнут (double-free), либо, наоборот, забыт.

- `ptr::read(src)` копирует значение *из* адреса по владению, **не** трогая источник:
  ответственность за то, чтобы источник больше не был дропнут, - на программисте.
- `ptr::write(dst, val)` записывает значение по адресу, **не** запуская деструктор того,
  что там лежало раньше (в отличие от обычного присваивания `*dst = val`, которое дропает
  старое). Нужен, когда по адресу лежит мусор/uninit.
- `ptr::drop_in_place(p)` запускает деструктор значения по адресу, не освобождая память -
  так дропают элементы в своём буфере.
- `ManuallyDrop<T>` - обёртка, отменяющая автоматический `Drop`; сбросить вручную можно
  через `ManuallyDrop::drop` (unsafe). `mem::forget(x)` - просто "потерять" значение, не
  вызывая деструктор.

```rust
// Переставить значение по &mut, не дропнув его дважды:
fn replace<T>(slot: &mut T, new: T) -> T {
    unsafe {
        let old = std::ptr::read(slot);   // забрали старое, не тронув slot
        std::ptr::write(slot, new);       // положили новое, не дропнув мусор
        old                               // старое возвращаем - дропнет вызывающий
    }
}
```

Ключевой инвариант ручного перемещения: **каждое значение должно быть дропнуто ровно один
раз**. `ptr::read` без последующей перезаписи/забывания источника ведёт к double-free;
лишний `mem::forget` - к утечке (утечка не UB, но обычно баг). Документация:
<https://doc.rust-lang.org/std/ptr/index.html>.

```rust
// 1. Разыменование указателя на уже уничтоженное значение (dangling):

// unsafe { *p };                           // [!] UB: висячий указатель

// 3. assume_init до записи -> чтение uninit:
// let s: MaybeUninit<String> = MaybeUninit::uninit();
// let _ = unsafe { s.assume_init() };      // [!] UB: значение не записано

// 4. ptr::read без "забывания" источника -> двойной дроп:
// let s = String::from("x");

//    не знает предусловий. Всегда описывайте инвариант.

// 7. add/offset за границу аллокации - UB сам по себе, даже без разыменования.
```
