# M27 - Представление в памяти

> Часть IX "Небезопасность, память, FFI". Предыдущий модуль: [M26 unsafe](../26-unsafe/README.md).

## Цель модуля

До сих пор тип для нас был множеством значений и набором операций, а *как именно* эти
значения лежат в памяти, компилятор скрывал. Для safe-кода это и не важно. Но как только
данные пересекают границу процесса - пишутся в файл, уходят в сеть, передаются в
библиотеку на C (M29), - важно ровно обратное: сколько байт занимает значение, в каком
порядке идут поля, где выравнивание вставило "дырки" (padding), в каком порядке байт
записано число. Ошибка здесь не отлавливается borrow checker'ом: она проявится как
испорченный пакет или чтение мусора у того, кто читает эти байты.

Важно с самого начала различать *layout* и *ABI/представление в файле*. Layout - это
решение компилятора о размере, выравнивании и смещениях полей конкретного типа в памяти
данного процесса. По умолчанию Rust использует представление `repr(Rust)`, которое
**не** фиксировано: компилятор вправе переставлять поля, добавлять padding и вообще
менять раскладку от сборки к сборке. Поэтому "просто скопировать структуру в байты и
отправить" в общем случае некорректно. Модуль про то, как сделать layout предсказуемым
(`repr(C)` и родственники), как измерять его (`size_of`/`align_of`/`offset_of!`) и как
осознанно превращать значения в байты и обратно, контролируя порядок байт (endianness).

После модуля вы умеете:

- [ ] объяснять разницу между `repr(Rust)` (layout не гарантирован) и `repr(C)`
      (предсказуемый порядок полей и padding по правилам C);
- [ ] измерять размер, выравнивание и смещения полей через `size_of`, `align_of`,
      `offset_of!` и объяснять, откуда берётся padding;
- [ ] применять `repr(transparent)` для newtype с тем же ABI, что у поля, и понимать,
      чем опасен `repr(packed)` (невыровненные ссылки - UB);
- [ ] сериализовать целые и структуры в байты и разбирать их обратно, явно выбирая
      порядок байт (`to_le_bytes`/`from_be_bytes` и т.п.);
- [ ] отличать little-endian, big-endian и native, знать про network byte order;
- [ ] делать zero-copy-приведение байтов к типу и обратно через `bytemuck` (трейты
      `Pod`/`Zeroable`) и называть условия, при которых это корректно.

## 1. Layout: размер, выравнивание, зачем padding

У каждого типа `T` есть две числовые характеристики. *Размер* (`size_of::<T>()`) - сколько
байт занимает одно значение; на столько сдвигается указатель между соседними элементами
массива. *Выравнивание* (`align_of::<T>()`) - степень двойки, на кратный которой адрес
обязано лежать значение. Процессор читает выровненные данные эффективнее (а на части
архитектур невыровненный доступ - вообще ошибка), поэтому компилятор располагает значения
по выровненным адресам.

Из выравнивания рождается padding. Если в структуре за однобайтовым полем идёт
четырёхбайтовое, между ними вставляются байты-заполнители, чтобы четырёхбайтовое начиналось
с адреса, кратного 4. Размер всей структуры тоже округляется вверх до её выравнивания,
чтобы в массиве каждый следующий элемент снова оказался выровнен.

```rust
use std::mem::{size_of, align_of};

assert_eq!(size_of::<u8>(), 1);
assert_eq!(size_of::<u32>(), 4);
assert_eq!(align_of::<u32>(), 4);

// (u8, u32): 1 байт + 3 байта padding + 4 байта = 8, выравнивание 4.
assert_eq!(size_of::<(u8, u32)>(), 8);
assert_eq!(align_of::<(u8, u32)>(), 4);
```

Выравнивание структуры равно максимальному из выравниваний её полей. Из-за padding сумма
размеров полей может быть меньше размера структуры - "потерянные" байты и есть
заполнители.

## 2. Измерение layout: `offset_of!`

Размер и выравнивание дают `size_of`/`align_of`. Смещение конкретного поля от начала
структуры даёт макрос `offset_of!(Type, field)` (стабилен с Rust 1.77). Он и есть основной
инструмент, чтобы увидеть, куда компилятор положил поле и сколько padding он вставил.

```rust
use std::mem::offset_of;

#[repr(C)]
struct S { a: u8, b: u32, c: u16 }

assert_eq!(offset_of!(S, a), 0);   // с начала
assert_eq!(offset_of!(S, b), 4);   // после a - 3 байта padding до кратного 4
assert_eq!(offset_of!(S, c), 8);   // сразу за b
// size_of::<S>() == 12: 10 байт данных, округлённые вверх до align 4.
```

Для `repr(Rust)` (см. раздел 3) эти числа не гарантированы и могут отличаться между
сборками - измерять смещения имеет смысл в основном у типов с фиксированным
представлением. Документация: <https://doc.rust-lang.org/std/mem/macro.offset_of.html>.

## 3. `repr(Rust)` против `repr(C)`

По умолчанию структура имеет представление `repr(Rust)`. Единственное, что гарантирует
компилятор, - что значения корректно выровнены и не перекрываются; **порядок полей и
padding не специфицированы**. На практике компилятор переставляет поля, чтобы уменьшить
padding (например, кладёт крупные поля первыми). Это хорошо для памяти, но означает, что
раскладку `repr(Rust)`-типа нельзя закладывать в формат файла или сетевого протокола.

Атрибут `#[repr(C)]` включает предсказуемое представление "как в C": поля идут в порядке
объявления, padding вставляется по тем же правилам, что и в разделе 1, размер округляется
вверх до выравнивания. Именно `repr(C)` используют, когда layout должен быть стабилен - для
FFI (M29), сериализации через байты, zero-copy (раздел 7).

```rust
#[repr(C)]
struct Rgba { r: u8, g: u8, b: u8, a: u8 }  // ровно 4 байта, поля по порядку, без дырок

#[repr(Rust)]                                // (по умолчанию) порядок полей не гарантирован
struct Loose { flag: u8, id: u64 }
```

Полное описание правил представлений - Rust Reference, раздел "Type Layout":
<https://doc.rust-lang.org/reference/type-layout.html>.

## 4. `repr(transparent)`

`#[repr(transparent)]` разрешён для структуры ровно с одним полем ненулевого размера (плюс
любое число ZST-полей). Он гарантирует, что размер, выравнивание и ABI обёртки **совпадают
с полем**. Это то, что нужно для newtype (M04): тип-обёртка существует на уровне системы
типов, но в памяти и в вызовах FFI неотличим от внутреннего значения.

```rust
#[repr(transparent)]
struct Meters(f64);   // в памяти и в ABI это ровно f64

assert_eq!(
    std::mem::size_of::<Meters>(),
    std::mem::size_of::<f64>()
);
```

В отличие от `repr(C)`, `transparent` ничего не добавляет к layout - он лишь фиксирует, что
обёртка прозрачна. Это важно для трейтов вроде `bytemuck::Pod` (раздел 7) и для передачи
newtype через границу C.

## 5. `repr(packed)` и невыровненный доступ

`#[repr(packed)]` (или `packed(N)`) убирает padding: поля укладываются вплотную,
выравнивание структуры становится 1 (или `N`). Так экономят байты в плотных бинарных
форматах, но ценой опасности: поле внутри packed-структуры может оказаться невыровненным,
а создать ссылку (`&`/`&mut`) на невыровненное значение - **UB**, даже если её не
разыменовывать.

```rust
#[repr(C, packed)]
struct Packed { tag: u8, value: u32 }   // value лежит по смещению 1 - невыровнено

let p = Packed { tag: 1, value: 0xAABBCCDD };
// let r = &p.value;          // [!] UB: ссылка на невыровненное поле
let v = p.value;              // копия по значению - можно (Copy-поле)
assert_eq!(v, 0xAABBCCDD);
```

С packed-полями работают либо копированием по значению (как выше, если поле `Copy`), либо
через сырые указатели макросами `std::ptr::addr_of!`/`addr_of_mut!`, которые дают
`*const`/`*mut`, не создавая промежуточной ссылки. Практический вывод: `packed` применяют
редко и осторожно; чаще достаточно `repr(C)` с ручной укладкой в байты (раздел 6).
Документация: <https://doc.rust-lang.org/std/ptr/macro.addr_of.html>.

## 6. Байтовый I/O и endianness

Чтобы значение пережило запись в файл или отправку по сети, его превращают в
последовательность байт. Для целых типов стандартная библиотека даёт методы прямого
преобразования, где порядок байт выбирается явно:

- `to_le_bytes` / `from_le_bytes` - little-endian: младший байт первым;
- `to_be_bytes` / `from_be_bytes` - big-endian: старший байт первым (он же network byte
  order, порядок байт в большинстве сетевых протоколов);
- `to_ne_bytes` / `from_ne_bytes` - native: порядок текущей платформы (непереносимо между
  архитектурами; годится только внутри одной машины).

```rust
let n: u32 = 0x0A0B0C0D;
assert_eq!(n.to_be_bytes(), [0x0A, 0x0B, 0x0C, 0x0D]);   // старший первым
assert_eq!(n.to_le_bytes(), [0x0D, 0x0C, 0x0B, 0x0A]);   // младший первым

let back = u32::from_be_bytes([0x0A, 0x0B, 0x0C, 0x0D]);
assert_eq!(back, n);
```

*Endianness* (порядок байт) - это соглашение о том, в каком порядке байты
многобайтового числа лежат в памяти или в потоке. x86 и ARM обычно little-endian, сетевые
протоколы - big-endian. При разборе чужого формата порядок байт задан спецификацией
формата, а не вашей платформой; поэтому используют явные `_le`/`_be`, а не `_ne`.

Методы `from_*_bytes` принимают массив фиксированной длины (`[u8; 4]` для `u32`). Кусок
среза приводят к массиву через `TryInto` (M13): `let arr: [u8; 4] = slice[0..4].try_into()?;`
- это же даёт бесплатную проверку длины.

## 7. Zero-copy через `bytemuck`

Ручная укладка поле-в-байты (раздел 6) корректна, но многословна. Когда тип уже имеет
`repr(C)` без padding и состоит только из "простых старых данных" (plain old data), его
байтовое представление совпадает с представлением в памяти, и превращение в `&[u8]` и
обратно можно делать *без копирования* - переинтерпретацией указателя. Делать это вручную
на unsafe легко неправильно (алиасинг, выравнивание, скрытый padding); стандартом де-факто
служит крейт `bytemuck`, дающий проверенные безопасные обёртки.

Ключевые трейты `bytemuck`:

- `Zeroable` - тип, для которого "все нули" - валидное значение;
- `Pod` (plain old data) - тип без указателей, padding и инвариантов: любая комбинация
  байт нужного размера - валидное значение. Требует `Copy` и `Zeroable`. Выводится
  `#[derive(Pod, Zeroable)]` только для `repr(C)`/`transparent`-типов без padding.

```rust
use bytemuck::{Pod, Zeroable};

#[repr(C)]
#[derive(Clone, Copy, Pod, Zeroable)]
struct Vertex { x: f32, y: f32 }

let verts = [Vertex { x: 1.0, y: 2.0 }, Vertex { x: 3.0, y: 4.0 }];
let bytes: &[u8] = bytemuck::cast_slice(&verts);   // zero-copy, 16 байт
assert_eq!(bytes.len(), 16);
```

`cast_slice` паникует, если выравнивание или длина не сходятся; `try_cast_slice` возвращает
`Result`. Когда исходные байты могут быть не выровнены (например, `&[u8]` из `Vec<u8>` имеет
выравнивание 1), безопаснее копирующий `pod_collect_to_vec`, которому выравнивание входа не
важно. Документация: <https://docs.rs/bytemuck/latest/bytemuck/>.

Почему `derive(Pod)` требует отсутствия padding: байты padding не инициализированы, а `Pod`
обещает, что *любые* байты значения валидны и читаемы. Тип с "дыркой" это обещание
нарушает, поэтому derive такой тип отвергает - и это ровно та проверка, которой не хватает
ручному unsafe.

## 8. Типовые грабли

```rust
// 1. Полагаться на порядок полей repr(Rust)-структуры при сериализации:
//    компилятор волен его переставить. Для стабильного layout нужен #[repr(C)].

// 2. Ссылка на поле packed-структуры - UB, даже без разыменования:
// #[repr(C, packed)] struct P { a: u8, b: u32 }
// let p = P { a: 0, b: 1 };
// let r = &p.b;          // [!] UB: невыровненная ссылка. Читайте копией: let v = p.b;

// 3. Порядок байт по умолчанию платформы (to_ne_bytes) в формате, который читают на
//    другой машине -> "перевёрнутые" числа. В протоколах используйте _le/_be явно.

// 4. from_*_bytes требует массив ТОЧНОЙ длины; срез неверной длины через try_into даст
//    Err - не игнорируйте, это ваша проверка границ.

// 5. derive(Pod) на типе с padding не скомпилируется - это защита, а не помеха:
//    переупорядочьте поля или уберите дырку, а не обходите проверку unsafe.

// 6. cast_slice на невыровненных байтах паникует; для &[u8] из Vec берите
//    pod_collect_to_vec (копирует) или try_cast_slice (Result), не unwrap вслепую.

// 7. Размер структуры != сумме размеров полей из-за padding: не считайте его "в уме",
//    измеряйте size_of/offset_of!.
```
