# M28 - Свои коллекции на unsafe

> Часть IX "Небезопасность, память, FFI". Предыдущий модуль: [M27 представление в памяти](../27-memory-layout/README.md).

## Цель модуля

`Vec`, `Box`, `String` кажутся встроенными в язык, но это обычные библиотечные типы. Внутри
они делают ровно то, что до сих пор пряталось за safe-абстракциями: запрашивают у
аллокатора блок памяти, кладут туда значения через сырые указатели, следят за длиной и
ёмкостью, а в конце возвращают память и роняют элементы. В этом модуле мы собираем такие
коллекции сами - и тем самым видим, из каких инвариантов складывается их безопасность.

Модуль опирается на M26 (сырые указатели, `unsafe`, инварианты) и M27 (`Layout`, размер и
выравнивание). Новое здесь - интерфейс аллокатора (`alloc`/`realloc`/`dealloc`), тип
`NonNull<T>` как строительный блок безопасных обёрток, и ручное управление жизненным циклом
элементов: инициализация неинициализированной памяти, перенос владения через `ptr::read`,
запуск деструкторов в `Drop`. Отдельно разбираются два крайних случая, на которых ломается
наивная реализация: типы нулевого размера (ZST) и подмена глобального аллокатора.

После модуля вы умеете:

- [ ] запрашивать и освобождать память вручную через `alloc`/`dealloc`/`realloc` с
      корректным `Layout`, обрабатывая отказ выделения (`handle_alloc_error`);
- [ ] объяснять, чем `NonNull<T>` лучше `*mut T` для обёрток (не-null, ковариантность), и
      строить на нём тип-указатель;
- [ ] реализовать `Box`-подобный владелец: выделение, `Deref`/`DerefMut`, `Drop` с
      `drop_in_place`;
- [ ] реализовать растущий `Vec`: удвоение ёмкости через `realloc`, `push`/`pop` на
      `ptr::write`/`ptr::read`, срез через `Deref`, освобождение и роняние элементов в
      `Drop`;
- [ ] объяснять, почему типы нулевого размера не требуют выделения, и корректно вести их
      длину и деструкторы;
- [ ] подменять глобальный аллокатор своим типом с `#[global_allocator]`, реализуя трейт
      `GlobalAlloc`.

## 1. Интерфейс аллокатора: `Layout`, `alloc`, `dealloc`

Куча (heap) - это область памяти, которой заведует *аллокатор*. Чтобы получить блок, ему
сообщают, сколько байт и с каким выравниванием нужно; описывает это уже знакомый по M27 тип
`Layout`. Низкоуровневый интерфейс живёт в `std::alloc`:

- `alloc(layout) -> *mut u8` - выделить блок под `layout`; возвращает указатель либо null
  при неудаче. Содержимое блока не инициализировано.
- `dealloc(ptr, layout)` - вернуть блок аллокатору. `layout` обязан совпадать с тем, что
  был при выделении.
- `realloc(ptr, old_layout, new_size)` - изменить размер блока, по возможности на месте,
  иначе выделить новый и скопировать старое содержимое; возвращает новый указатель.
- `handle_alloc_error(layout)` - стандартная реакция на нехватку памяти (аварийно
  завершает процесс); вызывается, когда `alloc`/`realloc` вернули null. Не возвращается.

```rust
use std::alloc::{alloc, dealloc, handle_alloc_error, Layout};
use std::ptr::NonNull;

let layout = Layout::new::<u64>();               // размер 8, выравнивание 8
// SAFETY: layout ненулевого размера.
let ptr = unsafe { alloc(layout) } as *mut u64;
let ptr = match NonNull::new(ptr) {
    Some(p) => p,
    None => handle_alloc_error(layout),          // память кончилась
};
unsafe {
    ptr.as_ptr().write(42);                      // инициализируем ячейку
    assert_eq!(ptr.as_ptr().read(), 42);
    dealloc(ptr.as_ptr() as *mut u8, layout);    // тем же layout
}
```

Три инварианта этого интерфейса: (1) в `alloc` нельзя передавать `Layout` нулевого размера;
(2) `dealloc` вызывается ровно один раз для каждого выделения (иначе double-free); (3)
`layout` при освобождении совпадает с выделявшим. Нарушение любого - UB. Документация:
<https://doc.rust-lang.org/std/alloc/index.html>.

## 2. `NonNull<T>` вместо `*mut T`

Хранить в обёртке сырой `*mut T` можно, но неудобно: он допускает значение null и
*инвариантен* по `T` (не пропускает подтипирование по времени жизни, о вариантности - M09).
Стандартные коллекции хранят вместо него `std::ptr::NonNull<T>` - обёртку над `*mut T` с
двумя свойствами: указатель гарантированно не null (это включает нишевую оптимизацию, как у
`&T`: `Option<NonNull<T>>` того же размера, что указатель) и ковариантность по `T`.

```rust
use std::ptr::NonNull;

let mut x = 10u32;
let p: NonNull<u32> = NonNull::from(&mut x);       // из ссылки - всегда не null
unsafe { assert_eq!(p.as_ptr().read(), 10); }

// NonNull::new проверяет на null и возвращает Option:
let raw: *mut u32 = std::ptr::null_mut();
assert!(NonNull::new(raw).is_none());

// Для пустой коллекции (ещё без выделения) нужен "висячий, но выровненный" указатель:
let dangling: NonNull<u32> = NonNull::dangling();  // не null, разыменовывать нельзя
```

`NonNull::dangling()` даёт указатель, равный выравниванию `T` (не null, но невалидный для
доступа) - им инициализируют буфер пустой коллекции, пока `cap == 0`. `NonNull` не даёт
никаких гарантий валидности или алиасинга: разыменование остаётся `unsafe`, за инварианты
по-прежнему отвечает автор. Что он добавляет - это "не null" и правильную вариантность, ровно
то, что нужно обёртке. Документация:
<https://doc.rust-lang.org/std/ptr/struct.NonNull.html>.

## 3. Свой `Box`: владелец одного значения

`Box<T>` - простейший владелец кучи: выделяет память под один `T`, кладёт туда значение,
даёт к нему доступ через `Deref`, а в `Drop` роняет значение и освобождает память. Соберём
`MyBox<T>` (для `T` ненулевого размера):

```rust
use std::alloc::{alloc, dealloc, handle_alloc_error, Layout};
use std::ops::Deref;
use std::ptr::NonNull;

struct MyBox<T> { ptr: NonNull<T> }

impl<T> MyBox<T> {
    fn new(value: T) -> Self {
        let layout = Layout::new::<T>();
        let raw = unsafe { alloc(layout) } as *mut T;
        let ptr = NonNull::new(raw).unwrap_or_else(|| handle_alloc_error(layout));
        unsafe { ptr.as_ptr().write(value) };      // write, не *p = value
        MyBox { ptr }
    }
}

impl<T> Deref for MyBox<T> {
    type Target = T;
    fn deref(&self) -> &T { unsafe { self.ptr.as_ref() } }
}

impl<T> Drop for MyBox<T> {
    fn drop(&mut self) {
        unsafe {
            std::ptr::drop_in_place(self.ptr.as_ptr());          // сначала деструктор T
            dealloc(self.ptr.as_ptr() as *mut u8, Layout::new::<T>());  // потом память
        }
    }
}
```

Два ключевых момента. Первый: в свежую память значение кладут через `ptr::write`, а не через
`*ptr = value`. Присваивание сначала пытается *уронить старое* значение по адресу, а его там
ещё нет - память не инициализирована, и запуск деструктора над мусором - UB. `write`
записывает, не роняя ничего. Второй: в `Drop` порядок строг - `drop_in_place` запускает
деструктор `T` (иначе ресурсы внутри `T`, например `String`, утекут), и только потом
`dealloc` возвращает память. `dealloc` сам деструкторов не вызывает.

## 4. Рост буфера: `realloc` и удвоение ёмкости

Вектор отличается от `Box` тем, что хранит *много* элементов в непрерывном буфере и умеет
расти. У него две величины: `cap` - сколько элементов помещается в текущем буфере, и `len` -
сколько уже занято (`len <= cap`). Пока места хватает, `push` просто пишет в следующую
ячейку; когда `len == cap`, буфер надо увеличить.

Наращивать по одному элементу дорого: каждый `push` копировал бы весь буфер. Поэтому ёмкость
растят *геометрически* - обычно удваивают. Тогда `n` вставок стоят суммарно `O(n)`
копирований (амортизированная константа на вставку). Само увеличение делает `realloc`,
который переносит старое содержимое в новый блок:

```rust
use std::alloc::{alloc, realloc, handle_alloc_error, Layout};
use std::ptr::NonNull;

// метод буфера со схемой "0 -> 4, иначе удвоение"
fn grow(&mut self) {
    let new_cap = if self.cap == 0 { 4 } else { self.cap * 2 };
    let new_layout = Layout::array::<T>(new_cap).expect("превышен предел ёмкости");

    let new_ptr = if self.cap == 0 {
        unsafe { alloc(new_layout) }                       // первого буфера ещё не было
    } else {
        let old_layout = Layout::array::<T>(self.cap).unwrap();
        unsafe { realloc(self.ptr.as_ptr() as *mut u8, old_layout, new_layout.size()) }
    };

    self.ptr = NonNull::new(new_ptr as *mut T)
        .unwrap_or_else(|| handle_alloc_error(new_layout));
    self.cap = new_cap;
}
```

`Layout::array::<T>(n)` считает layout массива и возвращает `Err` при переполнении (размер
больше `isize::MAX`) - это защита от целочисленного переполнения при вычислении размера, её
нельзя пропускать. После `realloc` старый указатель невалиден: аллокатор мог перенести блок,
поэтому все элементы адресуются заново от нового `ptr`.

## 5. Свой `Vec`: `push`, `pop`, срез, `Drop`

Сложив рост буфера (раздел 4) с ведением `len`, получаем вектор. Основные операции - на
`ptr::write` (положить) и `ptr::read` (забрать):

```rust
// методы MyVec<T> { ptr: NonNull<T>, cap: usize, len: usize }
fn push(&mut self, value: T) {
    if self.len == self.cap { self.grow(); }
    // ячейка [len] не инициализирована - только write
    unsafe { self.ptr.as_ptr().add(self.len).write(value) };
    self.len += 1;
}

fn pop(&mut self) -> Option<T> {
    if self.len == 0 { return None; }
    self.len -= 1;
    // read забирает значение, передавая владение наружу; len уже уменьшен,
    // поэтому эту ячейку больше не прочитают повторно
    Some(unsafe { self.ptr.as_ptr().add(self.len).read() })
}
```

`push` пишет в незанятую ячейку через `write` (по той же причине, что в разделе 3). `pop`
через `read` *перемещает* значение из буфера наружу и уменьшает `len` - ячейка считается
свободной, и повторного чтения (double-read, тоже UB) не будет.

Чтобы не переписывать вручную индексацию, итерацию и десятки методов среза, вектор отдаёт
`Deref<Target = [T]>`: первые `len` инициализированных ячеек - это и есть срез.

```rust
impl<T> Deref for MyVec<T> {
    type Target = [T];
    fn deref(&self) -> &[T] {
        unsafe { std::slice::from_raw_parts(self.ptr.as_ptr(), self.len) }
    }
}
```

Через это `v[i]`, `v.iter()`, `v.first()`, `v.len()` и прочее работают "бесплатно". Наконец,
`Drop` обязан сначала уронить все `len` живых элементов, затем освободить буфер - иначе
деструкторы элементов не вызовутся (утечка), а память не вернётся:

```rust
impl<T> Drop for MyVec<T> {
    fn drop(&mut self) {
        while self.pop().is_some() {}               // роняем элементы
        if self.cap != 0 {
            let layout = Layout::array::<T>(self.cap).unwrap();
            unsafe { dealloc(self.ptr.as_ptr() as *mut u8, layout) };
        }
    }
}
```

Полный разбор этой конструкции - глава "Implementing Vec" в Rustonomicon:
<https://doc.rust-lang.org/nomicon/vec/vec.html>.

## 6. Типы нулевого размера (ZST)

Реализация из разделов 4-5 молча предполагает `size_of::<T>() != 0`. Для типов нулевого
размера (ZST - `()`, пустые структуры, `PhantomData`) она ломается: `ptr.add(len)` не
сдвигается (шаг элемента - ноль байт), а `Layout::array::<T>(n)` даёт нулевой размер,
который запрещено передавать в `alloc`.

Правильный вывод: под ZST память не нужна вовсе. Миллион значений нулевого размера занимает
ноль байт - хранить достаточно одну лишь длину `len`, а как указатель использовать
`NonNull::dangling()`. Тонкость в другом: даже у ZST может быть `Drop`, и его нужно вызвать
столько раз, сколько значений было добавлено.

```rust
struct ZstVec<T> { len: usize, _marker: PhantomData<T> }

impl<T> ZstVec<T> {
    fn push(&mut self, value: T) {
        std::mem::forget(value);                    // байт нет, но ронять сейчас нельзя
        self.len += 1;
    }
    fn pop(&mut self) -> Option<T> {
        if self.len == 0 { return None; }
        self.len -= 1;
        // чтение ZST из dangling не трогает ни одного байта и даёт владеемый T
        Some(unsafe { NonNull::<T>::dangling().as_ptr().read() })
    }
}
```

`push` не хранит значение (хранить нечего), но и уронить его на месте нельзя - иначе
деструктор сработал бы раньше времени; поэтому `mem::forget` подавляет немедленный `Drop`, а
счётчик растёт. `pop` "воссоздаёт" один экземпляр чтением из висячего указателя (для ZST это
корректно - читается ноль байт) и передаёт владение наружу, где деструктор и отрабатывает.
Итог: ровно `len` деструкторов, ноль выделений. Подробнее - "Handling Zero-Sized Types" в
Rustonomicon: <https://doc.rust-lang.org/nomicon/vec/vec-zsts.html>.

## 7. Свой глобальный аллокатор: `GlobalAlloc`

До сих пор мы вызывали `alloc`/`dealloc` напрямую. Но и `Box`, и `Vec`, и `String`
обращаются к *глобальному аллокатору* программы. Его можно заменить своим: тип, реализующий
трейт `GlobalAlloc`, помеченный атрибутом `#[global_allocator]`, становится источником всей
динамической памяти. Так подключают альтернативные аллокаторы (jemalloc, mimalloc) или, как
здесь, оборачивают системный, чтобы профилировать выделения.

```rust
use std::alloc::{GlobalAlloc, Layout, System};
use std::sync::atomic::{AtomicUsize, Ordering};

struct Counting;
static LIVE: AtomicUsize = AtomicUsize::new(0);     // сейчас занято байт

unsafe impl GlobalAlloc for Counting {
    unsafe fn alloc(&self, layout: Layout) -> *mut u8 {
        let ptr = System.alloc(layout);             // делегируем системному
        if !ptr.is_null() {
            LIVE.fetch_add(layout.size(), Ordering::Relaxed);
        }
        ptr
    }
    unsafe fn dealloc(&self, ptr: *mut u8, layout: Layout) {
        System.dealloc(ptr, layout);
        LIVE.fetch_sub(layout.size(), Ordering::Relaxed);
    }
}

#[global_allocator]
static GLOBAL: Counting = Counting;
```

Особенности глобального аллокатора: он вызывается из любого потока, поэтому состояние ведут
через atomics (M23), а не `Mutex` (аллокатор не может занимать блокировку, которая сама
захочет выделить память). Учитывать выделение имеет смысл только при не-null указателе:
неудавшийся `alloc` памяти не создал. Реализация `GlobalAlloc` помечена `unsafe impl` -
автор обещает соблюдать контракт (валидные указатели, совпадающие layout). Документация:
<https://doc.rust-lang.org/std/alloc/trait.GlobalAlloc.html>.

## 8. Типовые грабли

```text
1. Запись в неинициализированную память присваиванием (*ptr = value): присваивание сначала
   роняет "старое" значение, а его там нет -> UB. В свежую ячейку пишут ptr::write.

2. Забыть drop_in_place / роняние элементов в Drop: память вернётся (dealloc), но
   деструкторы T не вызовутся -> утечка ресурсов внутри элементов.

3. dealloc с другим Layout, чем при alloc, или двойной dealloc -> UB. Освобождать тем же
   layout и ровно один раз.

4. Передать Layout нулевого размера в alloc -> UB. Пустая коллекция вообще не выделяет
   (cap == 0, ptr = NonNull::dangling()).

5. Игнорировать Err от Layout::array (переполнение размера) -> тихое переполнение и слишком
   маленький буфер. Проверять/паниковать.

6. Наивный Vec на ZST: ptr.add(len) не двигается, Layout::array даёт 0 -> сломанная
   арифметика. ZST обрабатывают отдельной веткой без выделения (раздел 6).

7. Использовать указатель после realloc: блок мог переехать. Все обращения - от нового ptr.

8. В GlobalAlloc считать выделение при null-указателе или брать Mutex: счётчик соврёт, а
   блокировка в аллокаторе может привести к рекурсивному выделению. Только atomics, только
   при успехе.
```

## Упражнения

Решайте по порядку, ярусами. В каждом крейте: условие и `todo!()` в `src/lib.rs`, тесты в
`tests/tests.rs` (менять нельзя). Запуск: `cargo test -p ex-28-NN-...`. Все упражнения - на
стандартной библиотеке, без внешних зависимостей. Работа идёт с сырой памятью: если стоит
`miri`, полезно прогнать решения под ним (`cargo +nightly miri test`) - он ловит UB, которое
обычные тесты пропускают.

**0x - синтаксис**
- `01_layout_calc` - `Layout::array` и вычисление размера/выравнивания массива, обработка
  переполнения.
- `02_nonnull` - построение `NonNull<T>` и чтение/запись через сырой указатель.

**1x - базовое**
- `03_heap_cell` - выделить одно значение на куче через `alloc`/`dealloc` и вернуть его.
- `04_my_box` - `MyBox<T>`: `Deref`/`DerefMut` и `Drop` с `drop_in_place`.

**2x - продвинутое**
- `05_raw_vec` - растущий сырой буфер: удвоение ёмкости через `realloc`.
- `06_my_vec` - `MyVec<T>`: `push`/`pop`, срез через `Deref`, роняние элементов в `Drop`.

**3x - хитрое**
- `07_counting_alloc` - свой `#[global_allocator]` со счётчиками выделенной памяти.

  деструкторами.
