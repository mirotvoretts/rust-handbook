# M21 - Внутренняя изменяемость

> Часть VII "Умные указатели". Предыдущий модуль: [M20 Умные указатели](../20-smart-pointers/README.md).

## Цель модуля

Правило M07 - shared-XOR-mutable - проверяется компилятором статически: имея `&T`,
изменить `T` нельзя. Но иногда мутация под общей ссылкой логически безопасна, а
компилятор доказать это на этапе компиляции не в силах (счётчик под несколькими
владельцами, обратная ссылка на родителя, мемоизация). Внутренняя изменяемость
(interior mutability) - это семейство типов, которые **переносят проверку
shared-XOR-mutable из compile-time в runtime**, давая мутацию через `&T` ценой
динамической проверки.

После модуля вы умеете:

- [ ] объяснить, почему `&T` обычно запрещает мутацию и что такое `UnsafeCell` в основе
      всех таких типов;
- [ ] применять `Cell<T>` для `Copy`-значений: `get`/`set`/`replace`/`take` без заёмов;
- [ ] применять `RefCell<T>`: `borrow`/`borrow_mut`, понимать, что нарушение
      shared-XOR-mutable даёт панику в рантайме;
- [ ] обрабатывать конфликт заёмов без паники через `try_borrow`/`try_borrow_mut`;
- [ ] строить `Rc<RefCell<T>>` - разделяемое владение с мутацией внутри одного потока;
- [ ] разрывать циклы `Rc` через `Weak<T>`, поднимать слабую ссылку `upgrade`, читать
      `weak_count`;
- [ ] выбирать между `Cell`, `RefCell` и (позже) `Mutex` по задаче.

## 1. Почему `&T` не даёт мутацию и где это мешает

Из M07: одновременно может существовать либо много `&T`, либо ровно один `&mut T`.
Это гарантирует, что читатель никогда не видит данные в момент их изменения, - основа
безопасности и оптимизаций (компилятор считает, что за `&T` данные неизменны).

Но некоторые корректные схемы этому правилу статически не удовлетворяют:

- разделяемый счётчик под `Rc` - владельцев много (`&T`), а инкремент нужен;
- узел дерева, знающий своего родителя, - двусторонняя связь;
- ленивая инициализация или кэш внутри метода, берущего `&self`.

Внутренняя изменяемость легализует такую мутацию: тип снаружи выглядит как обычное
разделяемое значение (`&T`), но внутри разрешает менять содержимое, сам следя за тем,
чтобы правило shared-XOR-mutable не нарушилось - статически (`Cell`) или динамически
(`RefCell`).

Все такие типы построены на `UnsafeCell<T>` - единственном в языке легальном способе
получить `&mut T` из `&T`. `Cell`/`RefCell` - безопасные обёртки над ним, добавляющие
свою дисциплину доступа.

## 2. `Cell<T>`: замена значения целиком

`Cell<T>` не выдаёт ссылок на своё содержимое - он позволяет только **заменить значение
целиком**. Раз ссылки наружу не уходят, никакого конфликта заёмов быть не может, и
проверка не нужна вовсе.

```rust
use std::cell::Cell;

let c = Cell::new(5);
c.set(10);                 // положить новое значение через &Cell
let old = c.replace(20);   // заменить, вернув прежнее: old == 10
let now = c.get();         // прочитать копию: now == 20 (нужен T: Copy)
let taken = c.take();      // забрать, оставив Default::default()
```

- `get` требует `T: Copy` (возвращает копию). `set`/`replace`/`take` - для любого `T`.
- Внутри `Cell` нет счётчиков и блокировок - это просто `UnsafeCell` плюс запрет на
  выдачу внутренних ссылок. Дёшево, но применимо, когда достаточно менять значение
  целиком.
- `Cell` не `Sync`: делить его между потоками нельзя.

Идиома: маленькое `Copy`-состояние под общей ссылкой (флаги, счётчики, id).

## 3. `RefCell<T>`: заём, проверяемый в рантайме

`RefCell<T>` даёт настоящие ссылки внутрь - `&T` и `&mut T`, - но следит за правилом
shared-XOR-mutable **во время выполнения**, а не компиляции:

```rust
use std::cell::RefCell;

let c = RefCell::new(vec![1, 2, 3]);

c.borrow_mut().push(4);           // &mut внутрь: временный эксклюзивный заём
let len = c.borrow().len();       // & внутрь: разделяемый заём
```

- `borrow()` возвращает `Ref<T>` (умный указатель, разыменуется в `&T`), `borrow_mut()`
  возвращает `RefMut<T>` (в `&mut T`). Пока такой guard жив, счётчик заёмов внутри
  `RefCell` изменён; при его drop счётчик возвращается.
- Инвариант тот же: сколько угодно `Ref` **или** ровно один `RefMut`. Нарушение -
  **паника** `already borrowed` / `already mutably borrowed`:

```rust
let a = c.borrow_mut();
let b = c.borrow();               // [!] panic: BorrowError - уже есть активный &mut
```

- Плата за гибкость - счётчик заёмов и возможность паники. Ошибку алиасинга вы получаете
  не от компилятора, а как падение теста/программы, поэтому держите guard-ы как можно
  короче (не тяните `borrow_mut()` в отдельную переменную без нужды).

`RefCell` тоже не `Sync` и живёт в пределах одного потока. Многопоточный аналог -
`Mutex`/`RwLock` (M23).

## 4. Без паники: `try_borrow` / `try_borrow_mut`

Когда конфликт заёма возможен и ронять программу нельзя, используйте не-паникующие
варианты - они возвращают `Result`:

```rust
use std::cell::RefCell;

let c = RefCell::new(1);
match c.try_borrow_mut() {
    Ok(mut v) => *v += 1,
    Err(_)    => { /* сейчас занято, отложим */ }
}
```

- `try_borrow() -> Result<Ref<T>, BorrowError>`,
  `try_borrow_mut() -> Result<RefMut<T>, BorrowMutError>`.
- Это способ **опросить** состояние заёма, не рискуя паникой: удобно в реэнтерабельном
  коде, где метод может быть вызван повторно, пока внешний вызов держит заём.

## 5. `Rc<RefCell<T>>`: разделяемая мутация в одном потоке

`Rc<T>` (M20) даёт много владельцев, но только `&T`. `RefCell<T>` даёт мутацию через
`&T`, но одного владельца. Композиция `Rc<RefCell<T>>` объединяет оба свойства:
**несколько владельцев одного изменяемого значения** в пределах потока.

```rust
use std::rc::Rc;
use std::cell::RefCell;

let shared = Rc::new(RefCell::new(0));
let a = Rc::clone(&shared);       // вторая ручка на то же значение
let b = Rc::clone(&shared);

*a.borrow_mut() += 1;             // мутация через одну ручку
*b.borrow_mut() += 10;           // ... видна через любую другую
assert_eq!(*shared.borrow(), 11);
assert_eq!(Rc::strong_count(&shared), 3);
```

Читайте тип "изнутри наружу": `RefCell` даёт изменяемость, `Rc` - разделяемость.
Это рабочая лошадь односвязных/графовых структур с общими изменяемыми узлами
(`Rc<RefCell<Node>>`). Порядок обёрток важен: `Rc<RefCell<T>>` - общий изменяемый узел;
`RefCell<Rc<T>>` - изменяемая ссылка на разделяемое неизменяемое значение.

## 6. `Weak<T>`: ссылка, не удерживающая жизнь

Из M20: два `Rc`, ссылающихся друг на друга, образуют цикл - `strong_count` никогда не
дойдёт до нуля, память утечёт. `Weak<T>` - **слабая** ссылка на данные `Rc`: она не
увеличивает `strong_count` и не продлевает жизнь значения.

```rust
use std::rc::{Rc, Weak};

let strong = Rc::new(5);
let weak: Weak<i32> = Rc::downgrade(&strong);   // получить Weak из Rc

assert_eq!(Rc::strong_count(&strong), 1);
assert_eq!(Rc::weak_count(&strong), 1);

// чтобы воспользоваться данными, Weak надо поднять до Rc:
if let Some(rc) = weak.upgrade() {              // Some, пока значение живо
    assert_eq!(*rc, 5);
}

drop(strong);
assert!(weak.upgrade().is_none());              // значение умерло -> None
```

- `Rc::downgrade(&rc)` создаёт `Weak`; `weak.upgrade()` возвращает `Option<Rc<T>>`:
  `Some`, пока жив хоть один сильный владелец, иначе `None`.
- Значение освобождается, когда `strong_count` доходит до 0, **даже если** есть живые
  `Weak` (сам блок памяти под счётчики держится, пока не уйдут и слабые, но `T` уже
  уничтожен).
- Смысл: `Weak` выражает "знаю про объект, но не владею им" - ровно то, что нужно для
  обратных ссылок.

## 7. Разрыв циклов слабой ссылкой

Правило для двусторонних связей: **владеющее** направление держите на `Rc` (сильное),
**обратное** - на `Weak` (слабое). Тогда сильных циклов не возникает и всё корректно
освобождается.

Классический пример - дерево, где родитель владеет детьми, а ребёнок знает родителя:

```rust
use std::rc::{Rc, Weak};
use std::cell::RefCell;

struct Node {
    value: i32,
    parent: RefCell<Weak<Node>>,        // вверх - слабая: не владеем родителем
    children: RefCell<Vec<Rc<Node>>>,   // вниз - сильная: владеем детьми
}

let leaf = Rc::new(Node {
    value: 3,
    parent: RefCell::new(Weak::new()),
    children: RefCell::new(vec![]),
});
let branch = Rc::new(Node {
    value: 5,
    parent: RefCell::new(Weak::new()),
    children: RefCell::new(vec![Rc::clone(&leaf)]),
});
*leaf.parent.borrow_mut() = Rc::downgrade(&branch);   // связь вверх - слабая

// подъём к родителю через upgrade:
let up = leaf.parent.borrow().upgrade().map(|p| p.value);
assert_eq!(up, Some(5));

// branch держит leaf сильно (strong 2), leaf держит branch слабо (strong 1):
assert_eq!(Rc::strong_count(&branch), 1);
assert_eq!(Rc::strong_count(&leaf), 2);
```

Если бы `parent` тоже был `Rc<Node>`, `branch` и `leaf` держали бы друг друга сильно -
классическая утечка. `Weak` рвёт цикл: удаление `branch` уронит его `strong_count` в 0,
`leaf.parent.upgrade()` начнёт возвращать `None`.

## 8. Что выбрать

- `Cell<T>` - меняю значение целиком, `T: Copy` или дешёвый; ссылки внутрь не нужны.
  Нулевая цена проверки.
- `RefCell<T>` - нужны `&`/`&mut` внутрь (мутирую поле большой структуры, зову методы).
  Цена - счётчик заёмов и риск паники.
- `Rc<RefCell<T>>` - несколько владельцев одного изменяемого значения в одном потоке.
- `Weak<T>` - обратная/некритичная ссылка, не удерживающая жизнь; разрыв циклов.
- Пересекает границу потока - не это семейство: нужен `Mutex`/`RwLock`/`Arc` (M23).
  `Cell`/`RefCell`/`Rc` не `Send`/`Sync` намеренно.

## 9. Типовые грабли

```rust
// 1. Два активных заёма из RefCell - паника в рантайме, а не ошибка компиляции
let c = RefCell::new(0);
let a = c.borrow_mut();
let b = c.borrow_mut();     // [!] panic: already mutably borrowed

// 2. Долго живущий guard блокирует другие заёмы
let g = c.borrow_mut();     // держится до конца области видимости
some_call(&c);              // [!] panic, если внутри тоже berёт заём -> дропни g раньше

// 3. Cell::get требует Copy
let s = Cell::new(String::from("x"));
let v = s.get();            // [!] String: !Copy -> используй take/replace/into_inner

// 4. Забыли, что Weak не держит значение
let w = Rc::downgrade(&Rc::new(1));  // временный Rc умер сразу
assert!(w.upgrade().is_none());      // uz None: сильных владельцев нет

// 5. Обратная ссылка через Rc вместо Weak = цикл и утечка
// parent: Rc<Node> + children: Rc<Node> -> взаимное удержание, drop не сработает
```
