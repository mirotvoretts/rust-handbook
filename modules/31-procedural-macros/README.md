# M31 - Процедурные макросы

> Часть X "Метапрограммирование". Предыдущий модуль: [M30 декларативные макросы](../30-declarative-macros/README.md).

## Цель модуля

Декларативный `macro_rules!` из [M30](../30-declarative-macros/README.md) сопоставляет ввод с
образцами и подставляет заранее записанное тело. Его выразительность ограничена грамматикой
образцов: он не умеет считать, ветвиться по содержимому типа, читать имена полей структуры или
формировать сообщение об ошибке с указанием на конкретный токен. Процедурный макрос снимает эти
ограничения. Это не набор правил, а обычная функция на Rust: она получает на вход поток токенов
(`TokenStream`) и возвращает поток токенов, а между этими двумя точками выполняется произвольный
код - с циклами, условиями, разбором синтаксического дерева и генерацией нового кода.

Ключевое отличие от `macro_rules!` - процедурный макрос компилируется *отдельно*, в специальный
крейт с типом `proc-macro`, и загружается компилятором как плагин на этапе разбора крейта, который
его использует. Поэтому proc-macro крейт не может экспортировать ничего, кроме макросов, и не может
вызывать собственные макросы у себя в `src/`.

Процедурные макросы бывают трёх видов, и все три разбираются в модуле:

- *derive* (`#[derive(MyTrait)]`) - порождают *дополнительный* код рядом с помеченным типом
  (обычно impl-блок), сам тип оставляют нетронутым;
- *атрибутные* (`#[my_attr] fn ...`) - получают помеченный элемент и *заменяют* его на новый,
  могут менять сигнатуру, тело, оборачивать;
- *функциональные* (`my_macro!(...)`) - вызываются как `macro_rules!`, но тело - произвольный код.

Рабочая связка - три крейта: `proc-macro2` (переносимый тип токенов), `syn` (разбор токенов в AST)
и `quote` (сборка токенов из AST через шаблоны). Модуль учит читать вход `syn`-типами, строить
выход `quote!`, аккуратно возвращать ошибки компиляции и понимать, почему всё это работает именно
так.

После модуля вы умеете:

- [ ] заводить `proc-macro` крейт (`[lib] proc-macro = true`) с зависимостями `syn`/`quote`/
      `proc-macro2` и понимать, чем он ограничен;
- [ ] писать derive-макрос: разбирать `DeriveInput`, доставать имя типа и поля, генерировать
      impl через `quote!`;
- [ ] интерполировать переменные (`#name`) и разворачивать повторения (`#(...)*`) в `quote!`;
- [ ] писать атрибутный макрос, меняющий сигнатуру и тело функции (`ItemFn`);
- [ ] писать функциональный макрос с собственным разбором ввода;
- [ ] возвращать ошибки через `syn::Error::to_compile_error`, привязывая их к нужному `Span`;
- [ ] объяснять роль `proc-macro2` и разницу между `proc_macro::TokenStream` и
      `proc_macro2::TokenStream`.

## 1. Процедурный макрос против декларативного

`macro_rules!` - это сопоставление с образцом: компилятор ищет подходящее правило и подставляет
заранее записанный шаблон. Всё, что макрос "знает", выражено образцами, а всё, что он порождает, -
записано в теле руками. Он не выполняет вычислений: нельзя перебрать поля структуры, посчитать их,
сравнить строки, сходить в цикл.

Процедурный макрос - это функция, выполняемая компилятором во время компиляции. Её сигнатура в
самом общем виде такова:

```rust,ignore
fn my_macro(input: TokenStream) -> TokenStream
```

На входе - токены (для derive это токены помеченного типа, для функционального - содержимое
скобок вызова), на выходе - токены, которые компилятор вставит в программу и продолжит
компилировать как обычный код. Между входом и выходом - любой Rust-код. Отсюда мощь: макрос может
разобрать вход в дерево, проанализировать его и синтезировать сколь угодно сложный результат.

Плата - сложность и стоимость. Proc-macro крейт нужно скомпилировать в отдельный плагин прежде,
чем скомпилируется его пользователь; ошибки в макросе всплывают как ошибки в чужом коде; отладка
идёт по сгенерированному тексту. Правило выбора: если хватает `macro_rules!` (переменная арность,
простая генерация по образцу) - берут его; процедурный достают, когда нужен анализ содержимого
(поля, типы, имена), сложная логика генерации или качественные сообщения об ошибках с указанием
на токен. Обзор: <https://doc.rust-lang.org/reference/procedural-macros.html>.

## 2. Крейт proc-macro

Процедурные макросы живут в отдельном крейте, помеченном в `Cargo.toml`:

```toml
[lib]
proc-macro = true

[dependencies]
proc-macro2 = "1"
quote = "1"
syn = { version = "2", features = ["full"] }
```

Флаг `proc-macro = true` меняет природу крейта: он компилируется в динамический плагин для
компилятора, а не в обычную библиотеку. Из этого следуют жёсткие ограничения:

- крейт может экспортировать *только* макросы (функции с атрибутами `#[proc_macro]`,
  `#[proc_macro_derive]`, `#[proc_macro_attribute]`); обычные `pub fn`/`pub struct` наружу не
  видны;
- крейт не может использовать собственные макросы в своём `src/` (плагин к моменту компиляции
  собственного кода ещё не готов). Поэтому тесты и примеры для proc-macro крейта пишут в `tests/`
  или в отдельном крейте - это уже *другой* крейт, который зависит от нашего и потому может
  вызывать его макросы;
- поэтому тип `proc_macro::TokenStream` (см. раздел 3) доступен только внутри такого крейта.

Тесты в этом модуле лежат в `tests/tests.rs` каждого упражнения - отдельном крейте, где макросы
уже можно применять к тестовым структурам.

## 3. TokenStream и `proc-macro2`

Компилятор общается с макросом через тип `proc_macro::TokenStream` - последовательность token
tree (идентификаторы, литералы, пунктуация, скобочные группы). Этот тип живёт в крейте
`proc_macro`, встроенном в компилятор, и потому доступен *только* внутри proc-macro крейта: за его
пределами (в обычной библиотеке, в юнит-тесте) им пользоваться нельзя.

Это неудобно: логику разбора и генерации хочется тестировать и переиспользовать вне плагина.
Решение - крейт `proc-macro2`, который даёт тип `proc_macro2::TokenStream` с тем же смыслом, но
доступный где угодно. `syn` и `quote` работают именно с `proc_macro2::TokenStream`. Типичная
обвязка макроса конвертирует один тип в другой на границе:

```rust,ignore
use proc_macro::TokenStream;

#[proc_macro_derive(Hello)]
pub fn derive_hello(input: TokenStream) -> TokenStream {
    // input: proc_macro::TokenStream -> proc_macro2 через syn::parse
    let ast: syn::DeriveInput = syn::parse(input).unwrap();
    let expanded: proc_macro2::TokenStream = build(&ast); // работаем в proc_macro2
    expanded.into()   // proc_macro2::TokenStream -> proc_macro::TokenStream на выходе
}
```

Граница `proc_macro <-> proc_macro2` проходит по краям функции: приняли, сразу ушли в мир
`syn`/`quote`/`proc_macro2`, в конце `.into()` обратно. Внутри `build` тип `proc_macro` уже не
упоминается, а значит `build` можно вынести, протестировать и переиспользовать. Каждый token
несёт `Span` - позицию в исходнике, по которой компилятор рисует подчёркивание в сообщениях;
о нём в разделе 8. Разбор темы: <https://docs.rs/proc-macro2>.

## 4. `syn`: разбор токенов в AST

Разбирать `TokenStream` вручную мучительно. Крейт `syn` содержит парсер грамматики Rust и типы
AST для всех конструкций: `syn::DeriveInput` (тип с атрибутами - вход derive-макроса),
`syn::ItemFn` (функция целиком), `syn::Expr`, `syn::Type`, `syn::Ident` и десятки других.

Для derive макроса на вход приходит `DeriveInput` - разобранное объявление типа:

```rust,ignore
let ast: syn::DeriveInput = syn::parse(input).unwrap();

let name = &ast.ident;   // имя типа: Ident

// поля именованной структуры:
let fields = match &ast.data {
    syn::Data::Struct(syn::DataStruct {
        fields: syn::Fields::Named(named), ..
    }) => &named.named,   // Punctuated<Field, Comma> - список полей
    _ => panic!("ожидается структура с именованными полями"),
};

for f in fields {
    let ident: &syn::Ident = f.ident.as_ref().unwrap();  // имя поля
    let ty: &syn::Type = &f.ty;                          // тип поля
}
```

`ast.data` - это enum `Data::Struct | Data::Enum | Data::Union`; у структуры поля бывают
`Fields::Named` (обычные `{ x: T }`), `Fields::Unnamed` (кортежные `(T, U)`) или `Fields::Unit`.
Для функционального и атрибутного макроса разбирают другие типы (`ItemFn`, произвольное выражение,
собственную грамматику через `syn::parse::Parse`). Список типов и макрос `parse_macro_input!`
(удобная обёртка над `syn::parse`, сама превращающая ошибку разбора в `compile_error`):
<https://docs.rs/syn>.

## 5. `quote`: генерация токенов

Обратная задача - собрать `TokenStream` из кусочков. Крейт `quote` даёт макрос `quote!`, который
пишется как обычный Rust-код-шаблон, а `#`-интерполяция подставляет переменные:

```rust,ignore
use quote::quote;

let name = &ast.ident;  // например, Ident "Point"

let expanded = quote! {
    impl #name {
        fn type_name() -> &'static str {
            stringify!(#name)
        }
    }
};
// -> impl Point { fn type_name() -> &'static str { stringify!(Point) } }
```

`#name` подставляет значение переменной `name` как токены (works для всего, что реализует
`ToTokens`: `Ident`, `Type`, литералы, другие `TokenStream`). Повторения записываются как в
`macro_rules!`, но с `#`:

```rust,ignore
let field_names = fields.iter().map(|f| f.ident.as_ref().unwrap());

let expanded = quote! {
    impl #name {
        fn fields() -> Vec<&'static str> {
            vec![ #( stringify!(#field_names) ),* ]
        }
    }
};
```

`#( ... )*` разворачивает тело по итератору `field_names`; несколько итераторов под одним
повторением идут синхронно, попарно (как синхронные метапеременные в `macro_rules!`). Внутри
`quote!` можно вкладывать `quote!` и собирать результат из фрагментов - это обычные значения типа
`proc_macro2::TokenStream`. Полезен `format_ident!` для сборки нового идентификатора из
существующего (`format_ident!("get_{}", field)`). Справка: <https://docs.rs/quote>.

## 6. Три вида макросов

Вид макроса задаётся атрибутом над экспортируемой функцией.

**Derive** порождает *дополнительный* код рядом с типом, сам тип не трогает:

```rust,ignore
#[proc_macro_derive(Builder)]
pub fn derive_builder(input: TokenStream) -> TokenStream { /* ... */ }
```

Функция получает токены помеченного типа (`DeriveInput`) и возвращает *новые* элементы (обычно
impl-блоки), которые добавляются в модуль. Исходный `struct` остаётся как был. Derive может
объявлять *вспомогательные атрибуты* (helper attributes) - метки на полях, которые сам же читает:
`#[proc_macro_derive(Builder, attributes(builder))]` разрешает писать `#[builder(...)]` на полях.

**Атрибутный** макрос *заменяет* помеченный элемент:

```rust,ignore
#[proc_macro_attribute]
pub fn wrap_result(attr: TokenStream, item: TokenStream) -> TokenStream { /* ... */ }
```

Здесь два входа: `attr` - токены в скобках самого атрибута (`#[wrap_result(foo)]` -> `attr` это
`foo`), `item` - весь помеченный элемент (функция, структура). Возвращённый `TokenStream`
*встаёт на место* исходного элемента, поэтому атрибутный макрос может менять сигнатуру, оборачивать
тело, добавлять поля.

**Функциональный** макрос вызывается как `macro_rules!`, но внутри - произвольный код:

```rust,ignore
#[proc_macro]
pub fn make_answer(input: TokenStream) -> TokenStream { /* ... */ }
// вызов: make_answer!(...)
```

На вход - токены между скобками вызова, на выход - код, который встаёт на место вызова. В отличие
от `macro_rules!`, разбор ввода полностью на макросе (`syn::parse`, собственная грамматика).
Сводка по трём видам: <https://doc.rust-lang.org/reference/procedural-macros.html>.

## 7. Пример целиком: маленький derive

Соберём derive `TypeName`, добавляющий типу метод `type_name`, возвращающий имя типа строкой:

```rust,ignore
use proc_macro::TokenStream;
use quote::quote;
use syn::{parse_macro_input, DeriveInput};

#[proc_macro_derive(TypeName)]
pub fn derive_type_name(input: TokenStream) -> TokenStream {
    let ast = parse_macro_input!(input as DeriveInput);
    let name = &ast.ident;

    let expanded = quote! {
        impl #name {
            pub fn type_name() -> &'static str {
                stringify!(#name)
            }
        }
    };

    expanded.into()
}
```

Применение в другом крейте:

```rust,ignore
#[derive(TypeName)]
struct Widget;

assert_eq!(Widget::type_name(), "Widget");
```

`parse_macro_input!` разбирает вход и, если разбор не удался, сам возвращает из функции
`compile_error` с правильным span - руками писать `match` на ошибку не нужно. `stringify!` -
встроенный макрос, превращающий токен в строковый литерал уже во время окончательной компиляции.

## 8. Ошибки и `Span`

Макрос обязан сообщать об ошибках так, чтобы компилятор показал внятное подчёркивание в исходнике
пользователя, а не паниковал. Механизм - `syn::Error`, который умеет превращаться в токены
`compile_error!`:

```rust,ignore
return syn::Error::new_spanned(
    &field.ty,                       // к чему привязать сообщение
    "поле не может иметь такой тип", // текст
).to_compile_error().into();
```

`Error::new_spanned(tokens, msg)` берёт `Span` у переданных токенов - компилятор подчеркнёт именно
их. `to_compile_error()` даёт `proc_macro2::TokenStream` с раскрытием в `compile_error!(msg)`; его
возвращают вместо нормального кода. Разница со `panic!`: паника в макросе тоже прерывает
компиляцию, но выводит сообщение без привязки к месту и с пугающим "internal error"-обрамлением;
`compile_error` через span указывает точно на проблемный токен - так и надо в рабочих макросах.

`Span` - это позиция в исходнике. У сгенерированного токена span по умолчанию "макросовый"
(`Span::call_site()` в стабильном Rust) - ошибки в нём привязываются к месту вызова. Чтобы
диагностика указывала на конкретный кусок ввода пользователя, span берут у соответствующего
`syn`-узла (как `new_spanned` выше). Тонкости гигиены и span в стабильном/нестабильном Rust:
<https://doc.rust-lang.org/proc_macro/struct.Span.html>.

## 9. Типовые грабли

```text
1. proc-macro крейт экспортирует ТОЛЬКО макросы и не может вызывать свои же макросы в src/.
   Тесты и примеры - в tests/ или в отдельном крейте-потребителе.

2. Два разных TokenStream: proc_macro::TokenStream (только внутри плагина, на границах функции)
   и proc_macro2::TokenStream (для syn/quote, переносимый). Конверсия - .into() / syn::parse.

3. panic! в макросе прерывает компиляцию без привязки к месту. Для ошибок - syn::Error +
   to_compile_error() с нужным span (new_spanned), тогда компилятор подчеркнёт токен.

4. #name в quote! подставляет ToTokens-значение. Для нового идентификатора из старого -
   format_ident!("get_{}", field), а не форматирование строкой (строка станет строковым литералом,
   а не идентификатором).

5. Fields::Named / Unnamed / Unit - три формы полей. Обработать не тот вариант (или enum вместо
   struct) без явной ветки -> паника на unwrap. Проверять ast.data и возвращать compile_error.

6. Синхронные повторения в quote! (#(...)* по нескольким итераторам) должны быть равной длины,
   иначе паника при раскрытии. Итераторы часто одноразовые - не переиспользовать после первого #(...).

7. derive НЕ меняет помеченный тип, только добавляет код рядом. Менять сам элемент умеет только
   атрибутный макрос (он заменяет элемент своим выводом).

8. Медленная компиляция: syn с features=["full"] и quote тянут заметную сборку. Для derive часто
   хватает syn без "full"; "full" нужен для разбора выражений/функций (ItemFn, Expr).
```

## Упражнения

Решайте по порядку, ярусами. В каждом крейте: условие в `src/lib.rs`, тесты в `tests/tests.rs`
(менять нельзя). Запуск: `cargo test -p ex-31-NN-...`. Каждое упражнение - `proc-macro` крейт
(`[lib] proc-macro = true`); тесты лежат в `tests/` (отдельный крейт) и применяют макрос к своим
типам. Заглушка макроса разворачивается в `compile_error!`, поэтому тест-крейт не компилируется,
пока макрос не реализован, - это ожидаемо (упражнение решено, когда крейт собрался и тесты зелёные).

**0x - синтаксис**
- `01_make_answer` - функциональный `make_answer!()`: порождает `fn answer() -> u32 { 42 }`,
  минимальный `#[proc_macro]` + `quote!`.
- `02_hello_derive` - `#[derive(Hello)]`: метод `hello(&self) -> String` с именем типа, базовый
  разбор `DeriveInput`.

**1x - базовое**
- `03_field_names` - `#[derive(FieldNames)]`: `field_names() -> Vec<&'static str>` со списком
  имён полей, перебор `Fields::Named`.
- `04_getters` - `#[derive(Getters)]`: геттер `get_<поле>(&self) -> &Ty` на каждое поле,
  повторения в `quote!` + `format_ident!`.

**2x - продвинутое**
- `05_wrap_result` - атрибутный `#[wrap_result]`: переписывает `fn f(..) -> T` в `-> Result<T,
  String>`, оборачивая тело в `Ok`; разбор и правка `ItemFn`.
- `06_builder` - `#[derive(Builder)]`: классический builder с обязательными полями, `build()`
  возвращает `Result<T, String>`.

**3x - хитрое**
- `07_builder_optional` - `#[derive(Builder)]` с поддержкой `Option<T>`-полей как необязательных:
  разбор типа поля, определение обёртки `Option`, разная генерация для обязательных и опциональных
  полей.
</content>
