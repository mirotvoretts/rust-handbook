# M29 - FFI: интерфейс с C

> Часть IX "Небезопасность, память, FFI". Предыдущий модуль: [M28 свои коллекции на unsafe](../28-custom-collections/README.md).

## Цель модуля

FFI (Foreign Function Interface) - это способ, которым Rust вызывает код на других языках
и отдаёт свой код им. На практике "другой язык" почти всегда означает C: у C нет своей
рантайм-магии, зато есть стабильный двоичный интерфейс (ABI), к которому умеют
подключаться все остальные. Через C-ABI Rust дотягивается до операционной системы,
системных библиотек (libc, OpenSSL, SQLite) и до легаси-кода, который никто не будет
переписывать.

Граница FFI - это место, где исчезают гарантии компилятора. По ту сторону нет borrow
checker, нет времён жизни, нет проверки типов: есть только соглашение о том, как разложены
аргументы, кто владеет памятью и что означает возвращаемое число. Весь модуль - про то,
как аккуратно держать это соглашение с обеих сторон: объявлять и вызывать функции C,
экспортировать функции Rust под C-ABI, передавать через границу строки, структуры и
владение, ловить панику, чтобы она не разрушила чужой стек, и подключать функции-обратные
вызовы (callbacks).

Модуль опирается на M26 (`unsafe`, сырые указатели, инварианты) и M27 (`repr(C)`, раскладка
в памяти): FFI - это их прямое применение. Почти каждый вызов через границу `unsafe`, потому
что за корректность отвечает программист, а не компилятор.

После модуля вы умеете:

- [ ] объявлять внешние функции в `extern "C"` блоке и вызывать их из `unsafe`, используя
      C-типы из `std::os::raw` (`c_int`, `c_char`, `c_void`);
- [ ] экспортировать функции Rust под C-ABI через `#[no_mangle] pub extern "C" fn` и
      понимать, зачем нужны `#[repr(C)]` и отключение name mangling;
- [ ] передавать строки через границу (`CString`/`CStr`, нулевой терминатор, владение);
- [ ] отдавать и принимать владение кучей через `Box::into_raw`/`from_raw` и паттерн
      "непрозрачный указатель" (opaque handle);
- [ ] не допускать разворачивания паники через границу FFI с помощью `catch_unwind`;
- [ ] описывать `#[repr(C)] union` и type punning; читать поля union из `unsafe`;
- [ ] передавать в C функции-обратные вызовы (`extern "C" fn` указатели) и протаскивать
      состояние через `void*`-контекст.

## 1. Зачем FFI и что такое ABI

Компилируя вызов функции, компилятор должен решить массу низкоуровневых вопросов: в каких
регистрах и в каком порядке лежат аргументы, кто чистит стек, как возвращается результат,
как звучит имя функции в объектном файле. Набор этих правил - *ABI* (Application Binary
Interface). У каждого языка своя внутренняя ABI, и у Rust она *нестабильна*: между версиями
компилятора раскладка структур и соглашения о вызовах могут меняться. Поэтому напрямую
слинковать Rust-крейт с C нельзя - нужен общий, стабильный язык-посредник. Им служит ABI
языка C: она проста, документирована и зафиксирована на уровне платформы.

Ключевое слово `extern "ABI"` переключает соглашение о вызове. `extern "C"` означает "эта
функция вызывается по правилам C данной платформы". Оно нужно в двух направлениях:

- объявить *внешнюю* функцию, которую написали не мы (в `extern "C" { ... }` блоке), - чтобы
  Rust сгенерировал корректный вызов;
- пометить *свою* функцию (`extern "C" fn`), чтобы её можно было позвать из C.

Вторая половина соглашения - имя. Rust, как и C++, применяет *name mangling*: кодирует в
символ модуль, типы и дженерики, поэтому в объектном файле функция `add` называется как-то
вроде `_ZN3lib3add17h...`. C так не умеет и ищет символ по голому имени. Атрибут
`#[no_mangle]` отключает искажение, оставляя ровно то имя, что в исходнике. Подробный обзор -
глава "FFI" в Rustonomicon: <https://doc.rust-lang.org/nomicon/ffi.html>.

## 2. Вызов C из Rust: `extern` блок и C-типы

Чтобы позвать функцию C, её сигнатуру объявляют в блоке `extern "C" { ... }`. Тело не
пишут - его предоставит линковщик. Сам вызов всегда `unsafe`: компилятор не видит тело
внешней функции и верит объявленной сигнатуре на слово; ошибка в типах не будет замечена и
приведёт к UB.

```rust
use std::os::raw::c_int;

extern "C" {
    // int abs(int);  из стандартной библиотеки C
    fn abs(input: c_int) -> c_int;
}

fn magnitude(x: c_int) -> c_int {
    // SAFETY: abs тотальна для любого c_int, кроме c_int::MIN (в C это UB);
    // вызывающий обязан не передавать MIN.
    unsafe { abs(x) }
}
```

Типы по обе стороны обязаны совпадать *побайтово*, поэтому на границе используют не родные
`i32`/`usize`, а C-типы из `std::os::raw` (они же в `std::ffi`): `c_int`, `c_uint`, `c_long`,
`c_char`, `c_void` и прочие. Это псевдонимы платформенно-зависимой ширины: `c_int` почти
везде `i32`, а `c_long` - `i64` на 64-битном Linux, но `i32` на Windows. Писать `c_long`
вместо `i64` - значит остаться переносимым.

Функции стандартной библиотеки C (`abs`, `strlen`, `qsort`, ...) доступны без единой строчки
настройки: рантайм Rust и так линкуется с libc, символы находятся сами. Для *сторонней*
библиотеки линковку указывают атрибутом `#[link(name = "...")]` над блоком (раздел 8).
Справка по внешним блокам: <https://doc.rust-lang.org/reference/items/external-blocks.html>.

## 3. Строки через границу: `CString` и `CStr`

Строка Rust (`String`/`&str`) и строка C - разные вещи. У Rust строка это указатель +
длина, содержимое в UTF-8, нулевой байт внутри разрешён. Строка C - это указатель на массив
байт, завершённый нулевым байтом (`\0`), а длина вычисляется поиском этого нуля. Просто
передать `&str` в C нельзя: там нет длины и нет терминатора.

Мост между мирами - пара типов из `std::ffi`:

- `CString` - *владеющая* строка C: гарантирует завершающий ноль и отсутствие нулей внутри.
  Строится из `&str`/`Vec<u8>` через `CString::new`, возвращающий `Err`, если внутри есть
  нулевой байт. Метод `.as_ptr()` даёт `*const c_char` для передачи в C.
- `CStr` - *заимствованный* срез строки C (аналог `&str` для `String`). Строится из сырого
  указателя через `CStr::from_ptr` (unsafe: доверяем, что там валидная C-строка).

```rust
use std::ffi::{CStr, CString};
use std::os::raw::c_char;

extern "C" {
    fn strlen(s: *const c_char) -> usize;
}

let owned = CString::new("hello").expect("нет нулей внутри");
// SAFETY: as_ptr даёт валидный нуль-терминированный указатель, живой пока жив owned.
let len = unsafe { strlen(owned.as_ptr()) };
assert_eq!(len, 5);
```

Главная ловушка - время жизни. `owned.as_ptr()` валиден, только пока жив сам `owned`;
типичная ошибка - `CString::new(s).unwrap().as_ptr()`, где временный `CString` умирает в
конце выражения, оставляя висячий указатель. `CString` должен пережить вызов. Обратно, из
`*const c_char`, полученного от C, строку читают через `CStr::from_ptr(ptr).to_str()` (или
`to_string_lossy`). Документация: <https://doc.rust-lang.org/std/ffi/struct.CString.html>.

## 4. Экспорт Rust в C: `#[no_mangle] extern "C" fn`

Обратное направление: сделать функцию Rust вызываемой из C. Нужны три пометки - `extern "C"`
для C-ABI, `#[no_mangle]` для сохранения имени и `pub` для видимости. Сигнатура должна
оперировать только FFI-совместимыми типами (числа, сырые указатели, `#[repr(C)]` типы), но не
`&str`, `String`, `Vec`, кортежами - у них нет стабильной раскладки.

```rust
use std::os::raw::c_int;

#[no_mangle]
pub extern "C" fn add(a: c_int, b: c_int) -> c_int {
    a.wrapping_add(b)
}

// Массив C приходит как указатель + длина; собираем срез вручную.
/// # Safety
/// `ptr` ведёт на `len` инициализированных `i32` в одном выделении.
#[no_mangle]
pub unsafe extern "C" fn sum(ptr: *const i32, len: usize) -> i64 {
    if ptr.is_null() {
        return 0;
    }
    let slice = std::slice::from_raw_parts(ptr, len);
    slice.iter().map(|&x| x as i64).sum()
}
```

C не знает про срезы, поэтому массив всегда приходит парой "указатель + длина", и на
Rust-стороне её превращают в срез через `slice::from_raw_parts` (unsafe: за валидность и
длину отвечает вызывающий). Функция, принимающая сырые указатели, обычно помечается `unsafe`,
чтобы это требование было явным в сигнатуре. Чтобы такую библиотеку можно было слинковать с
C, крейт собирают как `cdylib` или `staticlib` (`crate-type` в `Cargo.toml`), а объявления
для C-стороны либо пишут вручную в `.h`, либо генерируют инструментом `cbindgen`.

## 5. Передача владения через границу: `Box::into_raw` и opaque handle

Числа и срезы копируются, но иногда C должен *хранить* объект Rust между вызовами - например,
парсер, соединение, счётчик. Отдавать наружу структуру целиком нельзя (C не знает её
раскладки и не умеет её ронять). Идиома - *непрозрачный указатель* (opaque handle): C держит
`*mut T` как безымянный `void*`-токен и не заглядывает внутрь, а вся работа идёт через
экспортированные функции.

Ключ - передача владения кучей. `Box::into_raw(b)` отдаёт сырой указатель и *снимает* с
`Box` ответственность за освобождение: теперь память живёт, пока кто-то не позовёт
`Box::from_raw`. Тот воссоздаёт `Box`, возвращая владение в Rust, и по выходу из области
видимости роняет объект и освобождает память.

```rust
pub struct Counter {
    value: i64,
}

#[no_mangle]
pub extern "C" fn counter_new() -> *mut Counter {
    Box::into_raw(Box::new(Counter { value: 0 })) // владение уходит наружу
}

/// # Safety
/// `c` получен из `counter_new` и ещё не освобождён.
#[no_mangle]
pub unsafe extern "C" fn counter_add(c: *mut Counter, n: i64) {
    if let Some(cnt) = c.as_mut() {
        cnt.value += n;
    }
}

/// # Safety
/// `c` получен из `counter_new`; после вызова указатель невалиден.
#[no_mangle]
pub unsafe extern "C" fn counter_free(c: *mut Counter) {
    if !c.is_null() {
        drop(Box::from_raw(c)); // возвращаем владение и роняем
    }
}
```

Контракт становится ручным: на каждый `counter_new` должен приходиться ровно один
`counter_free`. Забыли - утечка; позвали дважды - double-free и UB. Это цена работы через
C-ABI: то, за чем в Rust следил `Drop`, теперь стережёт документация. `Box::into_raw`/
`from_raw`: <https://doc.rust-lang.org/std/boxed/struct.Box.html#method.into_raw>.

## 6. Паника не должна пересекать границу FFI

Паника Rust разворачивает стек (unwinding), запуская деструкторы кадр за кадром. Стек C так
устроен не бывает: у его кадров нет таблиц раскрутки, и попытка размотать сквозь них -
неопределённое поведение. Поэтому паника обязана быть *пойманной* до того, как управление
вернётся в C. Начиная с Rust 1.81, разворачивание через границу `extern "C"` по умолчанию не
UB, а немедленный `abort` процесса - безопасно, но грубо: падает вся программа.

Правильно - поймать панику внутри своей экспортированной функции и превратить её в код
ошибки, понятный C. Инструмент - `std::panic::catch_unwind`: он выполняет замыкание и
возвращает `Result`, где `Err` означает "внутри была паника".

```rust
use std::os::raw::c_int;
use std::panic::{catch_unwind, AssertUnwindSafe};

fn divide(a: i32, b: i32) -> i32 {
    if b == 0 {
        panic!("division by zero"); // паникующая Rust-логика
    }
    a / b
}

/// Возврат: 0 - успех (результат записан в `*out`), 1 - была паника.
/// # Safety
/// `out` - валидный указатель на `c_int`.
#[no_mangle]
pub unsafe extern "C" fn checked_div(a: c_int, b: c_int, out: *mut c_int) -> c_int {
    let caught = catch_unwind(AssertUnwindSafe(|| divide(a, b)));
    match caught {
        Ok(v) => {
            if !out.is_null() {
                *out = v;
            }
            0
        }
        Err(_) => 1, // панику погасили, C получает код ошибки
    }
}
```

`AssertUnwindSafe` нужен, потому что `catch_unwind` требует от замыкания `UnwindSafe` -
гарантию, что после ловли паники видимое состояние не окажется в противоречивом виде; обёртка
означает "я проверил, здесь это безопасно". Ловить панику имеет смысл только на самой границе:
внутри Rust паника - штатный механизм, и глушить её везде подряд не нужно. Про раскрутку -
"Unwinding" в Rustonomicon: <https://doc.rust-lang.org/nomicon/unwinding.html>. Про
`catch_unwind`: <https://doc.rust-lang.org/std/panic/fn.catch_unwind.html>.

## 7. `union`: наложение полей и type punning

`enum` в Rust - это *tagged union*: он помнит, какой вариант активен, и тратит на тег байты.
C-шный `union` тега не хранит: все поля лежат по одному адресу, наложенные друг на друга, а
что там сейчас записано - знает только программист. Rust умеет описывать такие union для FFI
и для приёма type punning - перечитывания одних и тех же байт как другого типа.

```rust
#[repr(C)]
union Bits32 {
    u: u32,
    f: f32,
    bytes: [u8; 4],
}

let b = Bits32 { u: 0x3f80_0000 };
// SAFETY: все три поля занимают 4 байта и валидны для любого набора бит,
// поэтому перечитывание любого из них корректно.
let as_float = unsafe { b.f };
assert_eq!(as_float, 1.0_f32); // те же байты, прочитанные как f32
```

Два правила. Первое: читать поле union - всегда `unsafe`, потому что компилятор не знает,
какой вариант был записан последним, и не может гарантировать, что байты валидны для типа
поля (для `u32`/`f32`/`[u8;4]` валиден любой набор бит, а вот, скажем, для `bool` - нет).
Второе: если поле union - тип с деструктором (`String`, `Vec`), его нужно завернуть в
`ManuallyDrop`, иначе код не скомпилируется: union не знает, какое поле ронять, и запрещает
автоматический `Drop`. `#[repr(C)]` фиксирует раскладку так, как её видит C. Справка по union:
<https://doc.rust-lang.org/reference/items/unions.html>.

## 8. Callbacks и подключение библиотек

Многие C-API принимают *функцию-обратный вызов* (callback): `qsort` берёт компаратор,
событийные циклы - обработчик. С Rust-стороны это указатель на функцию с C-ABI:
`extern "C" fn(...) -> ...` (или `Option<extern "C" fn ...>`, если C допускает null).
Важное ограничение: передать можно только `extern "C" fn` - обычную функцию или non-capturing
замыкание, но *не* замыкание, захватившее окружение: у него нет стабильного адреса и он не
раскладывается в голый указатель.

Как же протащить состояние, если захватывать нельзя? Идиома C - *userdata*: рядом с callback
API просит нетипизированный `void*`, который передаёт обработчику нетронутым. В него кладут
указатель на свой контекст, а внутри callback приводят его обратно.

```rust
use std::os::raw::{c_int, c_void};

// C-подобное API: на каждое событие зовёт cb, прокидывая userdata насквозь.
fn run_events(events: &[c_int], cb: extern "C" fn(c_int, *mut c_void), userdata: *mut c_void) {
    for &e in events {
        cb(e, userdata);
    }
}

struct Ctx {
    target: c_int,
    count: usize,
}

extern "C" fn on_event(event: c_int, userdata: *mut c_void) {
    // SAFETY: userdata - это &mut Ctx, переданный run_events; он жив на время вызова.
    let ctx = unsafe { &mut *(userdata as *mut Ctx) };
    if event == ctx.target {
        ctx.count += 1;
    }
}

let mut ctx = Ctx { target: 2, count: 0 };
run_events(&[1, 2, 2, 3], on_event, &mut ctx as *mut Ctx as *mut c_void);
assert_eq!(ctx.count, 2);
```

Для callback компаратора в `qsort` работает та же схема: comparator - `extern "C" fn`,
элементы приходят как `*const c_void` и приводятся к нужному типу. Справка по указателям на
функции: <https://doc.rust-lang.org/reference/types/function-pointer.html>.

**Подключение сторонних библиотек.** Для функций не из libc линковку задают атрибутом
`#[link(name = "foo")]` над `extern` блоком (ищет `libfoo`), а если библиотека - это C-исходник
в вашем репозитории, его компилируют build-скриптом (`build.rs`) через крейт `cc`. Писать
`extern` блоки для большого C-API руками утомительно и легко ошибиться; их автогенерирует
`bindgen` - он читает `.h` заголовки и по ним выпускает Rust-объявления. Обзорно:
<https://rust-lang.github.io/rust-bindgen/>.

## 9. Типовые грабли

```text
1. Несовпадение сигнатуры extern-блока с реальной функцией C (тип/число аргументов,
   ширина c_long): компилятор верит объявлению -> тихий UB. Сверять с прототипом C.

2. CString::new(s).unwrap().as_ptr(): временный CString умирает в конце выражения,
   указатель повисает. CString должен жить дольше вызова (связать let).

3. Забыть, что as_ptr не передаёт владение: строку/буфер нельзя ронять, пока C держит
   указатель. Время жизни отслеживать вручную.

4. Утечка или double-free вокруг into_raw/from_raw: на каждый into_raw ровно один
   from_raw. Ни разу -> утечка; дважды -> UB.

5. Паника, разворачивающаяся в C: с Rust 1.81 это abort всей программы. На границе
   ловить catch_unwind и возвращать код ошибки.

6. Чтение неактивного поля union без учёта валидности бит: для bool/char/ссылок не любой
   набор бит корректен. Пунить только в типы, валидные для любых бит.

7. Поле union с Drop без ManuallyDrop: не компилируется. Оборачивать в ManuallyDrop и
   ронять вручную.

8. Передача capturing-замыкания туда, где ждут extern "C" fn: не скомпилируется.
   Состояние протаскивать через void*-userdata.

9. Возврат &str/String/Vec/кортежа через extern "C": у них нет стабильной раскладки.
   Только числа, сырые указатели, #[repr(C)] типы.
```
