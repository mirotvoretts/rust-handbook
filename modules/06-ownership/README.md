# M06 - Владение и move-семантика

> Часть II "Владение". Предыдущий материал: struct/enum/pattern matching (M04-M05).

Понять **центральную идею Rust**: как язык освобождает память в детерминированный момент
**без сборщика мусора и без класса ошибок use-after-free / double-free** - и всё это
проверяется на этапе компиляции, не стоя ничего в рантайме.

- [ ] реализовать `Drop` и предсказать порядок вызовов;
- [ ] выбирать между move, `.clone()`, `mem::swap`/`mem::replace`, `Option::take`.

## 1. Проблема, которую решает владение

Любой язык обязан ответить на вопрос: **когда освободить память под объект?** Есть три школы:

| Подход | Кто решает | Когда | Цена |
|---|---|---|---|
| Ручное управление (C) | программист | вручную `free` | ошибки: leak, use-after-free, double-free |
| Сборка мусора (Java, Go, Python) | рантайм | *динамически* - когда объект недостижим | пауза GC, память "про запас", runtime |
| Владение (Rust, C++/RAII) | компилятор | *статически* - на выходе из области видимости | нужно доказать корректность на компиляции |

Сборщик мусора **динамически** отслеживает живые указатели и освобождает недостижимое.
Rust идёт другим путём: он **статически** вставляет освобождение в фиксированную точку кода
(конец области видимости владельца) и **запрещает** конструкции, при которых это было бы
некорректно. Отсюда лозунг: *память освобождается там, где это видно из исходника, а не
"когда-нибудь потом".*

> [!note] C++ и Rust - одна школа, разные умолчания
> RAII в C++ - тот же принцип: деструктор на выходе из блока. Разница в умолчаниях
> (см. п.5 и п.7) и в том, что Rust **доказывает** отсутствие висячих ссылок, а C++ верит
> программисту. В C++ висячий указатель - UB в рантайме; в Rust - ошибка компиляции.

## 2. Стек и куча, дерево владения

```rust
fn foo() {
    let a = 1;              // на стеке
    let b = Box::new(2);    // сам Box (указатель) - на стеке, данные (2) - в куче
}                           // на выходе: сначала дропается b (free кучи), потом a
```

```
Стек (растёт вниз):        Куча:
+--------------+           +------------+
| foo: a = 1   |           |  2         |
| foo: b *-----+----ptr--->|            |
+--------------+           +------------+
```

| | Стек | Куча |
|---|---|---|
| скорость | очень быстро (сдвиг указателя) | медленнее (аллокатор, синхронизация) |
| освобождение | автоматически при выходе из функции | явные `alloc`/`dealloc` |
| время жизни | привязано к кадру функции | произвольное |
| размер | известен на компиляции | любой |

**Ключевой инвариант Rust: у каждого значения ровно один владелец.** Значения образуют
**дерево владения** - например, `Vec<Function>`, где `Function { params: Vec<Param>,
ret: Box<Type> }`, владеет всем поддеревом. Уничтожение корня рекурсивно освобождает
всё поддерево ровно один раз.

> [!info] Сравнение раскладки в памяти (следствие философии zero-cost)
> `Vec<Point>` в Rust хранит `Point`-ы **инлайн**, подряд (один уровень косвенности).
> В Java `ArrayList<Point>` хранит **ссылки** на разбросанные по куче объекты (два уровня
> косвенности, хуже локальность кэша). Rust даёт контроль над layout - как C++, в отличие
> от языков с обязательным боксингом объектов.

## 3. Move-семантика

Наивная проблема: если память освобождается на выходе из блока, не освободим ли мы её дважды?

```rust
fn foo() {
    let x = Box::new(92);
    let y = x;              // кто освобождает - x или y?
}
```

Ответ Rust: **присваивание, передача аргумента и возврат значения тратят (move) правую часть.**
Компилятор статически отслеживает, какие переменные инициализированы:

```rust
let x = Box::new(92);      // init: x
let t = x;                 // init: t;  x теперь moved-from (недоступен)
let y = t;                 // init: y;  t теперь moved-from
// освобождает память ровно y (в конце блока)
```

Обращение к перемещённому значению - ошибка компиляции:

```rust
let spam = Box::new(92);
let eggs = spam;
println!("{}", spam);      // [!] error[E0382]: use of moved value: `spam`
```

Физически move - это **`memcpy` ровно `size_of::<T>()` байт со стека** (для `Box` - копия
указателя, 8 байт), после чего источник помечается недоступным. Move в Rust:

- **всегда** тривиален (побитовое копирование), **никогда** не запускает пользовательский код
  и **не может кинуть** (в отличие от C++ move-конструктора, который можно перегрузить);
- по умолчанию - именно move (в C++ по умолчанию **копирование**, а move надо просить `std::move`).

Передача в функцию - тоже move:

```rust
fn bar(x: Box<i32>) { /* dealloc на выходе из bar */ }

fn foo() {
    let x = Box::new(92);
    bar(x);                // владение ушло в bar
    // x здесь недоступен
}
```

Функция `drop` тривиальна - просто забирает владение и роняет объект в конце своего тела:

```rust
fn drop<T>(_value: T) {}   // доступна из прелюдии
drop(y);                   // явно уничтожить прямо сейчас
```

## 4. Аффинные типы и drop flags (теория)

Как система типов трактует использование переменной:

- **обычная** типизация - переменную можно использовать сколько угодно раз;
- **линейная** - нужно использовать **ровно один** раз;
- **аффинная** - можно использовать, но **не более одного** раза.

Rust - **аффинная** система для владеющих значений: значение либо перемещается (используется)
один раз, либо просто роняется в конце области видимости.

Что, если владение уходит по-разному в зависимости от условия, известного лишь в рантайме?

```rust
let x = Box::new(92);
let (y, z);
if condition { y = x; } else { z = x; }
// освобождает y или z - зависит от рантайма
```

Компилятор кладёт на стек **невидимый drop-флаг** (инициализирована ли переменная - "очень
маленький счётчик, только 0/1") и по нему в конце блока решает, звать ли `dealloc`. Это
единственная рантайм-цена владения, и она возникает только в таких неоднозначных случаях;
обычно всё разрешается статически и флагов нет.

## 5. `Copy`-типы против не-`Copy`

Значения, **не владеющие ресурсами** (не требующие drop), помечены трейтом `Copy`. Для них
"move" превращается в копирование, поэтому источник **остаётся доступен**:

```rust
let x = 1;
let y = x;
let z = x;                 // ok: i32 это Copy, x не потрачен
assert_eq!(y, z);
```

`Copy` можно вывести для агрегатов из `Copy`-полей:

```rust
#[derive(Clone, Copy)]
struct Point { x: f64, y: f64 }
```

> [!warning] Что принципиально НЕ может быть `Copy`
> `Box<T>`, `Vec<T>`, `String` - владеют памятью на куче и обязаны её освобождать.
> Побитовая копия дала бы **двух владельцев одного буфера** -> double-free. Поэтому для них
> есть только явный `.clone()` (глубокая копия) и move (передача единственного владения).
> `Copy` - это ровно "у типа нет деструктора и его можно дублировать байтами безопасно".

`Copy` требует `Clone` как супертрейт (`Copy: Clone`): всё, что копируется байтами, тривиально
клонируется.

## 6. `Clone`: явная глубокая копия и её цена

```rust
let xs = vec![1, 2, 3];
let ys = xs;               // move: копируются только {ptr,len,cap} со стека (24 байта),
                           //       буфер на куче общий, xs становится недоступен
let zs = ys.clone();       // clone: НОВЫЙ буфер на куче + копия элементов (дорого)
```

Философия Rust: **дорогие операции видны в коде**. Глубокая копия не случается неявно -
вы всегда пишете `.clone()`. Сравните с C++, где `std::vector<int> ys = xs;` **по умолчанию
делает глубокую копию** молча.

### Виды присваивания `xs = ys` в разных языках (ключевое сравнение)

| Язык | Что делает `xs = ys` |
|---|---|
| Python | увеличивает счётчик ссылок (оба имени - один объект) |
| Java | копирует ссылку, GC разберётся позже (оба имени - один объект) |
| C++ | **глубокая копия** объекта (по умолчанию), можно перегрузить |
| Rust | помечает `ys` как moved-from на компиляции, копирует байты со стека в рантайме |

|  | Rust move | C++ copy (умолчание) |
|---|---|---|
| что происходит | `memcpy` `size_of::<T>` байт, всегда, без кода пользователя | вызов копирующего конструктора |
| стоимость | дёшево и предсказуемо | зависит от типа, может аллоцировать/кинуть |
| глубокая копия | только явный `.clone()` | неявно |
| причина умолчания | безопасность | совместимость с C++98 |

## 7. `Drop` и RAII

`Drop` - деструктор: код, выполняемый при уничтожении значения. Вызывается **автоматически**
в конце области видимости владельца (или раньше - явным `drop(x)`), рекурсивно для полей.

```rust
struct Guard(&'static str);

impl Drop for Guard {
    fn drop(&mut self) {
        println!("освобождаю {}", self.0);
    }
}

fn main() {
    let _a = Guard("a");
    let _b = Guard("b");
}   // порядок вывода: "освобождаю b", затем "освобождаю a"
```

**Порядок drop:** локальные переменные роняются в **обратном** порядке объявления (как стек);
поля структуры - в порядке объявления. Это тот же RAII, что в C++ (`~T()` на выходе из блока),
и он лежит в основе безопасного управления любыми ресурсами: файлами, сокетами, блокировками
мьютексов (`MutexGuard`), транзакциями.

> [!tip] `Box<T>` ~= `std::unique_ptr<T>`
> Владеющий указатель на кучу, не бывает нулевым, освобождает память ровно на выходе из
> области видимости. Move у `Box` - это передача единственного владения, как у `unique_ptr`
> с его удалённым копированием.

Нельзя вызвать `.drop()` вручную как метод (иначе объект дропнулся бы дважды) - для
досрочного уничтожения есть свободная функция `std::mem::drop`.

## 8. Перемещение из-под ссылки: `swap`, `replace`, `take`

Иногда нужно **забрать** владеющее значение, имея лишь `&mut` на него (например, поле
структуры). Просто `let x = *r;` запрещён - это оставило бы `*r` moved-from, а компилятор
требует, чтобы за `&mut` всегда лежало валидное значение. Инструменты:

```rust
use std::mem;

let mut a = String::from("a");
let mut b = String::from("b");
mem::swap(&mut a, &mut b);          // обмен без клонов: a == "b", b == "a"

let old = mem::replace(&mut a, String::from("new"));   // положить новое, забрать старое

let mut opt = Some(String::from("x"));
let taken = opt.take();             // == mem::replace(&mut opt, None): taken=Some("x"), opt=None
```

Это идиоматичная замена C++-приёму "сначала сконструировать заглушку, потом `std::swap`":
здесь всё выражено через владение и без лишних аллокаций.

## 9. Тизер к M07

Мы разобрали, как значения **перемещаются** и **уничтожаются**. Но постоянно клонировать или
передавать владение туда-обратно неудобно. Следующий модуль - **заимствование** (`&`/`&mut`):
временный доступ без передачи владения и правило **shared XOR mutable**, которое ловит на
компиляции целый класс багов вроде инвалидации итератора (в C++ - UB).
