# M17 - Коллекции

> Часть VI "Коллекции, замыкания, итераторы". Предыдущий модуль: [M16 Обработка ошибок](../16-errors/README.md).

## Цель модуля

Систематически пройти `std::collections`: как устроен `Vec` (и почему он почти всегда
правильный ответ), когда нужны `VecDeque`/`BinaryHeap`, как работают `HashMap` и
`BTreeMap` и что они требуют от ключей (`Hash + Eq` против `Ord` - M13 в действии),
правда про `String`/UTF-8 и `Cow<str>` - "владей только по необходимости".

После модуля вы умеете:

- [ ] объяснить `Vec` на уровне (ptr, len, cap): амортизацию x2, `with_capacity`,
      почему `Vec::new()` не аллоцирует;
- [ ] пользоваться `retain`/`extend`/`drain`/`dedup` вместо ручных циклов;
- [ ] выбирать `HashMap` или `BTreeMap` осознанно и пользоваться **Entry API**;
- [ ] оперировать множествами: `HashSet`, пересечения/объединения;
- [ ] работать со строками без ошибок UTF-8: `chars`/`char_indices`/байты, срезы по
      границам символов;
- [ ] применять `Cow<'_, str>`, чтобы не аллоцировать без нужды;
- [ ] обосновать выбор коллекции локальностью кэша.

## 1. Почему массив побеждает: иерархия памяти

Ориентировочные задержки: L1 ~= 0.5 нс, L2 ~= 7 нс, **основная память ~= 100 нс** - в
200 раз дороже L1. Поэтому компактные непрерывные структуры (массив) на практике
бьют теоретически изящные ссылочные (связный список): процессор читает память
кэш-линиями по 64 байта и любит предсказуемый последовательный доступ.

Весь дизайн `std::collections` отсюда: `Vec` - базовая структура; `LinkedList` есть,
но почти никогда не нужен; `BTreeMap` вместо красно-чёрного дерева; `HashMap` на
open addressing вместо цепочек.

## 2. `Vec<T>`: три слова

```rust
// концептуально:
struct Vec<T> { ptr: *mut T, len: usize, cap: usize }   // 24 байта на x86-64
```

- **`len`** - сколько элементов инициализировано; **`cap`** - на сколько выделен
  буфер. Инвариант: `len <= cap`, первые `len` слотов валидны.
- **`Vec::new()` не аллоцирует** - память появляется при первом `push`. Создавать
  пустые векторы дёшево.
- **Рост x2**: при `len == cap` буфер перевыделяется вдвое (`realloc`). Каждый
  элемент переезжает в среднем O(1) раз - **амортизированный** O(1) на `push`.
  Знаете размер заранее - `Vec::with_capacity(n)` убирает все реаллокации.
- Перевыделение - это `memcpy`: move в Rust всегда тривиален (M06), никакие
  конструкторы не вызываются.

Рабочие методы поверх ручных циклов:

```rust
v.retain(|x| x % 2 == 0);        // отфильтровать на месте (один проход)
v.extend([4, 5, 6]);             // дозаписать из итерируемого
v.dedup();                       // схлопнуть СОСЕДНИЕ дубликаты
v.drain(1..3);                   // вынуть диапазон итератором (хвост сдвинется)
v.sort(); v.sort_by_key(|x| ...);
```

`Vec<T>: Deref<Target = [T]>` - все методы срезов (`iter`, `windows`, `chunks`,
`binary_search`, ...) достаются бесплатно (механика Deref - в M20).

### Родственники

- **`VecDeque<T>`** - кольцевой буфер: O(1) `push_front`/`pop_front` **и**
  `push_back`/`pop_back`. Очередь (FIFO), скользящее окно.
- **`BinaryHeap<T: Ord>`** - max-куча: `push` + `pop` максимума за O(log n).
  Очередь с приоритетом.
- **`LinkedList`** - существует; берите `Vec`/`VecDeque`, пока профилировщик не
  скажет иное (не скажет).

## 3. `HashMap<K, V>`: хеш-таблица

Требования к ключу: **`K: Hash + Eq`** (оба - derive'ятся). Устройство - **open
addressing** с SIMD-просеиванием (дизайн hashbrown, state of the art; в C++
`std::unordered_map` навсегда прибит к цепочкам гарантиями инвалидации указателей
в API). Средний O(1) на операцию, порядок обхода **не определён**.

Хеш-функция - параметр таблицы. Умолчание - **SipHash**: не самый быстрый, зато
устойчив к HashDoS (злонамеренно подобранным ключам-коллизиям). Для внутренних
структур без внешнего ввода берут быстрые хешеры (`FxHashMap` в rustc).

### Entry API

Двойной поиск ключа - code smell:

```rust
if !map.contains_key(&k) { map.insert(k, 0); }    // ищем k дважды
```

`entry` находит слот **один раз** и даёт с ним работать:

```rust
*counts.entry(word).or_insert(0) += 1;             // классика: счётчик слов
map.entry(key).or_insert_with(Vec::new).push(v);   // multimap вручную
```

## 4. `BTreeMap<K, V>`: упорядоченный словарь

Требование к ключу: **`K: Ord`**. Это B-дерево: в узле - массив из ~11 пар, что
драматически лучше для кэша, чем "один узел - один элемент" красно-чёрного дерева.
O(log n) на операцию, обход - **в порядке ключей**, есть диапазонные запросы:

```rust
let scores = BTreeMap::from([(70, "C"), (80, "B"), (90, "A")]);
scores.range(75..).next();                 // первая пара с ключом >= 75
scores.first_key_value();                  // минимальный ключ
```

Выбор: нужен порядок/диапазоны/минимум-максимум - `BTreeMap`; нужна максимальная
скорость точечных операций - `HashMap`.

`HashSet<T>`/`BTreeSet<T>` - те же структуры без значений (`BTreeSet<T>` - буквально
`BTreeMap<T, ()>`; ZST-значение не занимает места). Готовые операции:
`union`, `intersection`, `difference`, `is_subset`.

## 5. `String` и `&str`: UTF-8 всерьёз

`String` - это `Vec<u8>` с инвариантом "содержимое - валидный UTF-8"; `str` - тот же
инвариант поверх `[u8]`. UTF-8 - кодировка **переменной длины**: ASCII - 1 байт,
кириллица - 2, эмодзи - 4:

```rust
"a".len() == 1;    "ы".len() == 2;    "😀".len() == 4;   // len - БАЙТЫ
```

Следствия:

- **индексации `s[i]` нет**: i-й "символ" нельзя найти за O(1), и неясно, что такое
  символ (codepoint? графема?);
- срезы `&s[1..3]` - по **байтовым** границам; попадание внутрь символа - паника.
  Безопасно резать по границам из `char_indices`/`find`;
- итерация: `s.chars()` (по codepoint'ам), `s.bytes()` (по байтам),
  `s.char_indices()` (пары "байтовое смещение + char");
- `char` - Unicode scalar value (4 байта). Даже он не "символ" с точки зрения
  человека (буква "e с акцентом" может быть двумя codepoint'ами) - для графем нужны
  внешние крейты.

Zero-copy методы возвращают `&str` в исходную строку - без аллокаций:
`trim`, `split_whitespace`, `strip_prefix`, `find` + срез. Аллоцирующие - честно
возвращают `String`: `to_lowercase`, `replace`, `format!`.

Сравните с Java/JS: там строки - UTF-16 с O(1)-индексацией по "чару", но этот чар -
суррогатная половинка для эмодзи; ошибка та же, только спрятана глубже. Rust делает
переменную длину явной.

## 6. `Cow<'_, str>`: владей по необходимости

Функция "нормализуй строку" чаще всего **ничего не меняет** - жалко аллоцировать
копию ради возврата. `Cow` (clone-on-write) хранит либо заём, либо владение:

```rust
use std::borrow::Cow;

fn normalize(s: &str) -> Cow<'_, str> {
    if s.contains(' ') {
        Cow::Owned(s.replace(' ', "_"))   // пришлось аллоцировать
    } else {
        Cow::Borrowed(s)                  // отдаём заём - ноль аллокаций
    }
}
```

`Cow<str>: Deref<Target = str>` - читается как обычная строка; `.into_owned()`
достаёт `String` (аллоцируя только если внутри был заём). Идиома для API, где
модификация - редкий случай: парсеры, экранирование, нормализация путей.

## 7. Шпаргалка выбора

| Задача | Коллекция |
|---|---|
| последовательность, стек | `Vec<T>` (по умолчанию - всегда он) |
| очередь, дек, скользящее окно | `VecDeque<T>` |
| словарь без порядка, максимум скорости | `HashMap<K, V>` (`K: Hash + Eq`) |
| словарь с порядком/диапазонами | `BTreeMap<K, V>` (`K: Ord`) |
| множество | `HashSet<T>` / `BTreeSet<T>` |
| очередь с приоритетом | `BinaryHeap<T: Ord>` |
| текст | `String`/`&str`; редкие правки - `Cow<str>` |

## 8. Тизер к M18

`retain(|x| ...)`, `or_insert_with(Vec::new)`, `sort_by_key(|x| ...)` - всюду
замыкания, которые мы пока писали "по образцу". Следующий модуль разбирает их
устройство: скрытая структура с окружением, тройка `Fn`/`FnMut`/`FnOnce`, вывод
способа захвата и `move`.
